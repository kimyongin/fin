# Database Overview

Read this file first for database work. Inspect only the relevant migration files when exact DDL, RPC bodies, grants, indexes, or RLS policies are needed.

## Scope

- Schema: `public`; all application records are tenant-scoped by `user_id`.
- Primary API surface: `app_*` RPCs for the web app and `mcp_*` wrappers for token-authenticated agents.

## Core Data Model

| Area | Tables | Notes |
| --- | --- | --- |
| Identity and sharing | `profiles`, `viewer_sessions`, `friendships`, `feature_sharing_policies`, `feature_sharing_grants` | Profiles can enable password-protected sharing. Guest sessions expire after seven days; logged-in friends retain read-only access until removed. Feature grants use stable read keys; the UI currently offers a simple portfolio-only versus portfolio-and-reviews bundle. |
| Accounts and holdings | `accounts`, `holdings`, `trade_previews`, `trade_entries`, `holding_reconciliation_previews`, `holding_reconciliations`, `holding_verifications`, `entity_note_mutation_receipts`, other mutation receipts | Holdings preserve the existing projection and add a numeric quantity/cost pool plus state version. Completed market trades and absolute corrections still use version-bound previews. The reversal tables/RPCs were removed by `20260923035022_retire_trade_reversal_storage.sql`; a wrong entry is corrected against current brokerage values. Historical reversed-at fields remain readable. Verification snapshots only explicitly checked fields and never mutates values. Existing public notes remain shared. Local migration adds owner-only `private_note` on instruments/holdings for current holding reasons; `app_list/save_private_holding_note` uses current-value CAS without changing financial state. |
| Instruments and prices | `instruments`, `instrument_tags`, `tags`, `holding_prices_daily` | An instrument belongs to one user and ticker; tags have a name and sort order, and prices are per user, ticker, and date. |
| Portfolio outputs | `activity_reports`, `activity_report_revisions`, `sync_runs`, `strategies`, `strategy_buckets`, `strategy_bucket_tags`, `strategy_bucket_mode_targets` | Active mode, mode-specific strategy targets, price-sync results, and source-linked activity retrospectives. The zero-row legacy `portfolio_snapshots`, `daily_reports`, and `rebalance_suggestions` tables (plus legacy `transactions`) are removed by `20260923042049_retire_unreferenced_legacy_outputs.sql`; the migration aborts if any acquired rows since the audit. |
| News research | `activity_events` (`record_kind=research`) | ChatGPT researches current sources; one owner-only activity keeps the result and bounded source context. Separate fact/opinion tables and their writers were removed by `20260923043008_retire_news_storage.sql`. The old daily-context base still receives an empty `saved_news` compatibility object until the review context is simplified. |
| Daily review | `daily_review_contexts`, `daily_briefings`, `daily_briefing_evidence`, `daily_briefing_scopes`, `daily_briefing_scope_sources`, `daily_briefing_scope_evidence`, `daily_review_mutation_receipts` | Short-lived server-owned analysis inputs and a single durable briefing aggregate containing the consumed snapshot, conclusions, uncertainties, source evidence, checked sources, and research windows. Mutation receipts make briefing saves idempotent. |
| Decisions and follow-ups | `investment_decisions`, `investment_decision_state_history`, `portfolio_tasks`, `portfolio_task_history`, `portfolio_task_evidence`, `investment_decision_tasks`, `execution_plans`, `task_fill_links`, `general_task_occurrence_states`, `decision_task_mutation_receipts`, `general_task_mutation_receipts` | Owner-only decisions, general tasks, research questions, and quantity-based execution plans. Decision content/status/history remains authoritative here while its activity event carries the visible question and direct target ID for unified navigation. A general task stores intent; completion/reopen events preserve performed facts. `origin_event_id` optionally identifies the one activity that directly caused a follow-up task. Daily recurrence keeps one task row and only projects dates that were completed or reopened, so future or missed dates are never materialized. |
| Legacy ToDo bundles | Removed by `20260923033412_retire_legacy_todo_bundle_storage.sql` | Prior migration mapped legacy items to general tasks or activities. The old bundle tables and RPCs are no longer part of the current schema; clients use tasks and activities. |
| Personal investment policy | `principles` | Owner-only goals, horizon, liquidity, risk/trading preferences, and explicit preferences/prohibitions are individual principle rows. Parallel profile/history/receipt tables were retired by `20260923041318_retire_investment_policy_storage.sql`. |
| Operating principles | `principles` (`kind=operation`, `scope=workflow`) | Data-handling conventions use the same owner-only principle revisions. The separate rule/history/receipt tables were removed by `20260923040254_retire_operating_rule_storage.sql`. A rule never bypasses current instructions or validation. |
| Simplified principles (local migration; production pending) | `principles` | One row per actual change, stable `principle_id` plus row `id`, server `effective_at` and `ended`. Owner-only current/as-of reads and append writes use `app_list_principles` / `app_save_principle`. Existing policy text, current restrictions, operating rules, and strategy notes are backfilled. |

| Holding reasons | `instruments.private_note`, `holdings.private_note` | Owner-only current reasons are stored directly on the instrument or account holding. The parallel thesis/history/task-link tables and close-position trigger were removed by `20260923035616_retire_holding_thesis_storage.sql`. The public `note` field remains separate. |
| Product feedback | `product_feedback`, `product_feedback_mutation_receipts`, `product_feedback_admins`, `product_feedback_admin_events` | App-quality feedback is separate from investment decisions and tasks. Reporters can read only their own submissions; allowlisted feedback admins are managed independently from portfolio permissions. Submission context accepts only short operational fields and never captures chat transcripts, holdings, email, or tokens. Admin events preserve status/response/link changes without duplicating feedback bodies. |
| Audit and agent access | `activity_events`, `activity_tags`, `activity_event_tags`, `portfolio_task_activity_tags`, `activity_embeddings`, `activity_mutation_receipts`, `agent_tokens` | User and agent actions are recorded with an occurrence timestamp/date distinct from storage time. An activity keeps its editable current title/note/result/conclusion and a minimal conflict version in the same row; no separate result/history table is used. `record_kind` distinguishes general, research, review, decision, retrospective, trade, reconciliation, and task without another record table. Manual records can select only non-financial kinds and optionally carry validated source/scope context; server-triggered financial kinds cannot be spoofed. Reusable activity tags are independent from allocation tags; task completion copies the current task tags without changing older occurrences. `activity_embeddings` is a rebuildable pgvector projection keyed by the current narrative hash, not a second activity source. Automatic financial before/after values and references stay protected. |

`portfolio_view` joins holdings, accounts, instruments, and the newest price. It converts USD values with the latest available `USDKRW=X` price.

The local `app_create_daily_context` wrapper includes the current owner-only `principles.items` and `private_holding_notes` in the persisted context snapshot. The old `investment_policy` field was removed. General portfolio DTOs and automatic activity JSON recursively redact private-note keys; shared briefing DTOs omit the context snapshot.

Instrument types are constrained to `market` for market-priced investments, `valuation` for evaluation-based investments, `cash` for cash balances, and `fx` for system-managed exchange rates.

## RPC Groups

| Prefix | Purpose |
| --- | --- |
| `app_save_*`, `app_delete_*`, `app_bulk_save_portfolio_rows` | Create, update, and remove accounts, holdings, instruments, and tags while writing activity events. The bulk editor saves up to 200 portfolio rows atomically as one user action and records whole-portfolio before/after snapshots. Direct market/valuation/cash balance edits advance the holding checkpoint/version; memo-only and unchanged saves do not. |
| `app_find_holdings`, `app_get_portfolio_state`, `app_get_portfolio_valuation_quality`, `app_list_recent_activity`, `app_list_action_timeline` | Web app read models. Portfolio state includes explicit known, missing, and stale valuation quality; missing prices or FX rates are never treated as zero. The action timeline applies feature permissions, date/filter rules, representative-event suppression, and stable pagination before returning pending work plus date groups. |
| `app_update_entity_note` | Idempotently update only an existing account, instrument, or holding note after comparing the normalized expected note. A real change writes one activity event; an unchanged retry/success writes none and does not change financial holding state. |
| `mcp_*` | Agent-token wrappers around portfolio, strategy, and news reads or mutations, plus price upserts and sync-run recording. |
| `agent_*` | Manage tokens and update holding average price. |
| `set_viewer_profile`, `unlock_viewer_access`, `get_active_viewer_access` | Configure and validate password-protected portfolio sharing. |
| `add_friend`, `list_friends`, `remove_friend` | Create, list, and remove persistent friend portfolio access after password verification. |
| `app_get_sharing_policy`, `app_update_sharing_policy`, `app_get_shared_feature_access`, `can_view_feature` | Read/CAS-update per-feature read grants and resolve the effective read features for a selected valid viewer/friend relationship. Missing new features default to deny; legacy asset/strategy/news/activity sharing remains enabled for compatibility. |
| `app_*_for_owner` review DTOs | Return allowlisted briefing, decision, and task reads for the selected owner only when the matching feature grant is enabled. Private policy snapshots, histories, context snapshots, and research evidence are omitted unless separately allowed. |
| `app_get_strategy_state`, `app_save_strategy` | Read a shared strategy or save the owner's active mode, detailed principles, buckets, mode targets, tag mappings, and rules. |
| Legacy news RPCs | Separate news read/write and token MCP tools were removed. New research uses activity CRUD/search; a temporary empty `app_get_news_state` response only supports the older daily-context base. |
| `app_create_daily_context` | Assemble the current portfolio, strategy, saved news, current content of the latest performed activities, previous briefing, last research scopes, current decisions, and unified pending tasks into a six-hour server-owned context without marking a review complete. Task-maintenance events are excluded from recent activity, and the legacy `todo_bundles` projection is explicitly marked `retired`. It accepts at most 200 subjects, limits snapshots to 2 MiB, and retains at most ten active contexts per user. |
| `app_save_daily_briefing` | Atomically copy a valid context snapshot into one briefing aggregate, save evidence and research scopes, write an activity event, and return the original result for an identical idempotent retry. |
| `app_get_daily_briefing`, `app_list_daily_briefings` | Read one complete owner-only briefing aggregate or list compact briefing summaries. |
| `app_list_daily_briefing_page` | Owner-aware allowlisted briefing summaries with stable `(analyzed_at,id)` keyset pagination. |
| `app_list_briefing_related_tasks` | Resolve briefing→decision→task relations before applying the display limit. Owner and shared reads return an explicit `ok`, `forbidden`, or `not_found` status; shared reads require all three relevant feature grants. |
| `app_record_investment_decision` | Atomically record a proposed or explicitly adopted decision plus zero to three research follow-ups. It is idempotent and cannot create an execution plan, trade, order, or holding change. |
| `app_get/list_investment_decision*`, `app_get/list_portfolio_task*` | Read owner-only decision/task detail and compact lists. Initial history and decision-task snapshots preserve what was linked at creation. |
| Legacy bundle RPCs | Removed with the legacy bundle tables. New clients use general tasks, automatic events, and manual activities. |
| `app_list_investment_decision_page`, `app_list_portfolio_task_page` | Owner-aware allowlisted keyset pages for the combined judgment/work queue. Filters are applied before pagination; `(updated_at,id)` cursors remain stable when timestamps tie. |
| `app_transition_investment_decision`, `app_transition_portfolio_task` | Apply idempotent expected-version transitions. Proposed decisions can be adopted/dismissed; research tasks can wait, resolve with evidence, reopen with new evidence, pause, resume, or close. These RPCs never change holdings or record trades. |
| `app_save_execution_task`, `app_link_trade_to_task`, `app_transition_execution_task` | Create/revise a market quantity plan, link an already-recorded matching fill, or pause/resume/cancel the plan. Progress is planned/partial/completed and includes overfill without altering or creating trades. |
| `app_list_general_task_page`, `app_get_general_task`, `app_save_general_task`, `app_transition_general_task`, `app_record_manual_activity` | Page/read owner-only general tasks, create or version-edit one-time/daily intent, complete/reopen a specific local-date occurrence, end future recurrence, or record explicit user-reported work already done outside the app. New general-task writes reject pause/resume; existing paused general tasks are ended without creating performed work, while their old history remains. Ending a repeat never creates a completion occurrence. Daily status uses a transactional occurrence projection and returns open again on the next local day without generating task rows. Writes use operation-scoped idempotency receipts; manual activity never changes financial records. |
| `app_create_activity`, `app_get_activity`, `app_update_activity`, `app_delete_manual_activity`, `app_create_activity_follow_up` | Create/read/edit a performed activity in place or create one future general task linked to its direct origin. Manual work can correct its non-financial category and bounded source/scope context, or be deleted with its searchable content scrubbed; linked follow-up tasks remain. Task/financial automatic facts cannot be deleted this way. Shared reads require the activity grant and additionally exclude private research/review/decision/retrospective kinds; writes remain owner-only. |
| `app_list/save/delete_activity_tag`, `app_set_activity_tags`, `app_set_general_task_tags`, `app_search_activities` | Manage owner activity tags and search the unified todo/done experience by current keyword, period, state, conclusion presence, account, instrument, and tags. Filters and sharing checks run before stable pagination. |
| `app_list_activity_embedding_jobs`, `app_upsert_activity_embedding`, `app_search_activity_semantic` | Maintain a rebuildable current-content embedding projection and retrieve related completed activities. Content hashes reject stale writes; ownership/sharing and structured filters are applied before the bounded semantic result. Edge callers merge it with keyword results and fall back to keyword-only search when embeddings are unavailable. |
| `app_get_activity_report_context`, `app_list_activity_reports`, `app_get_activity_report`, `app_save_activity_report` | Page complete current-content period action sources, list/read saved retrospectives with a regeneration flag, and idempotently save a versioned daily/weekly/monthly report. Included activity edits/date moves and newly included period activities mark the saved summary stale without rewriting it. Current open tasks are explicitly not a reconstructed historical period-end state, and saving a report does not create an action event. |
| Legacy personal-policy RPCs | Removed with the profile/history/receipt tables. Read and save individual `principles` rows for owner-only investment preferences; strategy allocation remains separate. |
| Legacy operating-rule RPCs | Removed. Read and save `kind=operation` principles, filtering by scope for the relevant workflow. |
| Legacy holding-thesis RPCs | Removed with the parallel thesis tables. Use owner-only private holding notes and a separate general task for future review. |
| `app_preview_trade_entry`, `app_log_completed_trade`, `app_list_transactions` | Preview a user-reported completed market buy/sell against the current version, confirm that exact preview idempotently while updating the holding projection, or list the new local trade ledger. Confirmation serializes one account/instrument stream before checking the locked holding so competing previews cannot overwrite one another, including first-holding creation. These RPCs never place brokerage orders, move cash, or mark balances verified. |
| `app_list_transaction_page` | Read owner-only trade history after applying optional instrument/account filters, with stable `(created_at,id)` keyset pagination. The legacy `app_list_transactions` contract remains available for existing MCP clients. |
| `app_preview_holding_reconciliation`, `app_reconcile_holding`, `app_verify_holding`, `app_get_holding_integrity` | Preview/apply an absolute market, valuation, or cash checkpoint; record only explicitly compared brokerage fields; and read whether the latest verification predates a holding change. Verification save/current-read responses include the optional note and source; an old idempotency receipt may retain its original smaller response. Price sync and briefing writes do not affect verification. An identical verification retry returns its stored success before checking the now-current holding version. |
| `app_get_portfolio_integrity` | Summarize verified, changed-since, and never-verified current holdings across the portfolio and by account without changing balances or treating old status as an error. |
| `app_get_price_sync_targets`, `app_upsert_price_rows`, `app_record_price_sync_run` | Resolve only the owner's held market and FX instruments, store validated Yahoo prices and resolved source symbols through an ownership-scoped contract, and record one auditable web sync result. Non-market holdings and null holiday rows are excluded. |
| Legacy trade reversal RPCs | Removed with the reversal tables. Confirm current brokerage values and apply an absolute correction; no historical replay is offered. |
| `app_submit_product_feedback`, `app_list_my_product_feedback`, `app_is_product_feedback_admin` | Idempotently submit app-quality feedback with an allowlisted operational context, list only the reporter's own feedback with keyset pagination, and expose whether the signed-in user has the independent feedback-admin role. |
| `app_list_product_feedback_admin`, `app_update_product_feedback_admin` | Allow only explicitly allowlisted feedback admins to page/filter the private triage queue and CAS-update status, public response, and one canonical GitHub issue link. Resolving requires a response; changes write a minimal admin event and grant no investment-data access. |

## Access Rules

- RLS applies to every application table.
- Owners have full access to their own rows through `auth.uid() = user_id` policies.
- Selected portfolio data can be read by an authorized guest viewer or friend through the relationship check plus `can_view_feature`; new review DTOs deny missing grants.
- Use RPCs for mutations where possible: they enforce ownership and create audit events.
- Daily review mutation/context internals remain owner-only. An explicit briefing grant exposes only the shared DTO; research evidence has a separate feature key.
- Decision/task mutation, history, and receipt tables remain owner-only. Explicit feature grants expose allowlisted read DTOs only.
- General-task mutation receipts and task detail are owner-only. New action events follow the existing `activity` feature grant and expose only the event DTO, never private task history through that grant.
- Research, review, decision, and retrospective activity events are owner-only even when the legacy `activity` feature grant permits a friend to read general/financial events. All detail, timeline, recent, keyword, and semantic RPCs filter these before limiting results.
- Personal investment policy profiles and history are owner-only and are not included in existing strategy sharing responses.
- Operating principles remain owner-only and are not included in existing strategy or portfolio sharing responses.
- Private instrument/holding reasons remain owner-only and are excluded from existing portfolio or strategy sharing responses.
- Product feedback is never shared with friends or guests and is excluded from portfolio activity, daily-review context, and CSV exports. Direct mutation is denied; submission uses the RPC contract.

- UI or Edge Function behavior only: inspect the relevant client/function and this overview; do not load migrations by default.
- Table, RPC, view, trigger, RLS, index, or grant change: inspect only the relevant migration files, add an incremental migration, then refresh this overview.
