# Database Overview

Read this file first for database work. Inspect only the relevant migration files when exact DDL, RPC bodies, grants, indexes, or RLS policies are needed.

## Scope

- Schema: `public`; all application records are tenant-scoped by `user_id`.
- Primary API surface: `app_*` RPCs for the web app/OAuth MCP and retained `mcp_*` wrappers for token-authenticated agents.

## Core Data Model

| Area | Tables | Notes |
| --- | --- | --- |
| Identity and sharing | `profiles`, `viewer_sessions`, `friendships` | One `sharing_enabled` flag grants authenticated friends or valid password viewers read-only access to the user-facing portfolio: assets, allocation, activity/tasks, and principles/history. The 2026-09-26 scope migration turned existing shares OFF once; re-enabling requires `input_share_scope='portfolio_all'`. Feature grant tables and their policy RPCs are retired. Passwords, tokens, feedback, and internal execution data remain private. `list_friends` returns the owner's avatar only while sharing remains enabled; guests expire after seven days. `friendships.last_viewed_at` is nullable and records the most recent successful web view signaled by a connected, nonanonymous friend; it is not an audit trail. |
| Accounts and holdings | `accounts`, `holdings`, `entity_note_mutation_receipts`, `holding_correction_mutation_receipts`, trade receipts | Holdings preserve the existing projection and numeric quantity/cost pool and state version. Web/OAuth trade and absolute-correction flows estimate without saving a preview, then lock and version-check a direct write. Each performed fact is an automatic `activity_events` row, not a parallel ledger. There is no separate verified/unverified state or brokerage-comparison checkpoint. The old trade, correction, and verification tables were retired. Account notes and the common instrument note remain; account-holding rows have no note column. |
| Instruments and prices | `instruments`, `instrument_tags`, `tags`, `holding_prices_daily` | An instrument belongs to one user and ticker; tags have a name and sort order, and prices are per user, ticker, and date. |
| Portfolio outputs | `sync_runs`, `allocation_targets` | Each owned asset tag has at most one current percentage target; mode, bucket, and recommendation settings were removed by `20260923175703_simplify_tag_allocation.sql`. Targets are read with the strategy sharing grant, independently from assets. Price-sync results remain in `sync_runs`. A requested retrospective is an ordinary activity body with an optional user tag. |
| News research and reviews | `activity_events` | ChatGPT researches current sources; only explicit save intent creates an ordinary title/body/tag activity. `app_get_daily_context` is read-only current context with recent activities, not preclassified review/decision rows. Separate news and briefing tables were retired. |
| Decisions and tasks | `activity_events`, `portfolio_tasks`, `general_task_occurrence_states`, `general_task_mutation_receipts` | A recorded judgment is an ordinary activity body; a general task stores future intent independently. Completion/reopen events preserve performed facts and may retain `task_id` for navigation. None/daily/weekly schedules keep one task row, optional local time, timezone, and (weekly only) ISO weekday array. The server computes the latest due occurrence without materializing future rows; `app_list_due_general_tasks` pages the owner-only due queue for on-demand agent work. The current-row version remains for competing edits/transitions. |
| Legacy ToDo bundles | Removed by `20260923033412_retire_legacy_todo_bundle_storage.sql` | Prior migration mapped legacy items to general tasks or activities. The old bundle tables and RPCs are no longer part of the current schema; clients use tasks and activities. |
| Personal and operating principles | `principles` | One current Markdown document, with previous full bodies and optional `change_note` retained as dated rows. Explicit-owner read overloads allow a valid whole-portfolio viewer to read current/history; writes remain owner-only. The latest owner row (effective_at, id) is current; old owner-only read signatures remain for internal callers. Existing principle_id and ended columns remain for historical compatibility but new writes reuse the current ID and cannot end individual documents. Saved text is context, never authority to bypass current instructions or validation. |

| Holding reasons | `instruments.note` | A single common instrument memo follows the existing asset-sharing boundary. Private instrument/holding columns and their dedicated read/write RPCs were retired by #124; prior private text is not auto-copied into shared notes. Account notes remain separate. |
| Product feedback | `product_feedback`, `product_feedback_mutation_receipts`, `product_feedback_admins`, `product_feedback_admin_events` | App-quality feedback is separate from investment decisions and tasks. Reporters can read only their own submissions; allowlisted feedback admins are managed independently from portfolio permissions. Submission context accepts only short operational fields and never captures chat transcripts, holdings, email, or tokens. Admin events preserve status/response/link changes without duplicating feedback bodies. |
| Activity and agent access | `activity_events`, `activity_tags`, `activity_event_tags`, `portfolio_task_activity_tags`, `activity_embeddings`, `activity_mutation_receipts`, `agent_tokens` | A manual activity has title, editable Markdown `body`, occurrence time, optional owner-validated `task_id` and `instrument_id`, and ordinary tags. The legacy activity `holding_id` column and holding/account search filters are removed; automatic holding writes resolve the common instrument while the financial execution target remains a holding ID. The former `record_kind` classifier is removed by `20260924147000_remove_activity_kind.sql`; historic meaningful kinds are copied once to ordinary tags. Automatic financial records keep execution-time readable values without private notes/verification JSON. Editing/deleting a record does not reverse financial/task state or clear financial retry receipts. Embeddings are rebuildable from title/body. The wider `activity` sharing grant starts denied; related task/asset references require their separate grants. |

`portfolio_view` joins holdings, accounts, instruments, and the newest price. It converts USD values with the latest available `USDKRW=X` price.

`app_get_daily_context` is a read-only current owner context with portfolio (including common instrument notes), strategy, principles, open tasks, and recent activities. It does not insert a snapshot or classify records as reviews/decisions. General portfolio DTOs and generic edit activity JSON redact verification details.

Instrument types are constrained to `market` for market-priced investments, `valuation` for evaluation-based investments, `cash` for cash balances, and `fx` for system-managed exchange rates.

## RPC Groups

| Prefix | Purpose |
| --- | --- |
| `app_save_*`, `app_delete_*`, `app_bulk_save_portfolio_rows` | Create, update, and remove accounts, holdings, instruments, and tags while writing activity events. The bulk editor saves up to 200 portfolio rows atomically as one user action and records whole-portfolio before/after snapshots. Direct market/valuation/cash balance edits advance the holding checkpoint/version; memo-only and unchanged saves do not. |
| Retired `app_save_asset_detail` | The old private-note-aware detail writer was removed by #124. Do not restore it for existing clients; refresh the web app. |
| `app_save_asset_detail_current` | The #124 web path saves direct current values, common instrument note and optional explicit price. It checks expected versions and inserts one instrument-linked activity containing account changes and an optional reason in the same transaction. It neither accepts nor returns retired private/holding memo fields. |
| `app_find_holdings`, `app_get_portfolio_state`, `app_get_portfolio_valuation_quality`, `app_list_recent_activity`, `app_list_action_timeline` | Web app read models. Portfolio state includes explicit known, missing, and stale valuation quality; missing prices or FX rates are never treated as zero. The action timeline applies feature permissions, date/filter rules, representative-event suppression, and stable pagination. Its task section retains each active recurring definition after a completed occurrence or before its first due time, projecting `done` or `not_scheduled`; one-time completed tasks still leave the list. Legacy research/execution plans are not projected into pending work. |
| `app_update_entity_note` | Idempotently update only an existing account or instrument note after comparing the normalized expected note. A real change writes one activity event; an unchanged retry/success writes none and does not change financial holding state. |
| `mcp_*` | Retained agent-token wrappers around portfolio and strategy reads or mutations, plus price upserts and sync-run recording. Legacy news wrappers were removed. |
| `agent_*` | Legacy token listing/revocation and holding average-price update. `agent_create_token` was retired by `20260926064607_retire_agent_token_issuance.sql`; new MCP connections use OAuth. Existing token rows and token-authenticated endpoint remain for a separately verified retirement. |
| `set_viewer_profile`, `unlock_viewer_access`, `get_active_viewer_access`, `app_set_profile_avatar` | Configure and validate password-protected portfolio sharing. Avatar changes accept one of 20 predefined animal/fruit icons without mutating public name/password; an active guest session reads only its authorized owner's icon. |
| `add_friend`, `list_friends`, `remove_friend` | Create, list, and remove persistent friend portfolio access after password verification; authorized friend listings include the owner's chosen icon. |
| `set_viewer_profile`, `app_get_shared_feature_access`, `can_view_feature` | The four-argument profile writer requires `portfolio_all` scope for ON; the old three-argument writer can only turn sharing OFF. The shared-access response derives supported read keys from one relationship check; `can_view_feature` is a thin supported-key/relationship compatibility guard. Per-feature policy reads/writes are removed. |
| `app_list_portfolio_viewers`, `app_mark_shared_portfolio_view` | Owner-only reverse friendship pages expose only public name, avatar and last web-view time; connected nonanonymous friends can mark only their own successful view while the owner shares. Neither API exposes credentials or grants direct friendship updates. |
| `app_get_general_task_for_owner` | Return an owner general-task detail or a narrow friend detail only with the `tasks` grant. The friend response omits performed-event payloads and never exposes a task revision log. Activity sharing alone does not expose the task detail. |
| `app_get_strategy_state`, `app_save_allocation_targets` | Read configured per-tag targets under the strategy sharing grant, or atomically replace the owner's entire 100.00% target set. The save accepts an expected target set for concurrent-edit protection; identical retries are no-ops. Token MCP uses `mcp_save_strategy` with the same target contract. |
| Legacy news RPCs | Separate news read/write and token MCP tools, then the unused empty news-state compatibility RPC, were removed. New research uses activity CRUD/search. |
| Retired narrative pages | `app_list_narrative_activities` and the OAuth review/decision list tools were removed. Read all records through `app_search_activities` / `search_activities`, with date, keyword and ordinary tags. |
| `app_get_daily_context` | Owner-only current review context read, assembled from current portfolio/strategy/principles/private notes/open tasks and saved review/decision activities. Validates timezone and optional ticker list, caps response size, and does not insert a snapshot or claim a new review. |
| Legacy investment-decision and special-task RPCs | Removed with the parallel tables. Recorded judgments use ordinary activity CRUD/search; follow-ups use general-task RPCs. |
| Legacy bundle RPCs | Removed with the legacy bundle tables. New clients use general tasks, automatic events, and manual activities. |
| `app_list_general_task_page`, `app_list_due_general_tasks`, `app_get_general_task`, `app_save_general_task`, `app_save_general_task_detail`, `app_create_general_task_with_tags`, `app_transition_general_task` | Page/read owner-only general tasks, create or version-edit one-time/daily/weekly intent, and complete/reopen a due local-date occurrence or end future recurrence. The due queue is read-only, owner-only, paged by `next_offset`, and returns only the latest due unfinished occurrence per task; one-time tasks use a null external occurrence date. The owner detail includes selected tags; `app_save_general_task_detail` saves task fields and tags atomically with one idempotency receipt. New tagged task creation likewise calls the existing task and tag writers in one DB transaction; a failed tag write rolls back the task and action event. General-task writes reject pause/resume. Ending a repeat never creates a completion occurrence. The occurrence projection creates no future task rows. |
| `app_create_activity`, `app_create_activity_with_tags`, `app_get_activity`, `app_update_activity`, `app_save_activity_detail`, `app_delete_activity` | Create/read/edit/delete a readable activity. A related task summary is returned only with separate task access; `holding_id` is returned only with asset access. Tagged creation and detail save each compose validated field/tag writes in one transaction. Automatic records are editable/deletable, but the underlying financial/task state and financial retry receipts are not changed by record maintenance. Shared reads require an explicit activity grant and omit internal before/after JSON. |
| `app_list/save/delete_activity_tag`, `app_set_activity_tags`, `app_set_general_task_tags`, `app_search_activities` | Manage owner activity tags and search todo/done by keyword, period, state, account, instrument, holding, and ordinary tags. Active recurring definitions stay in todo results whether their latest occurrence is open, done, or not yet scheduled; task hits project that occurrence state and recurrence fields for web list actions. Multiple selected tags use OR by default or optional AND; different dimensions combine before pagination. No built-in activity kind or reserved tag controls access. Timeline cards show current title/body and tags. |
| `app_search_activity_references` | Owner-only, bounded search of existing instruments by name/ticker and all general tasks by title, including old ended tasks. Empty query returns no candidates; offset advances within the same search. The #125 form uses instrument ID rather than holding ID for new manual records. |
| `app_list_activity_embedding_jobs`, `app_upsert_activity_embedding`, `app_search_activity_semantic` | Maintain a rebuildable current-content embedding projection and retrieve related completed activities. Content hashes reject stale writes; ownership/sharing and structured filters are applied before the bounded semantic result. Edge callers merge it with keyword results and fall back to keyword-only search when embeddings are unavailable. |
| `app_get_activity_report_context` | Page title/body/tag period sources. A prior summary can appear among activities; the agent must not count it as a new real-world action. Current open tasks are not reconstructed historical period-end state. Requested retrospectives are ordinary activities found through normal search; there is no parallel report storage or automatic regeneration state. |
| Legacy personal-policy RPCs | Removed with the profile/history/receipt tables. Read and save individual `principles` rows for owner-only investment preferences; strategy allocation remains separate. |
| Legacy operating-rule RPCs | Removed. Read the active Markdown principle bodies for relevant conventions; no kind/scope filter remains. |
| Legacy holding-thesis/private-note RPCs | Removed. Use the common instrument note for an approved reason and a separate general task for future review. |
| `app_preview_trade_entry`, `app_record_completed_trade`, `app_list_transactions` | Estimate a user-reported completed market buy/sell without storage, then confirm the same inputs against a locked current holding and expected version with a financial idempotency key. The write updates `holdings` and one automatic trade activity; no separate trade ledger remains. These RPCs never place brokerage orders, move cash, or mark balances verified. |
| `app_list_transaction_page` | Read owner-only completed trade activities after optional instrument/account filters, with stable `(created_at,id)` keyset pagination. The legacy `app_list_transactions` response shape remains for existing MCP clients. |
| `app_preview_holding_reconciliation`, `app_apply_holding_correction` | Estimate/apply an absolute market, valuation, or cash correction without a persisted preview. The write retains owner checks, holding version conflict detection, idempotency, and one automatic correction activity, but has no confirmed-fields or verification-status branch. |

The trade and holding-correction/verification date guards use the `Asia/Seoul` business date, matching the UI default even between midnight and 09:00 KST when the PostgreSQL session date is still the prior UTC day.
| `app_create_instrument`, `app_save_asset_detail_current` | Create a new owner-scoped instrument without a holding or price; reject duplicate normalized tickers without overwriting existing data. Asset detail edits save instrument fields and current holdings atomically, but reject manual price fields. The internal asset-detail function retains the existing holding transaction and is not executable by clients. |
| `app_get_price_sync_targets`, `mcp_get_price_sync_targets`, `app_upsert_price_rows`, `app_record_price_sync_run` | Resolve the owner's registered market and FX instruments, including unheld market tickers, store validated Yahoo prices and resolved source symbols through an ownership-scoped contract, and record one auditable web sync result. Non-market instruments and null holiday rows are excluded. |
| Legacy trade reversal RPCs | Removed with the reversal tables. Confirm current brokerage values and apply an absolute correction; no historical replay is offered. |
| `app_submit_product_feedback`, `app_list_my_product_feedback`, `app_is_product_feedback_admin` | Idempotently submit app-quality feedback with an allowlisted operational context, list only the reporter's own feedback with keyset pagination, and expose whether the signed-in user has the independent feedback-admin role. |
| `app_list_product_feedback_admin`, `app_update_product_feedback_admin` | Allow only explicitly allowlisted feedback admins to page/filter the private triage queue and CAS-update status, public response, and one canonical GitHub issue link. Resolving requires a response; changes write a minimal admin event and grant no investment-data access. |

## Access Rules

- RLS applies to every application table.
- Owners have full access to their own rows through `auth.uid() = user_id` policies.
- Selected portfolio data can be read by an authorized guest viewer or friend through the one whole-portfolio relationship check plus supported-key allowlist. Every mutation remains owner-only.
- Use RPCs for mutations where possible: they enforce ownership and create audit events.
- Current daily context is owner-only and read-only; it returns recent ordinary activities without a saved briefing or decision classification.
- General-task mutation receipts and full task history remain owner-only. Valid viewers receive narrow task detail and linked activity summaries, never private execution payloads.
- Readable activity titles/bodies/tags and principle current/history are part of whole-portfolio sharing. Internal execution JSON remains owner-only. The legacy raw recent feed is owner-only.
- Private instrument/holding reasons remain owner-only and are excluded from existing portfolio or strategy sharing responses.
- Product feedback is never shared with friends or guests and is excluded from portfolio activity, daily-review context, and CSV exports. Direct mutation is denied; submission uses the RPC contract.
