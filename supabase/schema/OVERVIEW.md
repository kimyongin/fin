# Database Overview

Read this file first for database work. Inspect only the relevant migration files when exact DDL, RPC bodies, grants, indexes, or RLS policies are needed.

## Scope

- Schema: `public`; all application records are tenant-scoped by `user_id`.
- Primary API surface: `app_*` RPCs for the web app/OAuth MCP and retained `mcp_*` wrappers for token-authenticated agents.

## Core Data Model

| Area | Tables | Notes |
| --- | --- | --- |
| Identity and sharing | `profiles`, `viewer_sessions`, `friendships`, `feature_sharing_policies`, `feature_sharing_grants` | Profiles can enable password-protected sharing. Guest sessions expire after seven days; logged-in friends retain read-only access until removed. Feature grants use stable read keys; the UI currently offers a simple portfolio-only versus portfolio-and-reviews bundle. |
| Accounts and holdings | `accounts`, `holdings`, `entity_note_mutation_receipts`, financial mutation receipts | Holdings preserve the existing projection and add numeric quantity/cost pool and state version. Web/OAuth trade and absolute-correction flows estimate without saving a preview, then lock and version-check a direct write. Each performed fact is an automatic `activity_events` row, not a parallel ledger. The latest explicit brokerage comparison is one private `holdings.last_verification` JSON checkpoint; a standalone verification also produces a private automatic activity. The old trade, correction, and verification tables were retired. Shareable portfolio DTOs and generic edit activities redact `private_note` and `last_verification`; only explicit owner integrity APIs return verification details. Existing public notes remain shared. |
| Instruments and prices | `instruments`, `instrument_tags`, `tags`, `holding_prices_daily` | An instrument belongs to one user and ticker; tags have a name and sort order, and prices are per user, ticker, and date. |
| Portfolio outputs | `sync_runs`, `strategies`, `strategy_buckets`, `strategy_bucket_tags`, `strategy_bucket_mode_targets` | Active mode, allocation targets, and price-sync results. A requested retrospective is one owner-only `activity_events` row (`record_kind=retrospective`); parallel report/revision/receipt tables were retired by `20260923043832_retire_activity_report_storage.sql`. |
| News research | `activity_events` (`record_kind=research`) | ChatGPT researches current sources; one owner-only activity keeps the result and bounded source context. Separate fact/opinion tables and their writers were removed by `20260923043008_retire_news_storage.sql`. |
| Daily review | `activity_events` (`record_kind=review`) | The current review context is read-only via `app_get_daily_context`; only explicitly saved reviews create activity rows. The seven parallel context/briefing tables were retired by `20260923053741_retire_briefing_storage.sql`. |
| Decisions and tasks | `activity_events` (`record_kind=decision`), `portfolio_tasks`, `general_task_occurrence_states`, `general_task_mutation_receipts` | A decision is a current-content activity; a general task stores future intent independently. Completion/reopen events preserve performed facts; a completed event retains `task_id` to show the original task. The reverse `origin_event_id` follow-up link was retired. Daily recurrence keeps one task row and projects only actual completion/reopen dates. Parallel decision/research/plan tables and the obsolete `research_state` column were retired; the current-row version remains solely for competing edits/transitions. |
| Legacy ToDo bundles | Removed by `20260923033412_retire_legacy_todo_bundle_storage.sql` | Prior migration mapped legacy items to general tasks or activities. The old bundle tables and RPCs are no longer part of the current schema; clients use tasks and activities. |
| Personal and operating principles | `principles` | Owner-only Markdown body with nullable `change_note`, stable `principle_id`, revision row `id`, server `effective_at`, and `ended`. Current/as-of reads and append writes use `app_list_principles` / `app_save_principle`; `app_list_principle_changes` pages changes for the timeline. The `20260923173731_simplify_principles_markdown.sql` migration moves legacy kind/scope into the body once, then removes both columns and their index. Separate policy/rule storage was retired earlier. Saved text is context, never authority to bypass current instructions or validation. |

| Holding reasons | `instruments.private_note`, `holdings.private_note` | Owner-only current reasons are stored directly on the instrument or account holding. The parallel thesis/history/task-link tables and close-position trigger were removed by `20260923035616_retire_holding_thesis_storage.sql`. The public `note` field remains separate. |
| Product feedback | `product_feedback`, `product_feedback_mutation_receipts`, `product_feedback_admins`, `product_feedback_admin_events` | App-quality feedback is separate from investment decisions and tasks. Reporters can read only their own submissions; allowlisted feedback admins are managed independently from portfolio permissions. Submission context accepts only short operational fields and never captures chat transcripts, holdings, email, or tokens. Admin events preserve status/response/link changes without duplicating feedback bodies. |
| Audit and agent access | `activity_events`, `activity_tags`, `activity_event_tags`, `portfolio_task_activity_tags`, `activity_embeddings`, `activity_mutation_receipts`, `agent_tokens` | User and agent actions are recorded with an occurrence timestamp/date distinct from storage time. An activity keeps its editable current title/note/result/conclusion and a minimal conflict version in the same row; no separate result/history table is used. `record_kind` distinguishes general, research, review, decision, retrospective, trade, reconciliation, and task without another record table. Manual records can select only non-financial kinds and optionally carry validated source/scope context; server-triggered financial kinds cannot be spoofed. Reusable activity tags are independent from allocation tags; task completion copies the current task tags without changing older occurrences. `activity_embeddings` is a rebuildable pgvector projection keyed by the current narrative hash, not a second activity source. Automatic trade, correction, and verification activities are owner-only in shared detail/search/timeline/recent APIs. Legacy agent tokens remain because the app exposes token issuance and existing remote tokens have not been retired with their users. |

`portfolio_view` joins holdings, accounts, instruments, and the newest price. It converts USD values with the latest available `USDKRW=X` price.

`app_get_daily_context` is a read-only current owner context with portfolio, strategy, principles, private holding notes, open tasks, and saved review/decision activities. It does not insert a snapshot. The legacy stored contexts and briefing aggregate were retired. General portfolio DTOs and generic edit activity JSON recursively redact private-note and verification keys.

Instrument types are constrained to `market` for market-priced investments, `valuation` for evaluation-based investments, `cash` for cash balances, and `fx` for system-managed exchange rates.

## RPC Groups

| Prefix | Purpose |
| --- | --- |
| `app_save_*`, `app_delete_*`, `app_bulk_save_portfolio_rows` | Create, update, and remove accounts, holdings, instruments, and tags while writing activity events. The bulk editor saves up to 200 portfolio rows atomically as one user action and records whole-portfolio before/after snapshots. Direct market/valuation/cash balance edits advance the holding checkpoint/version; memo-only and unchanged saves do not. |
| `app_find_holdings`, `app_get_portfolio_state`, `app_get_portfolio_valuation_quality`, `app_list_recent_activity`, `app_list_action_timeline` | Web app read models. Portfolio state includes explicit known, missing, and stale valuation quality; missing prices or FX rates are never treated as zero. The action timeline applies feature permissions, date/filter rules, representative-event suppression, and stable pagination before returning only general pending tasks plus dated activities. Legacy research/execution plans are not projected into pending work. |
| `app_update_entity_note` | Idempotently update only an existing account, instrument, or holding note after comparing the normalized expected note. A real change writes one activity event; an unchanged retry/success writes none and does not change financial holding state. |
| `mcp_*` | Retained agent-token wrappers around portfolio and strategy reads or mutations, plus price upserts and sync-run recording. Legacy news wrappers were removed. |
| `agent_*` | Manage tokens and update holding average price. |
| `set_viewer_profile`, `unlock_viewer_access`, `get_active_viewer_access` | Configure and validate password-protected portfolio sharing. |
| `add_friend`, `list_friends`, `remove_friend` | Create, list, and remove persistent friend portfolio access after password verification. |
| `app_get_sharing_policy`, `app_update_sharing_policy`, `app_get_shared_feature_access`, `can_view_feature` | Read/CAS-update per-feature read grants and resolve the effective read features for a selected valid viewer/friend relationship. Missing new features default to deny; legacy asset/strategy/news/activity sharing remains enabled for compatibility. |
| `app_get_general_task_for_owner` | Return an owner general-task detail or a narrow friend detail only with the `tasks` grant. The friend response omits performed-event payloads and never exposes a task revision log. Legacy decision/special-task DTOs were retired; review and decision activity summaries use `app_list_narrative_activities`. |
| `app_get_strategy_state`, `app_save_strategy` | Read a shared strategy or save the owner's active mode, detailed principles, buckets, mode targets, tag mappings, and rules. |
| Legacy news RPCs | Separate news read/write and token MCP tools, then the unused empty news-state compatibility RPC, were removed. New research uses activity CRUD/search. |
| `app_list_narrative_activities` | Current saved review/decision activity page, newest first with `(occurred_at,id)` cursor. Owner receives context; friends require the matching `briefings` or `decisions` grant and receive a narrow summary without private note, source list, scope, or decision reason. A friend with the decision grant receives only the allowlisted proposed/adopted/dismissed state. Today and the OAuth review/decision list tools use this path. Parallel decision storage was retired. |
| `app_get_daily_context` | Owner-only current review context read, assembled from current portfolio/strategy/principles/private notes/open tasks and saved review/decision activities. Validates timezone and optional ticker list, caps response size, and does not insert a snapshot or claim a new review. |
| Legacy investment-decision and special-task RPCs | Removed with the parallel tables. New decisions use activity CRUD/narrative read; follow-ups use general-task RPCs. |
| Legacy bundle RPCs | Removed with the legacy bundle tables. New clients use general tasks, automatic events, and manual activities. |
| `app_list_general_task_page`, `app_get_general_task`, `app_save_general_task`, `app_create_general_task_with_tags`, `app_transition_general_task` | Page/read owner-only general tasks, create or version-edit one-time/daily intent, complete/reopen a specific local-date occurrence, or end future recurrence. New tagged task creation calls the existing task and tag writers in one DB transaction with the same operation-scoped key; a failed tag write rolls back the task and action event. General-task writes reject pause/resume. Ending a repeat never creates a completion occurrence. Daily status uses a transactional occurrence projection and returns open again on the next local day without generating task rows. |
| `app_create_activity`, `app_create_activity_with_tags`, `app_get_activity`, `app_update_activity`, `app_delete_manual_activity` | Create/read/edit a performed activity in place. A completion detail returns the original task summary in the same response only when task access is granted; reverse follow-up creation and its RPC were retired. New tagged activity creation calls the existing activity and tag writers in one DB transaction with the same operation-scoped key; a failed tag write rolls back the activity. Manual work can correct its non-financial category and bounded source/scope context, or be deleted with its searchable content scrubbed; independent tasks remain. Task/financial automatic facts cannot be deleted this way. Shared reads require the activity grant and additionally exclude private research/review/decision/retrospective/trade/reconciliation kinds; writes remain owner-only. |
| `app_list/save/delete_activity_tag`, `app_set_activity_tags`, `app_set_general_task_tags`, `app_search_activities` | Manage owner activity tags and search the unified todo/done experience by keyword, kind, period, state, conclusion, account, instrument, and tags. Optional `input_record_kinds` uses OR within kinds and AND with other filters; empty means all, omitted preserves the older single-kind argument. Filters/sharing checks precede pagination. Shared reviews require briefings permission and expose/search only public summary fields, not private notes/tags/context. Timeline cards include persisted `record_kind` and current narrative fields (migration `20260923140858_activity_kind_multi_select.sql`). |
| `app_list_activity_embedding_jobs`, `app_upsert_activity_embedding`, `app_search_activity_semantic` | Maintain a rebuildable current-content embedding projection and retrieve related completed activities. Content hashes reject stale writes; ownership/sharing and structured filters are applied before the bounded semantic result. Edge callers merge it with keyword results and fall back to keyword-only search when embeddings are unavailable. |
| `app_get_activity_report_context` | Page current-content period sources, excluding `retrospective` summaries from later source counts. The decision summary is derived from decision activities, not `investment_decisions`. Current open tasks are not reconstructed historical period-end state. Requested retrospectives are saved through `app_create_activity` with category `retrospective`, then found through normal activity search. There is no parallel report storage or automatic regeneration state. |
| Legacy personal-policy RPCs | Removed with the profile/history/receipt tables. Read and save individual `principles` rows for owner-only investment preferences; strategy allocation remains separate. |
| Legacy operating-rule RPCs | Removed. Read the active Markdown principle bodies for relevant conventions; no kind/scope filter remains. |
| Legacy holding-thesis RPCs | Removed with the parallel thesis tables. Use owner-only private holding notes and a separate general task for future review. |
| `app_preview_trade_entry`, `app_record_completed_trade`, `app_list_transactions` | Estimate a user-reported completed market buy/sell without storage, then confirm the same inputs against a locked current holding and expected version with a financial idempotency key. The write updates `holdings` and one automatic trade activity; no separate trade ledger remains. These RPCs never place brokerage orders, move cash, or mark balances verified. |
| `app_list_transaction_page` | Read owner-only completed trade activities after optional instrument/account filters, with stable `(created_at,id)` keyset pagination. The legacy `app_list_transactions` response shape remains for existing MCP clients. |
| `app_preview_holding_reconciliation`, `app_apply_holding_correction`, `app_verify_holding`, `app_get_holding_integrity` | Estimate/apply an absolute market, valuation, or cash correction without persisted preview; store only explicitly compared brokerage fields in the holding's latest-verification checkpoint; and read whether it predates a holding change. Standalone verification is also a private activity. Verification save/current-read responses include the optional note and source; an old idempotency receipt may retain its original smaller response. Price sync and briefing writes do not affect verification. An identical verification retry returns its stored success before checking the now-current holding version. |

The trade and holding-correction/verification date guards use the `Asia/Seoul` business date, matching the UI default even between midnight and 09:00 KST when the PostgreSQL session date is still the prior UTC day.
| `app_get_portfolio_integrity` | Summarize verified, changed-since, and never-verified current holdings across the portfolio and by account without changing balances or treating old status as an error. |
| `app_get_price_sync_targets`, `app_upsert_price_rows`, `app_record_price_sync_run` | Resolve only the owner's held market and FX instruments, store validated Yahoo prices and resolved source symbols through an ownership-scoped contract, and record one auditable web sync result. Non-market holdings and null holiday rows are excluded. |
| Legacy trade reversal RPCs | Removed with the reversal tables. Confirm current brokerage values and apply an absolute correction; no historical replay is offered. |
| `app_submit_product_feedback`, `app_list_my_product_feedback`, `app_is_product_feedback_admin` | Idempotently submit app-quality feedback with an allowlisted operational context, list only the reporter's own feedback with keyset pagination, and expose whether the signed-in user has the independent feedback-admin role. |
| `app_list_product_feedback_admin`, `app_update_product_feedback_admin` | Allow only explicitly allowlisted feedback admins to page/filter the private triage queue and CAS-update status, public response, and one canonical GitHub issue link. Resolving requires a response; changes write a minimal admin event and grant no investment-data access. |

## Access Rules

- RLS applies to every application table.
- Owners have full access to their own rows through `auth.uid() = user_id` policies.
- Selected portfolio data can be read by an authorized guest viewer or friend through the relationship check plus `can_view_feature`; new review DTOs deny missing grants.
- Use RPCs for mutations where possible: they enforce ownership and create audit events.
- Current daily context is owner-only and read-only. An explicit briefing grant exposes only the narrow saved review activity summary; research evidence has a separate feature key.
- General task mutation receipts and performed activity rows remain owner-only. Explicit feature grants expose only allowlisted general-task/decision-activity reads; the duplicate task revision table was retired.
- General-task mutation receipts and full task detail are owner-only. The explicit `tasks` feature grant permits only a narrow general-task friend detail, never private task history or event payloads. New action events follow the existing `activity` feature grant and expose only the event DTO.
- Research, review, decision, and retrospective activity events stay hidden from the legacy general `activity` grant. The dedicated narrative page can share a bounded review/decision summary under the corresponding explicit feature grant; private context, scope, source links, and notes stay owner-only. Detail, timeline, recent, keyword, and semantic general-activity RPCs still exclude these kinds for friends.
- Personal investment policy profiles and history are owner-only and are not included in existing strategy sharing responses.
- Operating principles remain owner-only and are not included in existing strategy or portfolio sharing responses.
- Private instrument/holding reasons remain owner-only and are excluded from existing portfolio or strategy sharing responses.
- Product feedback is never shared with friends or guests and is excluded from portfolio activity, daily-review context, and CSV exports. Direct mutation is denied; submission uses the RPC contract.
