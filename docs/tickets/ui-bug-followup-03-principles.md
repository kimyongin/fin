# 원칙 편집 보호와 날짜 조회 응답 순서 수정

2026-09-23 · 로컬 구현·격리 검증 완료, 운영 배포 전 · #99/#100 후속 버그.

## 근거와 재현 조건

PrincipleJournal.jsx의 날짜 effect 조회는 active로 무효화하지만 reload는 별도로 setItems한다. 저장 후 재조회/목록 재시도 중 날짜를 바꾸면 이전 응답이 선택 날짜의 목록을 덮어쓸 수 있다. ModalShell에 dirty가 없고 저장 중 입력도 열려 있어 닫기 시 초안 유실, 저장 도중 추가 편집 유실 위험이 있다. 정적 확인 단계이며 실제 지연 응답 재현은 구현 시 수행한다.

## 최소 범위

조회와 reload에 기존 createRequestGate를 적용하거나 하나의 조회 경로로 정리한다. 기존 ModalShell의 dirty/closeDisabled와 저장 중 입력 잠금을 재사용한다. 원칙 이력·안정 ID·재시도 계약은 변경하지 않는다.

## 완료 기준

- [x] 현재 조회를 지연하고 과거 날짜 조회를 먼저 완료해도 화면은 선택 날짜와 일치한다.
- [x] 목록 재시도에도 같은 순서 보호를 적용한다.
- [x] 원칙 추가/수정에서 닫기·취소·Escape의 초안 확인이 일관된다.
- [x] 저장 중 입력/중복 저장/닫기를 막는다.
- [x] 저장 성공 뒤 조회 실패는 계속 성공한 저장으로 취급하며 재조회만 가능하다.
- [ ] 기존 원칙 생성 재시도 테스트 및 모바일 390px/PC 1440px 회귀 결과를 기록한다.

별도 범용 비동기 상태 프레임워크는 추가하지 않는다.

## 구현·검증 기록 (2026-09-23)

PrincipleJournal 조회와 저장 후 재조회를 기존 `createRequestGate`로 묶고, 사용자가 날짜를 바꿀 때 이전 요청을 무효화한다. 편집 시작 초안과 현재 초안을 비교해 ModalShell의 닫기 확인을 사용한다. 저장 중에는 폼과 닫기를 잠근다. 성공 저장 뒤 목록 실패의 안내와 재조회만 재시도하는 흐름을 유지했다. 격리 브라우저에서 늦은 이전 날짜 응답, 미저장 취소, 기존 저장 재시도/재조회 시나리오가 통과했다. 운영 배포·실기기 확인은 하지 않았다.
