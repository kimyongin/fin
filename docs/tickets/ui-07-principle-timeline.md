# [UI/UX] 원칙 날짜 선택을 변경 타임라인으로 전환

2026-09-24 · P2 · 로컬 구현 및 자동 검증. 운영 DB 적용·배포·실기기 평가는 별개다.

GitHub: https://github.com/kimyongin/fin/issues/114

## 목적과 사용자 시나리오

사용자는 원칙이 변경된 날짜를 기억하지 못한다. 날짜를 추측해 선택하는 대신 현재 원칙을 읽고 아래로 내려가며 언제 어떤 원칙이 바뀌었는지 확인한다. 실제 변경 이력을 탐색하는 것이 목적이며 과거 포트폴리오 복원 기능으로 확대하지 않는다.

## 기존 구현 확인

- `src/features/strategy/PrincipleJournal.jsx`: 상단 날짜 선택기와 현재/해당 날짜 원칙 목록, 추가·수정·적용 종료 모달을 제공한다.
- `src/features/strategy/data.js`: `app_list_principles`와 `app_save_principle`의 어댑터다.
- `principles`: 같은 원칙을 묶는 `principle_id`, 행 `id`, 내용·종류·범위, `effective_at`, `ended`를 이미 저장한다. 소유자 전용이다.
- `app_list_principles`는 현재 또는 지정 날짜 말 기준의 원칙별 마지막 행을 반환한다. `input_include_ended=true`도 전체 변경 이력을 반환하는 옵션은 아니다.
- #89의 동일 테이블 이력 계약과 #99/#106의 저장 재시도·늦은 조회 응답·초안 보호를 재사용한다. 날짜 선택 UI 요구만 이 티켓으로 대체한다. 기존 현재/날짜 조회 API와 MCP 소비자는 유지한다.

## 화면 계약

```text
원칙                                  원칙 추가

현재 적용 중인 원칙
  투자 방향 · 내용                         수정
  운영 규칙 · 내용                         수정

변경 이력
  │ 9월 23일
  ● 14:30 수정 · 위험 허용
  │ 변경 후 내용
  │ 이전 내용 보기
  ● 09:10 적용 종료 · 운영 규칙
  │ 종료한 내용
  │ 9월 18일
  ● 08:20 추가 · 투자 방향
  │ 처음 등록한 내용

  이전 변경 더 보기
```

- 상단 날짜 선택기와 `현재로` 버튼을 제거한다. `원칙 추가`는 항상 현재 원칙에 대한 행동이다.
- 현재 원칙과 변경 이력을 위아래로 배치한다. 두 섹션 제목은 카드 밖에 같은 스타일로 둔다. 별도 탭·페이지·전체 상태 스냅샷 카드를 늘리지 않는다.
- 본문의 자연스러운 세로 스크롤을 사용한다. 내부 이중 스크롤, 스크롤 강제 이동, 새로운 타임라인 라이브러리는 필요 없다.
- 변경은 최신순이며 업무 시간대 기준 날짜별로 묶고 시각을 표시한다. 같은 날의 여러 변경을 합쳐 없애지 않는다.
- 각 항목은 `추가 / 수정 / 적용 종료`를 글자로 구별한다. 종류·적용 범위와 해당 변경 내용을 표시하며 색만으로 의미를 전달하지 않는다.
- 수정은 변경 후 내용을 먼저 표시하고 `이전 내용 보기`를 펼치면 같은 원칙의 바로 이전 내용·종류·범위를 확인한다. 단어 단위 diff 엔진은 추가하지 않는다.
- 종료 항목에는 무엇을 종료했는지 내용을 남긴다. 현재 활성 원칙이 없어도 종료된 과거 이력은 볼 수 있어야 한다.
- 수정·종료는 현재 원칙 목록에서만 수행한다. 과거 행 수정·복원·되돌리기 버튼은 추가하지 않는다.
- 처음에는 최근 20건을 표시하고 `이전 변경 더 보기`로 다음 페이지를 붙인다. 경계가 같은 날짜면 날짜 그룹을 이어 붙이며 기존 펼침·스크롤 위치를 유지한다.
- 최초 등록만 있으면 추가 이력을 표시한다. 이력이 없으면 빈 상태를, 조회 실패면 오류와 해당 목록 재시도를 표시한다. 로딩을 빈 원칙으로 표시하지 않는다.

## 최소 조회 계약과 구현 방향

정본은 기존 `principles`이며 새 이력 테이블·버전 번호·활동 본문 복제는 만들지 않는다. `app_save_principle`의 쓰기 계약은 그대로 사용한다.

- 현재 원칙: 기존 `app_list_principles`의 현재 조회를 재사용한다.
- 변경 이력: 소유자 전용 읽기 RPC `app_list_principle_changes(input_limit=20, input_cursor=null)`를 추가하는 방향으로 구현한다. 기존 API가 전체 이력 조회를 지원하지 않아 필요한 한 개의 목적별 조회다.
- 응답은 `items`와 `next_cursor`. 항목은 해당 변경 행, `change_type`, 같은 `principle_id`의 바로 이전 행 또는 null을 제공한다. 사용하지 않는 전체 과거 배열은 포함하지 않는다.
- 정렬·커서는 `(effective_at, id)` 내림차순이다. 이전 행은 현재 페이지 내 배열이 아닌 같은 소유자의 전체 원칙 행에서 찾는다. 따라서 페이지 경계에서도 추가/수정을 올바르게 구별한다.
- 종료 행은 `적용 종료`, 이전 행이 없는 비종료 행은 `추가`, 나머지는 `수정`으로 파생한다. 별도 분류 컬럼을 저장하지 않는다. 저장된 최초 행 이전의 이력을 추정하지 않는다.
- 인증 사용자 본인의 행만 반환하며 클라이언트가 임의 소유자를 지정하는 계약은 추가하지 않는다. 원칙의 기존 비공개·공유 경계를 유지한다.
- 페이지 크기는 서버에서 제한한다. 기존 인덱스와 실제 조회 계획을 먼저 확인하고 필요할 때만 조회용 인덱스를 추가한다.
- 최종 DTO/오류 계약은 구현 첫 단계에서 이 티켓에 기록한다. 새 프레임워크나 범용 이력 조회 엔진은 만들지 않는다.

## 상태·저장·문서 연결

- 현재 목록과 이력은 각각 로딩·오류·재시도 상태를 가진다. 이력 조회가 실패해도 이미 읽은 현재 원칙은 사용할 수 있다.
- 저장 성공 후 현재 목록과 최신 이력을 갱신한다. 이력은 첫 페이지부터 다시 조회하여 새 변경을 반영한다. 실패한 재조회만 다시 시도하며 저장을 재실행하지 않는다.
- 이전 페이지 요청 중 새 원칙을 저장하거나 화면을 떠나도 늦은 응답이 갱신된 목록을 덮어쓰지 않도록 기존 request gate를 재사용한다.
- `ModalShell`의 미저장 초안 확인·저장 중 잠금과 현재 행 충돌·동일 저장 재시도 처리를 유지한다.
- PRD, 화면 구조, START-HERE, 스키마 개요와 이 티켓을 갱신한다. 기존 `list_principles`/`save_principle` MCP 계약은 변경하지 않는다. 새 웹 조회를 자동으로 공개 MCP 도구로 늘리지 않는다. 제품 가이드에 날짜 선택 안내가 있으면 실제 화면에 맞게 수정하고, 영향이 없으면 검토 사유만 기록한다.

## 완료 기준

- [x] 날짜를 입력하지 않고 현재 원칙과 실제 변경 날짜·내용을 탐색할 수 있다.
- [x] 추가 → 수정 → 종료가 한 원칙의 이력으로 연결되고 이전 내용 비교가 정확하다. 같은 종류의 여러 원칙도 섞이지 않는다.
- [x] 같은 날 여러 변경·동일 시각 정렬·페이지 경계의 이전 내용·다음 페이지 중복/누락을 검증한다.
- [ ] 현재 원칙 없음/전체 종료/이력 없음/긴 내용/현재 조회 실패/이력 조회 실패를 구별한다.
- [ ] 생성·수정·종료 후 현재/이력이 함께 갱신되고, 저장 성공 후 조회 실패와 늦은 응답에서 중복 저장·목록 역전이 없다.
- [x] 인증 없음·다른 사용자 데이터 접근이 차단되며 공유 범위가 확대되지 않는다.
- [ ] 기존 현재/지정 날짜 조회와 MCP 저장·조회, 초안 보호·저장 재시도 회귀가 유지된다.
- [ ] 360/390/768/1024/1440px에서 페이지 가로 넘침 없이 현재 읽기·이력 펼침·더 보기·편집이 가능하다. 키보드 조작, 44px 조작 영역, 하단 메뉴와 본문 겹침을 확인한다.
- [ ] 관련 DB/API·사용자 시나리오 검사, 빌드, 인코딩과 diff 검사를 수행하고 실제 결과·미검증 범위를 기록한다.
- [ ] 문서와 티켓 상태를 갱신하고 로컬 구현·운영 적용·배포 여부를 구분한다.

## 진행 순서와 현재 상태

한 수직 슬라이스로 조회 계약 확정 → 기존 테이블 기반 이력 조회 → 현재 목록과 타임라인 연결 → 편집 후 갱신·검증을 진행한다. 운영 DB 적용·배포는 별도 단계다.

로컬 변경: `app_list_principle_changes(input_limit, input_cursor)`가 기존 `principles` 행에서 최신순 변경·바로 이전 행을 반환한다. `(effective_at,id)` 커서, 50건 상한과 소유자 제한을 적용했다. 현재 목록은 기존 RPC 그대로이고 새 조회를 MCP 도구로 공개하지 않았다. 날짜 선택 UI는 현재 원칙+변경 이력으로 대체했다. 저장 후 두 조회만 갱신하며 미저장 초안 보호를 유지한다.

검증: 원칙 변경·페이지 경계·다른 사용자 거부 DB 테스트, 현재/이력 오류 분리·저장 재시도·더 보기 E2E, 360/390/768/1024/1440px 레이아웃 E2E, 전체 DB/브라우저·빌드·인코딩 검사 통과. 독립 실기기·스크린리더와 운영 DB 적용은 미검증이다. 새 RPC의 최종 응답은 `{items, next_cursor}`이고 항목은 변경 행·`change_type`·`previous`다.
