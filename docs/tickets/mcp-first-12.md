# [MCP-first] 점검 범위·사건·검토 질문·판단 이력 데이터 계약

## 단순화 적용 기준 — ADR-0004 (2026-09-21)

[ADR-0004](https://github.com/kimyongin/fin/blob/master/docs/adr/0004-domain-storage-and-minimal-mutation-contract.md)가 아래 이전 설계의 물리 구조 요구보다 우선한다. 해당 ADR은 현재 작업 트리에서 작성됐으며 원격 링크는 푸시 후 유효하다. 도메인 테이블+공통 변경 규약, 필요한 대상만 version 검사, 현재값+중요 변경 이력/당시 snapshot을 사용한다. 모든 모델에 head/revision 쌍을 만들지 않는다.

- 문맥은 서버 임시 context_id, 결과는 단일 briefing으로 저장한다. signed receipt·전역 가격/메타데이터 버전 차단은 도입하지 않는다. TTL/정리/생성 제한과 소유권은 테스트한다.
- 사건 엔진/일반 조사구간 집합 엔진/보유 구간 자동 복원/가이드 전용 도구는 후순위다. 아래 사건·이력 인수 조건은 첫 버전에서 근거 정정 참조, 판단/task 연결, 중요 변경 이력과 snapshot으로 충족한다. 보안·원가·보정 보호·원자성은 줄이지 않는다.
- 구현되지 않은 과거 진행 기록은 역사다. 신규 완료 게이트는 갱신된 contracts 문서와 이 절을 따른다. 기능 제공/자동 테스트 통과/티켓 완료를 뜻하지 않는다.

## 계약·구현 대조 완료 (2026-09-21)

- 에이전트 전달 계약을 `docs/design/contracts/agent/`에 추가했다: 공통 규칙, 도구 설명, W01~W08 작업 가이드와 S/R 시나리오 연결. 현재 로컬 OAuth의 35개 도구는 공통 schema/handler와 연결했고 observed-local/released를 구분한다.
- 지속 관리: #33 공통 정의에서 tools/list/dispatch·스키마를 연결하고, 각 기능 변경 시 시나리오·설명·스키마·테스트를 함께 갱신한다. 설명은 에이전트 안내이며 소유권/버전/원자성 강제는 서버 책임이다.

- 후속 산출물: `docs/design/contracts/lifecycle-model-api.md`, `scenario-api-model-matrix.md`(동일 디렉터리). 24개 사용자 시나리오별 API·변경 모델·불변 조건·담당을 대조하고, 원칙→판단→질문→대체 판단→부분 체결→취소→보정의 연결 사례를 작성했다.
- 누락 보완: 판단/보유 이유+후속 질문 원자 저장, 질문 CAS 충돌 시 batch rollback, 취소 전용 preview, 실행 control_state/progress 분리, 브리핑의 당시 task history 고정, 문맥 대상 manifest 대비 누락 조사 처리. 새 API 명칭은 서비스 계약안이며 모두 MCP 도구로 노출한다는 뜻이 아니다.
- 아래 상세 계약을 migration/RPC/MCP/UI와 다시 대조했다. 로컬 DB 223개 assertion, 단위 53개, 앱 E2E 22개가 통과했다. 운영 배포·legacy 행 이관·5일 파일럿은 구현 티켓과 #39의 외부 게이트다.

- 로컬 산출물: `docs/design/schema-audit-20260921.md`, `docs/design/contracts/README.md`, `daily-review-model.md`, `daily-review-api.md`(마지막 두 파일도 contracts 디렉터리). 현재 작업 트리 작성본이며 커밋/푸시 여부는 Git으로 확인한다.
- 원격 public 스키마 읽기 전용 확인 완료. 기존 transactions 재계산은 절대 보정 정책과 다르고, daily_reports/rebalance_suggestions는 새 구조화 점검 원본으로 사용하지 않고 역사 자료를 보존한다. 로컬 DB에는 해당 legacy 테이블이 없어 원격과 동일한 테스트 환경이 아니다.
- 문맥 조회 → 분석 저장 → 재조회, 질문/판단 전이, 보유 이유, 개인 기준, 체결·보정·취소, 공유 DTO까지 관계와 불변 조건을 구현했다.
- 운영 배포는 하지 않았다. 이 티켓은 로컬 관계 계약으로 완료하며, 운영 증거가 필요한 항목은 각 구현 티켓과 #39에서 닫는다.

## 구현 인계 확정 사항 (2026-09-20)

- 필독: [ADR-0002](https://github.com/kimyongin/fin/blob/master/docs/adr/0002-cost-basis-reconciliation-and-sharing.md), [ADR-0003](https://github.com/kimyongin/fin/blob/master/docs/adr/0003-extensible-feature-sharing.md), [구현 계약 초안](https://github.com/kimyongin/fin/blob/master/docs/design/implementation-contract-draft.md).
- 공유 구조는 ADR-0003을 따른다. 기능별 키·필드와 관계 투영 계약은 여기서 확정하고 실제 권한 기반은 #43에서 구현한다. #35는 이를 소비한다. 친구별 상속/override/문서별 ACL을 설계 범위에 추가하지 않는다. 기존 거래/리포트 DDL 후속 확인 결과는 위 2026-09-21 진행 기록을 따른다.
- 문서화는 구현/배포/보안 검증 완료가 아니다. 미검증 DDL·정밀도·상태 전이는 해당 티켓의 첫 작업으로 남기며 완료 체크를 앞당기지 않는다.

## 기존 모델과 새 책임의 대응표
- 종목 태그 / 여러 태그를 묶는 전략 버킷 / 모드별 목표 / 원칙 버전을 별도 개념으로 명시한다.
- 기존 규칙 기반 배분 계산, 저장된 뉴스 사실/해석, 감사 활동, 신규 판단·할 일을 서로 다른 의미로 매핑한다.
- 기존 데이터 재사용/확장/이관/유지 항목과 권한 영향을 모델별로 기록한다. 기존 뉴스 의견·감사 로그를 확정 결정으로 자동 승격하지 않는다.
- 판단 당시 원칙·계산 입력·출처 버전을 참조해 후속 편집으로 과거 근거가 바뀌지 않게 한다.
- #35-A가 스키마 기반을 만든 뒤 #34 읽기와 #35-B 저장이 통합된다. 원칙 버전은 #43, 잔고 기준점은 #37/#38이 담당한다.
- [x] 기존 공유 항목과 새 비공개 항목의 노출 행렬, 과거 데이터 원문 보존과 마이그레이션 검증 기준을 작성한다.

## PRD·ADR·Ticket 비유를 적용한 데이터 계약
- 투자 원칙·운용 계획(#43)은 버전 있는 기준, 판단 기록은 ADR 역할, 조사·점검/실행할 일은 Ticket 역할로 정의한다. 실제 매매 원장은 독립 모델이다.
- 판단 필드: 상황/질문, 검토 선택지, 근거와 출처, 적용 원칙·보유 이유 버전, 제안/사용자 채택 결정/대체됨 상태, 선택 이유, 영향·불확실성, 재검토 조건, 이전 판단 관계.
- 기존 검토 질문은 조사·점검할 일의 질문/답/근거로 통합한다. 중복 질문 큐를 만들지 않는다.
- 할 일 공통 필드: ID, 유형, 대상, 목적, 관련 판단/보유 이유, 예정일 또는 시작 조건, 작성 주체와 상태 이력.
- 조사·점검 상태는 기존 질문 전이 계약을 따른다. 실행은 예정/부분 체결/완료/보류/취소를 구분하고 계획 단위별 완료 조건을 정의한다.
- 결정 없이 조사할 일을 만들 수 있고, 유지/보류 결정은 실행할 일 없이 유효하다. 브리핑 생성은 새 ADR 생성과 동의어가 아니다.
- 하나의 실행할 일에 여러 체결이 연결될 수 있다. 첫 버전은 각 체결을 최대 하나의 실행할 일에 연결하며 계획/체결 단위가 맞을 때만 진행도를 계산한다.
- 매매 원장 참조와 체결 ID를 통해 실제 실행을 입증한다. 계획 상태 변경만으로 체결을 생성하거나 잔고를 변경하지 않는다.
- 실행할 일 취소와 실제 매매 기록 취소를 구분한다. 체결 정정 시 진행도 갱신 규칙은 #37/#38과 공유한다.
- [x] “원칙 → 유지 결정 → 실적 조사할 일 → 새 근거 → 대체 판단 → 10주 계획 → 6주/4주 체결”의 관계·상태 예시를 작성한다.
- [x] 계획 없는 즉시 매매, 채택되지 않은 모델 제안, 부분 체결 후 계획 취소 사례도 포함한다.

## 목적과 선행 작업
- #32 제품 계약을 바탕으로 #34 일일 문맥, #35 저장, #36 화면이 공유할 데이터 계약을 확정한다.
- 이 티켓은 설계 산출물과 기존 모델 대응표를 담당한다. 실제 마이그레이션·RPC 구현은 #35, 읽기는 #34에서 수행한다. 이중 구현이나 순환 의존성을 만들지 않는다.
- 사용자가 매일 분석을 요청한다. 예약/자동 생성은 현재 범위에서 제외한다.

## 구조
- 점검 실행: briefing_id, 요청/분석 시각, 대상 기간, 사용자 시간대, 사용한 잔고·전략·보유 이유 버전, 이전 실행 참조, 진행/부분 완료/완료/실패 상태.
- 조사 범위: 종목 또는 질문별 조사 기간·확인 출처·마지막 확인 시각·충분/일부/미확인 상태와 사유. “충분”은 선언한 조사 범위에 대한 상태이며 전체 웹의 완전성을 보증하지 않는다.
- 사건과 근거: 사건 ID와 종목, 발생/발표/발견 시각(불명 허용), 출처별 URL/제목/발행·확인 시각, 사실 요약, 정정/대체 관계. 같은 사건에 여러 출처를 연결한다.
- 검토 질문: 안정적인 ID, 무엇을/왜 확인하는지, 관련 종목·보유 이유 버전·근거, 확인 조건/선택 날짜, 상태와 후속 질문 관계.
- 판단: 분석 의견/사용자 결정 구분, 당시 근거·적용 원칙 버전, 이전 판단 참조와 변경 이유.
- 브리핑은 읽기용 요약이고 위 레코드를 참조한다. 본문을 다시 파싱해야 관계를 복원하는 구조에 의존하지 않는다.

## 상태와 연결 규칙
- 질문은 열린 상태/자료 대기/해결/사용자 보류/사용자 종료를 구분하고 전이 조건을 문서화한다. 새 자료 또는 정정으로 재개할 수 있다.
- 모델이 근거를 붙여 질문 해결을 제안/기록하는 것과 사용자의 매매 결정·할 일 완료를 구분한다. 모델 업데이트의 작성 주체와 근거를 보존하며 사용자의 보류/종료를 묵시적으로 취소하지 않는다.
- 질문 해결은 답과 출처가 필요하다. 관련 기사 하나를 찾았다는 사실만으로 해결하지 않는다.
- 조사 이후 중요한 변화 + 이전 미확인 범위 + 열린 질문을 다음 실행의 입력으로 삼는다.
- 마지막 브리핑 저장일을 모든 종목의 조사 완료 시점으로 사용하지 않는다. 늦게 공개된 자료를 찾을 수 있도록 겹치는 기간 재조회와 중복 판별 규칙을 둔다.
- 같은 URL과 같은 사건은 다르다. URL 정규화/기사 중복과 사건 연결을 구분한다. 애매한 사건은 자동 병합하지 않고 추후 연결·분리가 가능하게 한다.
- 기사 정정/철회와 사용자의 정정은 원본을 덮어쓰지 않고 어떤 과거 판단에 영향을 주는지 추적한다.
- 우선순위와 의미 해석은 ChatGPT가 담당하고 서버는 소유권·ID 참조·허용 상태 전이·버전·중복을 검증한다.

## 실패와 동시 실행
- 초안 저장으로 조사 완료 범위를 전진시키지 않는다. 저장된 근거/범위와 연결해 확정할 때만 반영한다.
- 일부 조사 성공은 해당 범위만 확정할 수 있고 실패 범위는 다음 점검에 남긴다.
- 멀티턴 저장 중 실패해도 briefing_id와 idempotency로 이어갈 수 있게 한다. 브리핑에서 연결되지 않은 근거를 유실하거나 이중 저장하지 않는다.
- 웹/모바일 또는 두 대화의 동시 실행은 각각 보존한다. 늦게 도착한 과거 실행이 최신 질문·판단·조사 범위를 덮어쓰지 않도록 버전 충돌 처리를 정의한다.
- 열람 시각, 분석 생성, 조사 범위, 실제 잔고 확인(#42)은 독립 상태이다.
