# 저장 확인에서 변경 메모·활동 태그 함께 지정

2026-09-27 · 로컬 구현 및 주요 화면·계약 검증 완료 · 운영 배포 전

GitHub: https://github.com/kimyongin/fin/issues/159

## 목적

자산·배분·원칙을 변경한 뒤 활동 화면으로 이동해 기록을 찾아 태그를 붙이는 재작업을 없앤다. 편집 화면에서는 원본 값을 수정하고, 저장을 누른 시점에 이번 변경의 메모와 활동 태그를 선택한다. 최종 저장 한 번으로 원본 변경·활동 기록·태그 연결이 함께 반영된다.

## 웹 사용 흐름

1. 원본 필드를 수정한 뒤 `저장`을 누른다. 필드 검증에 실패하거나 원본 변경이 없으면 확인창을 열지 않는다.
2. 공통 확인 표현으로 `변경 내용 저장` 창을 연다. 원본 변경의 짧은 요약 → `변경 메모 (선택)` → `활동 태그 (선택)` → `취소 / 저장` 순서다. 메모는 최대 1,000자이며 입력을 강제하지 않는다.
3. 기존 활동 태그를 검색 없는 다중 선택 칩으로 보여준다. 선택 개수·체크 표시로 레이아웃을 바꾸지 않는다. 태그 생성·이름 변경·삭제는 이 창에서 제공하지 않는다.
4. 최종 저장 전까지 서버 쓰기는 없다. 취소/X/Escape는 원본 편집으로 돌아가며 원본 초안·메모·태그 선택·스크롤을 보존한다. 동일 초안으로 다시 저장을 누르면 메모·태그가 유지된다.
5. 성공하면 원본의 기존 저장 후 동선을 유지하고 이번 변경의 메모·태그 초안을 비운다. 다음 저장이나 다른 대상에 자동 재사용하지 않는다. 실패하면 전부 보존한다.
6. 자산의 금융값 요약/사유 확인을 이 창으로 교체한다. 새 확인창을 연속해서 추가하지 않는다. 배분 초기화 역시 기존 위험 확인과 합쳐 `초기화` 버튼 한 번으로 확정한다.

이 확인창은 원본이 페이지에 있든 모달에 있든 같은 역할이다. 원본 모달 위에 열릴 때만 계층 2이며 배경은 inert, 최상위 하나만 활성화한다. 휴대폰에서도 내용 크기의 중앙 확인창이며 긴 태그 목록은 본문 안에서 스크롤한다. 새로운 전체 화면 편집 모달이나 3차 모달은 없다.

태그 목록 로딩/실패/빈 목록을 구분한다. 실패 시 재시도와 `태그 없이 저장` 선택을 제공하며, 선택한 태그를 오류 때문에 조용히 버리고 저장하지 않는다. 저장 중에는 중복 실행·닫기·선택 변경을 막는다.

## 기록과 저장 계약

- 기존 `activity_events`, `activity_tags`, `activity_event_tags`를 재사용한다. 자산 대표 태그(`tags`)는 별도 의미이며 활동 태그로 자동 복사하지 않는다. 새 분류/테이블/범용 명령 엔진은 만들지 않는다.
- 각 목적별 저장 API에 선택적인 `activity_tag_ids`를 추가한다. 웹 RPC에서는 `input_activity_tag_ids`를 사용한다. 기존 자산 사유·원칙 변경 메모 필드는 의미를 유지하고 배분에 선택 메모를 추가한다. 태그를 생략하거나 `[]`로 보내면 새 기록에 태그를 붙이지 않는다.
- 한 저장으로 생성한 변경 기록에 선택한 태그를 연결한다. 자산 여러 계좌 수정과 배분 여러 목표 수정은 각각 기존 단일 변경 기록을 사용한다. 이미 존재하는 기록을 수정하거나 별도 수동 활동을 추가 생성하지 않는다.
- 서버에서 소유자·태그 유효성·원본 충돌을 검사하고 원본 변경+활동 생성+태그 연결을 같은 트랜잭션으로 처리한다. 잘못된/삭제된/타인 태그면 부분 저장 없이 실패한다. 기존 공유 읽기 전용 권한을 유지한다.
- 태그·메모만 지정했거나 원본 변경이 없는 재요청은 새 기록을 생성하지 않는다. 사후 기록 편집은 기존 활동 상세를 사용한다. 원칙의 기존 본문/변경 메모 동일 여부에 대한 no-op 계약은 유지한다.
- 현재 자산 저장의 멱등성 키/receipt에 메모·태그까지 포함한다. 배분·원칙은 현재 동일값 재요청 처리와 충돌 검사를 재사용한다. 응답 유실 재시도에서도 최초 기록·태그만 남기고, 재요청으로 그 기록의 태그를 교체하지 않는다. 구현 첫 슬라이스에서 이 보장을 검증하고 필요한 최소 변경만 한다.
- 반환 결과에는 생성된 기록 ID(기록이 없는 no-op은 null)를 제공해 웹/MCP 재조회에 사용한다. 기존 반환 필드를 유지하며 같은 저장을 찾기 위해 최신 활동을 추측해서 조회하지 않는다.

## 원칙 기록의 의미

- 실제 원칙 변경은 기존 방식대로 새 원칙 행을 추가한다. 같은 트랜잭션에서 제목 `원칙 변경`(최초 작성은 `원칙 작성`)의 활동 한 건을 만든다. 활동 본문에는 변경 메모를 사용하고 비어 있으면 짧은 기본 설명을 쓴다. 원칙 전문은 복제하지 않는다.
- 변경 메모는 한 번 입력받아 원칙 이력과 최초 활동 요약에 반영한다. 원칙 본문·변경 메모의 정본은 원칙 행이다. 활동 내용은 그때 남긴 기록이며 이후 두 화면의 편집을 자동 동기화하지 않는다.
- 기존 `target_table`/`target_id`로 원칙 행을 참조한다. 원칙 행이 나중에 삭제되어도 활동은 남고, 연결 화면에서 원문이 없음을 처리한다. 활동 삭제는 원칙 행을 삭제하지 않는다. 별도 관계 테이블은 추가하지 않는다.
- 과거 원칙 이력의 잘못된 내용 정정/삭제는 이번 새 원칙 저장 흐름과 구별한다. 기존 정정 폼의 변경 메모는 해당 과거 행의 속성이므로 그대로 편집한다. 정정/삭제마다 새 활동을 만드는 범위로 확대하지 않는다.

## MCP·가이드

- 자산 상세 저장, 배분 저장/초기화, 원칙 저장의 HTTP/OAuth MCP 계약을 함께 확장한다. 에이전트가 기존 태그 조회 → 목적별 저장에 태그·메모 포함 → 기록 재조회까지 한 흐름으로 수행할 수 있어야 한다.
- 웹의 확인창을 채팅에서 기계적으로 재현하거나 태그 입력을 의무 질문으로 만들지 않는다. 사용자가 지정한 태그/메모는 저장에 포함하고, 지정하지 않으면 생략한다. 태그 선택을 위해 별도 활동 쓰기 호출을 요구하지 않는다.
- 도구 설명·입출력 스키마·adapter·workflow guide·review manifest·HTTP/OAuth 계약표를 함께 갱신한다. 시세·환율 직접 쓰기 금지와 기존 저장 승인 범위는 유지한다.

## 구현 순서와 범위

1. **자산 수직 슬라이스:** 기존 확인 표현·태그 picker를 재사용하고 자산 웹/HTTP/MCP 저장·실패/재시도·활동 검색까지 검증한다. 공유 기반의 완료 기준은 이 실제 소비 흐름이다.
2. **배분 수직 슬라이스:** 목표 저장·초기화에 동일 입력과 원자 저장을 연결한다. 현재 비중/차트와 목표 계산에는 활동 태그가 영향을 주지 않는다.
3. **원칙 수직 슬라이스:** 확인 단계로 변경 메모를 이동하고 원칙 이력+활동+태그의 저장 및 양쪽 조회를 검증한다.
4. **누락 경로 점검:** 계좌/종목 추가·편집, 보유 삭제, 표 편집, 매매·보정 MCP 등 자동 활동 생성 경로의 현황과 같은 불편을 조사해 적용/별도 후속/제외 이유를 기록한다. 본 티켓의 필수 구현 범위는 위 세 흐름이며 발견된 나머지를 완료로 보고하지 않는다. 설정·프로필·가격 갱신 등에 일괄 확인창을 도입하지 않는다.

활동 기록 자체의 추가/편집은 기존 본문 안의 태그 선택과 단일 저장을 유지한다. 활동을 저장하면서 다시 활동 기록을 생성하는 재귀 흐름은 만들지 않는다. 할 일 완료의 기존 태그 상속도 유지한다.

## 수용·검증 조건

- [ ] 자산/배분/원칙에서 저장할 때 메모·태그를 선택하고 활동 화면에서 해당 태그로 즉시 검색된다. 태그 생략도 성공한다.
- [ ] 원본 변경 한 번당 기존 단위의 활동 한 건만 남고 원칙 이력도 한 행만 추가된다. no-op·중복 클릭·응답 유실 재시도 시 중복/태그 덮어쓰기가 없다.
- [ ] 취소→다시 저장, 실패→재시도, 원본 편집→다른 대상 전환에서 초안 보존/폐기가 명확하다. 성공 후 다음 저장에는 메모·태그가 비어 있다.
- [ ] 타인/삭제된 태그, 원본 충돌, 태그 조회 실패를 검증한다. 저장 실패 시 원본/활동/태그 중 일부만 반영되지 않는다.
- [ ] 웹 저장→MCP 조회, MCP 저장→웹 태그 검색을 세 도메인 모두 확인한다. 기존 태그 없는 호출의 호환성과 공유 읽기 전용을 확인한다.
- [ ] 360/390/768/1024/1440px, 0/1/30개 태그·긴 이름, 키보드·포커스 복귀·모바일 키보드·스크롤을 점검한다. 실제 검증하지 못한 항목을 명시한다.
- [ ] 관련 DB/RPC·MCP 테스트, 빌드, 인코딩, workflow guide 검사를 통과한다. 일반 로컬·격리 테스트·운영 DB 대상을 구별한다.
- [ ] 모달/태그 가이드와 티켓에 적용/검증 범위를 기록하고 남은 자동 기록 경로 목록을 남긴다. 구현·커밋·배포는 각각 기록한다.

- `npm run check:edge`는 이 호스트에 `deno` 실행 파일이 없어 수행하지 못했다. 실제 로컬 Edge 함수 경유 MCP 계약 테스트는 통과했다. `.e2e` 격리 인스턴스에는 보존해야 할 기존 로컬 변경이 있어 reset 기반 `npm run test:e2e`는 실행하지 않았다.
- 별도 임시 로컬 계정으로 `e2e/domain-save-context.spec.js`를 직접 실행했다(격리 인스턴스 reset 없이 일반 로컬 DB의 추가 마이그레이션 사용). 자산·배분·원칙의 저장 확인을 실제 Chromium에서 거쳐 HTTP 기록 상세의 태그를 확인했다. 원칙 확인창에서 취소→재진입 시 메모·태그가 유지됨을 확인했고, 360/390/768/1024/1440px에서 확인창 노출·가로 넘침 없음도 확인했다. 테스트 계정과 종속 데이터는 삭제했다.
- 0/30개 활동 태그, 긴 태그 이름, 모바일 실기기 키보드·스크린리더, 모든 초점 복귀·스크롤 상태는 아직 확인하지 않았다. 따라서 전체 시각적 완료와 운영 배포는 주장하지 않는다.
- 범위 밖 자동 기록 경로: 계좌 저장/삭제, 종목 등록/삭제, 보유 삭제, 자산 대표 태그 관리, 표 편집, 거래·잔고 보정, 가격 갱신 등. 이번 요청의 세 저장 경로와 달리 각각 다른 승인/일괄 흐름이므로 태그 확인창을 무조건 확대하지 않았다. 실제 사용 중 필요성이 확인되면 목적별 후속 티켓으로 다룬다.

다음 단계는 남은 극단 상태·실기기 확인을 하고, 별도 커밋·푸시·배포 단계를 결정하는 것이다. 기존 사용자 설정 파일과 무관한 작업 트리 변경은 건드리지 않았다.
