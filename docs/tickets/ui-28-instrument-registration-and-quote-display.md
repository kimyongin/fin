# [자산 UX] 종목 등록과 보유 입력 분리·시세 읽기 전용 표시

2026-09-26 · Astra 설계 후 Sol 로컬 구현. 운영 배포와 커밋은 별도 확인 대상.

GitHub: https://github.com/kimyongin/fin/issues/139

2026-09-26 승인된 후속 표현은 [모달 필드 통일](./ui-29-modal-field-consistency.md)이다. 아래 현재가/기준일의 일반 텍스트/입력칸 금지 문장은 동일한 읽기 전용 필드 표시로 대체한다. 시세 수정 금지·payload 제거·등록/보유 분리 계약과 이 티켓의 구현 검증 이력은 유지한다.

## 목적

사용자는 먼저 관리할 종목을 등록하고, 자산 목록에서 그 종목을 선택해 계좌별 보유량을 입력한다. 종목 등록에 계좌나 보유량을 요구하지 않는다. 시세는 가격 갱신으로 가져오고, 사용자는 자신의 수량·평균가를 편집한다.

이 티켓은 #124의 상세 수동 가격 입력, #113/#138의 상단 `보유 추가`와 보유 행이 있는 종목만 보여주는 요구를 대체한다. #134의 종목/보유/평가 3열, 태그 필터, 공통 모달·확인 규칙은 유지한다.

## 현재 구현에서 확인한 차이

- `AssetsPage.scopedRows`는 전체 계좌에서도 `accountCount > 0`인 종목만 노출한다. 반면 `usePortfolioDerivedData.instrumentRows`에는 이미 보유 없는 종목과 0 합계가 있다. 기존 파생값을 재사용한다.
- 상단 `보유 추가`는 `HoldingEditorModal`을 열어 계좌·티커·수량·평균가를 함께 받는다. 기존 티커 추천 목록도 이 폼에 있다.
- `InstrumentEditorModal`/`instrumentActions`에 종목 등록이 이미 있지만, 계좌 연결과 등록 후 보유 폼 자동 진입, 수동 가격 입력이 섞여 있다.
- `lookup-ticker`는 이름 조회와 동시에 `app_save_instrument`로 종목·가격을 저장한다. 새 등록 흐름에서는 조회 취소가 실제 등록으로 남아서는 안 된다.
- `app_get_price_sync_targets`는 보유가 있는 시세형 종목과 환율만 대상으로 한다. 0보유 종목도 가격을 갱신할 수 있도록 변경해야 한다.
- `AssetDetailModal`은 헤더 아래 티커/시세 요약과 본문의 편집 가능한 가격을 중복 표시하며, 일반 저장에 `manual_price`/`manual_price_date`를 실을 수 있다.

## 사용자 흐름

1. 자산 상단 햄버거의 `종목 추가`를 연다. 계좌가 하나도 없어도 가능하다.
2. 시세형은 일반 텍스트 입력칸에 티커를 입력하고 `조회`한다. 이름·통화를 확인하고 필요한 종목명·태그·메모를 입력한 뒤 `등록`한다. 기존 티커 선택 목록은 없다.
3. 등록 성공 후 모달을 닫고 전체 계좌의 자산 목록에 새 종목을 보여준다. 계좌·검색·태그 조건을 전체로 초기화해 새 종목이 숨지 않게 하고 해당 행으로 초점/스크롤을 이동한다. 취소/실패 때는 기존 목록 조건을 유지한다.
4. 종목은 보유 0으로 표시된다. 선택하면 기존 자산 상세에서 `계좌별 보유`에 계좌·수량·평균가를 입력하고 저장한다. 보유가 없을 때 버튼은 `보유 추가`, 있을 때는 `다른 계좌에 보유 추가`다. 새 편집 모달을 쌓지 않는다.
5. 계좌가 없으면 상세 본문에 계좌 추가가 필요함을 알린다. 상세 위에 계좌 편집 모달을 쌓지 않고, 상세를 닫아 자산 메뉴의 `계좌 추가`를 사용한다. 미저장 초안은 공통 닫기 규칙으로 보호한다.
6. `가격 갱신`을 누르면 보유 여부와 관계없이 등록된 시세형 종목의 현재가·실제 기준일을 갱신한다.

## 등록과 목록 계약

- 상단 메뉴/빈 화면의 등록 진입은 `종목 추가`로 통일한다. 상단 `보유 추가`의 이름만 바꾸고 기존 보유 폼을 열면 미완료다. 상단 카드 제목은 0보유 종목도 포함하는 `자산`으로 정리한다.
- 등록 모달에서 계좌·수량·평균가·수동 현재가·수동 가격일 입력과 등록 후 보유 폼 자동 열기를 제거한다. 유형/통화/이름/태그/메모는 기존 종목 모델을 재사용한다. 평가형·현금성 등록과 기존 식별자 생성 규칙도 지원한다.
- 조회는 초안 채우기이며 종목·보유·가격·활동을 저장하지 않는다. 조회만 하고 닫아도 DB는 그대로다. 시세형은 조회한 티커와 등록할 티커가 일치해야 하며, 조회 실패는 같은 폼에서 재시도한다. 입력 변경 후 이전 조회 결과로 저장하지 않는다.
- 동일 사용자·동일 정규화 티커는 중복 등록하지 않는다. 기존 종목의 이름/태그/메모를 등록 요청으로 덮어쓰지 않고 이미 등록됨을 알린다. 기존 상세로 이동할 수 있게 하되 모달을 겹치지 않는다. 동시 등록은 기존 고유 제약과 등록 의미를 검증해 처리한다.
- 종목만 저장하고 0 수량의 가짜 `holdings` 행을 만들지 않는다. 등록 취소 때 이미 저장한 종목을 삭제하는 보상 절차도 만들지 않는다.
- 전체 계좌 목록에는 등록된 비환율 종목을 모두 표시한다. 특정 계좌 필터에서는 그 계좌의 실제 보유 행만 표시한다. 계좌에 없는 종목을 추가하려면 전체 계좌에서 선택한다.
- 0보유 시세형은 수량 0·평가액 0, 평균가와 수익률은 `—`로 표시한다. 시세가 없으면 현재가는 `—`다. 평가형/현금성도 보유 없음이 분명해야 하며 수량을 억지로 만들지 않는다.
- 0보유 종목의 시세 없음은 보유 자산의 `평가 불가` 건수에 넣지 않는다. 실제 보유가 있을 때 시세/환율 누락을 0원으로 바꾸는 것은 금지한다. 전체 평가액·배분 분모·보유 계좌 수는 실제 보유로 계산한다.
- 마지막 보유를 삭제해도 종목은 목록에 0보유로 남는다. 필요 없어진 종목은 상세에서 기존 종목 삭제 API로 제거할 수 있게 한다. 실제 보유 행이 있으면 종목 삭제를 허용하지 않는다. 삭제 영향은 기존 공통 2차 확인에서 안내한다.
- 검색·태그 없음/태그 OR 필터를 0보유 종목에도 적용한다. 공유 목록은 기존 자산 권한/소유자 범위 안에서만 구성한다.

## 상세 표시와 시세 계약

본문 순서: 종목명·티커 → 통화/유형 → 현재가·가격 기준일 → 태그 → 메모 → 계좌별 보유.

- 헤더는 종목명과 닫기만 표시한다. 헤더 바로 아래 작은 티커/가격/날짜 요약을 제거하고 티커는 본문에 읽기 전용으로 한 번 표시한다.
- 시세형의 현재가·가격 기준일은 읽기 텍스트로 표시한다. disabled 입력칸을 만들지 않는다. 작은 화면에서도 접지 않으며 가격·날짜는 태그/메모보다 위에 둔다.
- 짧은 안내는 `시세는 자산 메뉴의 가격 갱신으로 갱신합니다.`로 한다. 시세 없음에 0이나 오늘 날짜를 넣지 않는다. 공유 상세에서도 허용된 티커/시세를 읽을 수 있다.
- 상세 초안과 저장 payload에서 수동 가격을 제거한다. 메모·보유값 저장이 가격/기준일을 다시 저장하지 않게 한다. 상세 RPC의 수동 가격 분기도 퇴역시켜 옛 입력을 조용히 적용하지 않는다.
- 새 종목 등록은 시세를 입력받거나 조회값을 가격 테이블에 저장하지 않는다. 등록 직후 시세가 없을 수 있으며 기존 `가격 갱신`으로 채운다. 별도 자동 갱신 스케줄·대기 상태·큐는 만들지 않는다.
- 가격 갱신 대상은 현재 사용자의 등록된 시세형 종목과 필요한 환율이다. 0보유 포함, 평가형/현금성 제외, 타 사용자 격리·출처·실제 거래 기준일·부분 실패 안내는 유지한다. 실패 시 기존 시세를 지우거나 기준일을 오늘로 덮어쓰지 않는다.
- 수량·평균가·평가형 금액·현금 잔액은 계속 직접 편집한다. 시장 현재가 읽기 전용을 개인 보유값까지 확대하지 않는다.

## 구현 범위와 경계

새 테이블/등록 상태/종목과 보유의 추가 관계 모델은 필요 없다. `instruments`와 `holdings`를 재사용한다. 기존 가격 이력과 보유 데이터는 보존한다.

- 웹: `AssetsPage`, `AssetDetailModal`, `EditorModals`, `PortfolioEditorModals`, portfolio actions/hooks/helpers 및 등록 후 필터/초점 연결을 수정한다. 사용자 진입이 사라진 독립 보유 추가 폼은 실제 호출자를 대조하고 정리한다. 표 편집의 대량 보유 입력은 유지한다.
- 서버: `lookup-ticker`의 등록창 조회를 읽기 전용으로 만들고 관련 호출자를 함께 바꾼다. 기존 목적별 종목 저장/상세 저장/가격 갱신 API를 우선 재사용한다. 새 등록이 기존 종목의 upsert 수정으로 처리되지 않도록 생성 시 중복 계약을 확인한다.
- 등록 조회의 read-only 전환은 이 endpoint를 쓰는 웹/MCP 호출자를 함께 검토한다. MCP가 조회를 등록으로 설명하거나 저장 결과로 간주하는 경우 schema/description/handler/가이드를 갱신한다.
- MCP도 종목 등록과 계좌별 보유 저장의 의미를 구분하고 0보유 조회/시세 갱신 대상을 일치시킨다. 에이전트의 명시적 보유 입력·매매/보정 도구를 웹 폼 폐기 때문에 제거하지 않는다.
- 이번 티켓의 수동 시세 제거 대상은 자산 등록·상세의 사용자 편집 및 그 저장 호출이다. 가격 수집용 하위 저장 API와 별도 MCP 시세 입력 도구의 전면 폐기는 범위 밖이다. 남은 소비자는 구현 기록에 적고, 종목/보유 등록 설명에서 수동 시세 입력을 권장하지 않는다.
- 공유 권한·소유권·보유 원자 저장/충돌 검사·금융 멱등성은 유지한다. 운영 migration/Edge/웹 배포는 별도 단계다.

## 수직 슬라이스와 완료 기준

1. **종목 등록 → 0보유 목록 → 상세 보유 저장**: 기존 종목 등록을 간소화하고 조회의 숨은 쓰기·중복 생성 문제를 해결한 뒤 전체 흐름을 실제 API로 검증한다.
2. **읽기 전용 시세 → 0보유 가격 갱신 → 재조회**: 상세 가격 payload를 제거하고 갱신 대상·MCP 설명을 연결해 검증한다. 각 슬라이스를 검증하고 별도로 커밋한다.

- [x] 계좌 없는 사용자도 종목만 등록할 수 있고 보유 행은 생기지 않는다. 조회 취소/실패도 저장하지 않는다. DB 생성 테스트와 웹 조회 전 상태 확인.
- [x] 등록 성공 후 새 종목이 필터에 가려지지 않으며 새로고침 후에도 0보유로 보인다. 웹 등록 E2E와 DB 저장 확인.
- [x] 기존 티커/동시 등록에서 중복이나 기존 메모/태그 덮어쓰기가 없다. 사용자·티커 잠금과 DB 중복·메모 보존 테스트.
- [x] 0보유 → 첫 계좌 보유 → 두 계좌 보유 → 마지막 보유 삭제 → 종목 삭제 흐름이 자연스럽고 값·활동이 일관된다. 신규 흐름과 기존 다계좌 회귀를 함께 검증.
- [x] 0보유와 실제 보유의 시세 누락을 구분하고 검색/태그/계좌 필터·평가액·배분을 검증한다. 파생값은 기존 실제 보유 기반 집계를 유지.
- [x] 현재가/기준일은 태그·메모 위의 읽기 정보이며 헤더 중복은 없고 본문 티커는 남는다. 상세 저장 요청에 가격이 없고 서버에서도 옛 수동 가격 입력을 거절한다.
- [ ] 0보유/실제 보유 시세형의 가격 갱신 성공·부분 실패·재조회와 타 사용자/공유 읽기 경계를 검증한다. DB 대상/격리와 웹의 모의 성공·실패는 검증. 실제 Yahoo 응답을 이용한 0보유 갱신과 모바일 실기기 검증은 미실시.
- [x] 평가형/현금성·계좌 추가·표 편집·기존 MCP 보유 입력 회귀가 없다. DB·MCP 계약·웹 E2E 범위에서 확인.
- [ ] 관련 DB/API/MCP 회귀와 웹 E2E, 360/390/768/1024/1440px의 등록·상세·긴값·빈값·초점·저장/닫기 확인, 인코딩 검사를 기록한다. 실제 모바일 실기기와 운영 배포는 미실시.
- [x] START-HERE/기존 티켓 대체 안내·도구 설명/가이드·schema overview의 변경 사실을 갱신한다. 로컬 완료와 운영 배포를 구분한다.

## 로컬 구현 메모

- 신규 테이블·가짜 0보유 행 없음. `app_create_instrument`는 생성만 허용하며, 기존 저장 RPC는 호환용으로 유지한다.
- 웹 `lookup-ticker`는 인증 후 외부 조회만 수행한다. 구 token MCP의 별도 `lookup_ticker`는 저장까지 하는 호환 계약이라 읽기 전용으로 오인하지 않도록 에이전트 가이드에 기록했다. ChatGPT용 OAuth MCP에는 종목 등록 도구가 없으며 웹에서 등록한다.
