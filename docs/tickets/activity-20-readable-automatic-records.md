# [활동] 자동 기록의 제목·본문 완성 및 웹·MCP 조회 일관성

상태: 로컬 구현 및 검증 완료 · 운영 배포/실데이터 점검 전 · 2026-09-29
GitHub: https://github.com/kimyongin/fin/issues/168

## 목적과 확인한 문제

활동 하나만 읽어도 어떤 대상에 무엇을 했고 결과가 무엇인지 알 수 있게 한다. 목록·보기·편집·검색·에이전트가 같은 저장 내용을 읽어야 한다. 사용자가 자동 기록을 찾아 제목이나 설명을 다시 작성하게 하지 않는다.

2026-09-28 사용자 제보의 계정 범위에서 제목이 비어 있고 본문이 `기록`인 자동 기록 23건을 확인했다. 메모 수정 12건 외에 계좌 등록/수정, 종목 등록/삭제, 보유 삭제, 자산 태그 생성이 포함됐다. 별도로 목표 배분 변경도 제목이 없는 행이 있었다. 이 숫자는 조사 시점의 해당 계정 표본이며 전체 사용자 데이터 통계가 아니다. 공개 티켓에는 실제 메모·계좌 정보·사용자 ID를 복사하지 않는다.

- `app_update_entity_note` 등 일부 작성 경로는 제목·본문 없이 내부 변경 전후 값만 저장한다. `app_fill_activity_body`가 이를 `기록`으로 대체한다.
- 같은 행의 목록은 `포트폴리오`, 읽기는 `update_entity_note`, 편집은 빈 제목을 보여준다. 각 화면의 대체값이 다르고 실제 메모 내용은 숨겨진 변경 데이터에만 남는다.
- 일부 자산 상세 기록은 `종목 정보 변경`만 쓰거나 금융값을 JSON 문자열로 본문에 넣는다. 배분은 선택 메모만 저장해 메모 생략 시 무엇을 바꿨는지 알 수 없다.
- 종목 메모 수정 경로에는 시장 종목 티커 연결이 빠진다. 검색·임베딩은 제목·본문을 사용하므로 숨겨진 변경 데이터의 내용으로 검색할 수 없다.

## 기존 계약과의 관계

- [#122](https://github.com/kimyongin/fin/issues/122)의 읽을 수 있는 제목·본문 중심 활동 계약을 완성한다. 활동 종류·종류별 편집 제한·예약 태그를 복원하지 않는다.
- [#159](https://github.com/kimyongin/fin/issues/159)의 변경 메모·활동 태그 원자 저장과 원칙 전문 비복제는 유지한다. 해당 티켓의 확인창 적용 범위를 모든 저장으로 확대하지 않는다.
- [#166](https://github.com/kimyongin/fin/issues/166)의 시장 티커 참조와 [#167](https://github.com/kimyongin/fin/issues/167)의 명시적 읽기/편집·마크다운·모바일 조작을 사용한다. 본 티켓은 저장 내용과 소비 경로를 바로잡으며 목록의 새 진입 방식을 만들지 않는다.
- #161/#165의 기존 비동기 색인·검색 근거 계약을 소비한다. 검색 모델 교체, #162 연결 맥락 확장, #163 자동완성은 별도 범위다.
- 정본은 PRD, SIMPLICITY, ADR-0008/0009다. UI는 `docs/design/list-interaction-guidelines.md`, `modal-guidelines.md`, `typography-guidelines.md`, `timeline-guidelines.md`를 따른다.

## 저장할 내용의 최소 계약

1. 기존 `activity_events.title`, `body`, 시각·출처·태그·선택 참조를 사용한다. 새 이력 테이블·종류·범용 감사 엔진·LLM 요약 호출은 만들지 않는다. 반복되는 문자열 조립은 실제 소비 경로에 필요한 작은 서버 함수만 공유한다.
2. 자동 기록을 남기는 목적별 저장은 실제 변경 시점의 대상 이름·값으로 의미 있는 제목과 마크다운 본문을 함께 작성한다. 제목은 대상과 행동, 본문은 결과와 필요한 변경값을 담는다. 일반 UI의 JSON 원문·필드명·내부 명령 이름 표시를 제거한다.
3. 사용자의 선택 변경 메모는 사실 설명 뒤에 붙인다. 메모가 비어 있어도 실제 변경을 설명할 수 있어야 한다. 필수 변경 사유나 추가 확인 단계는 도입하지 않는다.
4. 기록 내용의 정본은 저장된 제목·본문이다. 이후 사용자가 이를 편집하면 목록·읽기·검색·MCP도 편집한 내용을 읽는다. 현재 자산값이나 내부 실행 데이터로 과거 본문을 다시 생성하거나 사용자 편집을 덮어쓰지 않는다.
5. 자동 기록의 빈 제목/본문을 `포트폴리오`, `기록`, 명령 코드로 채우는 경로는 종료한다. 사용자가 직접 작성한 동일 단어까지 금지하는 문자열 검사는 만들지 않는다. 수동 기록의 기존 선택 본문/빈 상태 계약은 유지한다.
6. 변경 당시 실제 시장 종목이 하나로 확정되면 정규화 티커를 같은 트랜잭션에서 저장한다. 종목 삭제는 삭제 전에 티커를 확보한다. 여러 계좌의 같은 종목은 한 티커로 연결한다. 여러 종목 일괄 변경은 본문에 종목명·티커별 내역을 남기며 임의의 대표 종목을 선택하거나 새 복수 참조 테이블을 만들지 않는다. 비시장 자산은 기존처럼 본문·태그로 표현한다.
7. 저장된 사실을 설명하는 일반 콘텐츠만 본문에 넣는다. 인증 정보·내부 영수증·폐기된 비공개 메모 등 원본 JSON 전체를 복제하지 않는다. 현재 일반 종목/계좌 메모의 공유는 ADR-0009를 따른다. 사용자 원문·출처 링크를 임의 요약/변형하지 않고 마크다운은 기존 안전한 렌더러로 표시한다.

## 자동 기록 경로 적용표

아래는 목표이며 구현 완료 표가 아니다. 구현자는 현재 웹 HTTP·OAuth MCP·호환 RPC의 도달 가능한 경로를 대조해 각 행의 수정/회귀/예외와 검증 결과를 남긴다.

| 경로 | 제목·본문 기준 |
| --- | --- |
| 계좌/종목 메모 추가·수정·삭제 | `대상명 · 메모 수정`처럼 제목 작성. 본문은 변경한 메모 전문, 삭제는 `메모를 삭제했습니다.`. 긴 이전/이후 원문 쌍이나 별도 diff UI는 추가하지 않음 |
| 자산 상세의 종목 정보·대표 태그·계좌별 보유 수정 | `종목명 · 자산 정보 수정`. 실제 바뀐 이름/통화/태그/메모와 계좌별 수량·평균가·평가금액·배분 포함 여부를 알아볼 수 있는 문장/목록. 숫자는 단위·통화를 붙여 전후 값 표시. 변경 없는 속성은 생략 |
| 계좌/종목/보유 등록·수정·삭제 | 대상 이름·행동과 식별에 필요한 계좌/티커, 변경한 값. 삭제 후에도 당시 대상과 작업을 이해할 수 있어야 함 |
| 자산 태그 관리에서 이미 생성하는 자동 기록 | 태그 이름과 추가/이름 변경/삭제 사실. 태그 관리에 새 자동 기록 의무나 추가 확인창을 도입하지 않음 |
| 목표 배분 저장·초기화 | `목표 배분 변경`/`목표 배분 초기화`. 변경 태그별 목표 전후 비중과 선택 메모. 최초 미설정 상태와 초기화를 모든 목표 0%로 혼동하지 않음 |
| 표 편집 | `보유 N건 수정` 등 실제 변경 건수. 변경한 종목·계좌별 항목과 값만 표시. 전체 포트폴리오 snapshot을 그대로 본문에 출력하지 않음 |
| 매매·잔고 보정 | 종목·계좌와 매수/매도/보정, 수량·체결가 또는 보정값·전후 보유값. 원본 금융 실행 규칙은 유지 |
| 할 일 완료·다시 열기·반복 중단 등 현재 노출하는 기록 | 실제 할 일 제목과 수행 결과/행동. 관련 할 일과 회차 의미 보존. 숨겨진 생성/수정 로그를 새로 타임라인에 노출하지 않음 |
| 원칙 저장 | 기존 `원칙 작성`/`원칙 변경`과 변경 메모, 메모 생략 시 기본 설명 유지. 원칙 전문·새 revision·줄 diff를 활동에 중복 저장하지 않음 |
| 조회·변경 없는 저장·재시도·기록 자체 편집 | 새 활동을 추가 생성하지 않음. 이미 성공한 금융 요청의 재시도도 최초 실행을 중복하지 않음 |

한 번의 기존 목적별 저장에서 여러 속성/계좌를 수정하면 활동 한 건에 함께 기록한다. 독립적으로 수행한 여러 MCP 호출을 시각이 가깝다는 이유로 사후 병합하지 않는다. 새 일괄 명령 API는 범위 밖이다. 가격 갱신·설정·프로필·피드백 등 다른 기능을 활동 기록 대상으로 추가 확장하지 않는다.

대량/긴 내용은 기존 제목·본문 길이 한도와 표 편집 지원 범위를 실제 fixture로 검증한다. 저장 내용을 조용히 잘라내거나 원본만 부분 저장하지 않는다. 한도를 넘는 입력은 명확한 오류와 초안 보존으로 처리한다. 기존 지원 시나리오가 한도 때문에 막히면 이 티켓에서 최소 한도 조정 계약을 먼저 명시한 뒤 적용한다.

## 읽기·편집·검색·MCP

- 목록과 검색 결과는 저장 제목과 본문 첫 내용의 짧은 일반 텍스트 미리보기를 쓴다. 읽기는 같은 제목과 전체 마크다운, 편집은 같은 제목·본문 원문이다. 접근성 이름도 같은 제목을 사용한다.
- 읽기→편집→저장/취소는 기존 1차 모달 전환을 유지한다. 별도 기술정보/diff/숨은 내용 모달을 추가하지 않는다. 긴 메모·링크·변경 내역도 화면 폭 안에서 읽으며 마크다운 표/코드만 내부 가로 스크롤을 허용한다.
- `app_list_action_timeline`, 최근 활동, 활동 단건, 검색, 일일/기간 문맥과 대응 MCP가 동일한 저장 제목·본문을 사용하도록 적용표를 만든다. 짧은 목록 응답은 전체 내용을 읽는 기존 단건 조회로 연결한다. 여러 조회가 서로 다른 제목을 추측하지 않는다.
- `update_entity_note` 등 자동 기록 작성 도구는 성공 결과로 기존 반환값과 함께 해당 `activity_id`를 재조회할 수 있게 한다. 새 실행의 no-op은 새 기록이 없음을 구별하고, 동일 성공 요청의 재시도는 최초 결과를 유지한다. 이미 삭제한 활동을 재시도로 다시 생성하지 않는다. 기존 receipt 결과의 호환 처리는 현재 호출자와 대조한다.
- 도구 설명·입출력 스키마·handler·workflow guide와 review manifest를 함께 맞춘다. 에이전트에 별도 `create_activity`를 호출하여 자동 기록을 중복 생성하도록 안내하지 않는다.
- 제목·본문 수정은 기존 비동기 색인을 갱신한다. 기록에만 있던 메모 표현과 연결 티커로 웹·MCP에서 같은 항목을 찾을 수 있어야 한다. 다중 종목 일괄 기록의 본문 일치와 단일 티커 연결 일치를 같은 것으로 표시하지 않는다.
- 기록 편집/삭제는 실제 종목 메모·보유·배분·원칙·할 일 상태를 되돌리지 않는다. 내부 금융/재시도 소비자에 필요한 실행 데이터는 그 역할로 보존하고 표시를 위해 권한을 넓히지 않는다. 내부 종류나 변경 JSON의 무조건 전면 삭제는 본 티켓 범위가 아니다.

## 기존 기록 복구

1. 적용 전 도달 가능한 자동 기록 경로와 누락 제목·일반 placeholder·읽을 수 없는 JSON 본문·참조 누락을 집계한다. 로컬에서는 익명 fixture를 사용한다. 운영 적용 전 대상·백업·건수·예외와 복구 방법을 기록한다.
2. 당시 `before_data`/`after_data`와 검증 가능한 대상 정보에서 읽을 수 있는 제목·본문·시장 티커를 복구한다. 현재 메모나 현재 보유값으로 과거 결과를 채우지 않는다. 현재 대상명만 확인 가능한 경우 이를 당시 이름으로 단정하지 않는다.
3. 자동 생성된 미완성 내용임을 확인한 필드만 보완한다. 사용자가 작성/수정한 제목·본문·태그·시각·참조와 금융 receipt를 보존한다. 본문이 `기록`이라는 이유만으로 사용자 원문을 일괄 덮어쓰지 않는다. 편집 여부가 모호하면 별도 예외 목록에 남긴다.
4. 대상이 삭제됐거나 당시 정보가 없으면 확인 가능한 행동/티커만 사용한다. 정보가 부족한 항목은 `당시 상세 내용이 남아 있지 않습니다.`처럼 알려주고 내부 코드나 추측한 금융값으로 대신하지 않는다. 기존 기록을 삭제하거나 시각이 같은 기록들을 합치지 않는다.
5. 새 migration/제한된 보정 절차는 재실행해도 중복 문구·활동을 만들지 않아야 한다. 읽기 요청으로 복구 쓰기를 실행하지 않는다. 복구된 본문은 기존 큐로 재색인하고 구 벡터가 수정 전 내용을 반환하지 않는지 확인한다.

## 구현 순서와 완료 조건

1. **S1 종목 메모 수직 슬라이스:** `update_entity_note`의 제목·전체 메모 본문·시장 티커·기록 ID를 원자 저장 → 웹 목록/읽기/편집과 MCP 단건 조회 → 본문/티커 검색까지 연결한다. 동일 기능의 웹 자산 상세 메모 저장도 비교하고 의미가 일치해야 한다. 이 흐름이 공통 표현·최소 저장 helper의 첫 소비자이며, 실제 API와 UI 왕복 확인 전 기반 완료로 보고하지 않는다.
2. **S2 다른 자동 저장 경로:** 적용표를 따라 자산/계좌/종목/삭제/배분/표 편집 등 누락을 해결하고 매매·보정·원칙·할 일 회귀를 확인한다. 각 경로마다 실제 변경·재조회·검색·실패/재시도까지 검증하고 독립 커밋 가능한 단위로 진행한다. 사용하지 않는 구 경로는 다시 활성화하지 않는다.
3. **S3 과거 복구와 전수 교차 검증:** 미완성 기록 복구·예외 보고·비동기 재색인을 연결한다. 최근/기간 문맥·OAuth MCP·본인/공유 읽기·사용자 편집 보존을 확인하고 도구 설명/스키마 색인/검증 기록을 맞춘다. 로컬 완료, 운영 DB·Edge·웹 배포, 실제 ChatGPT 검증을 별도로 기록한다.

## 인계

2026-09-28: 사용자 승인 개선안을 티켓으로 작성했다. 앱 코드·SQL·MCP·운영 데이터는 변경하지 않았다. 구현은 Sol에서 S1부터 시작한다. 구현 중 확정할 세부 항목은 현재 자동 기록 작성/조회 경로 전체 목록, 과거 사용자 편집 판별 근거, 대량 변경의 실제 길이 한도, 구 성공 receipt 응답 호환 처리다. 각 소비 슬라이스에서 최소 계약과 검증 근거를 먼저 남기며 새 데이터 모델로 확대하지 않는다.

2026-09-29 구현 기록:

- `app_update_entity_note`가 같은 트랜잭션에서 대상명 제목, 변경 후 메모 전문, 시장 티커, 활동 ID를 저장한다. 변경 없는 요청은 새 활동 ID가 `null`이며 기존 성공 receipt는 그대로 재생한다. 웹 자산 상세의 메모와 별도 MCP 메모 수정도 같은 활동 저장값을 조회한다.
- 기존 목적별 저장의 자동 활동 INSERT에서 계좌·종목·보유·태그, 자산 상세, 배분, 표 편집, 매매·보정, 할 일 전환을 사람이 읽을 수 있는 제목·본문으로 만든다. 배분 저장은 변경 전후 목표를 함께 전달한다. 변경 사실이 없는 일부 legacy UPDATE 활동은 생성하지 않는다. 원칙의 기존 제목/변경 메모는 유지한다. 활동 편집은 원본 금융·자산 값을 되돌리지 않는다.
- 목록/읽기/편집이 저장 제목을 우선 사용하며, 과거 제목 누락 행에 대해서도 동일한 한국어 대체 제목을 쓴다. 새 메모 기록은 활동 단건과 MCP `get_activity`에서 같은 본문·티커를 반환한다. 도구 결과에 `activity_id`를 추가하되 이전 receipt 호환을 위해 선택적 필드로 두고 workflow 안내/검증 목록을 갱신했다.
- 과거 보정은 성공·첫 버전·자동 활동·제목 누락·본문이 정확히 `기록`인 행 중 원래 전후 데이터가 있는 유형만 대상으로 한다. 사용자 편집 가능성이 있는 다른 행은 그대로 둔다. 재실행 시 0건 변경을 확인했다. 운영 DB의 실제 대상 건수·예외 건수는 배포 전에 별도 집계해야 한다. 당시 저장되지 않은 대상명/계좌명/티커를 현재 값으로 추정해 넣지 않는다.
