# [자산] 상세 안에서 직접 편집·저장하고 모달 왕복 제거

2026-09-24 · P2 · 검토·설계 완료, 구현 전.

GitHub: https://github.com/kimyongin/fin/issues/120

## 목적과 실제 구현 확인

이 티켓의 직접 편집·단일 저장은 자산 전용 예외가 아닌 [모달 디자인 가이드](../design/modal-guidelines.md)의 공통 규칙이다. [#123](./ui-16-modal-inline-edit.md)이 모든 모달 전수 적용을 담당하며 본 티켓은 자산의 구체적인 저장·금융 계약을 담당한다.

사용자는 자산 상세에서 보유값·종목 정보·메모를 확인하고 그 자리에서 수정·저장하기를 원한다. 속성마다 다른 편집 창을 열어야 하는 동선을 없앤다. 상세를 단순 링크 모음이 아닌 실제 편집 공간으로 만든다.

현재 `src/features/assets/AssetsPage.jsx`의 `InstrumentDetail`은 `ModalShell variant="detail"`로 종목·계좌별 보유를 읽기 전용 표시한다. 보유 수정/잔고 맞추기/종목 정보 수정/보유 메모/매매 기록/다른 계좌 보유 추가 버튼은 대체로 `onClose()` 후 별도 모달을 연다. 따라서 주요 경로는 두 dialog가 계속 겹치는 코드라기보다 상세 종료→다른 모달 진입이지만, 사용자가 같은 자산을 편집하며 화면을 반복 전환한다는 문제는 같다. 이번 검토는 코드 기준이며 실제 브라우저에서 모든 경로를 재현한 것은 아니다.

기존 편집 내용과 저장 경로:

- `features/modals/EditorModals.jsx`: 종목 표시명·통화·유형·가격/기준일·태그·메모, 계좌별 수량/평균가 또는 매입/평가금액·잔액·메모를 편집한다. 기존 종목 티커는 수정 불가다.
- `features/portfolio/instrumentActions.js`, `holdingActions.js`: 종목과 시장형/평가형/현금성 보유를 각각 목적별 RPC로 저장한다.
- `HoldingReasonModal`/`privateHoldingNotesData`: 종목 공통 또는 계좌별 비공개 보유 메모를 저장한다. 일반 메모와 공개 범위가 다르다.
- `HoldingIntegrityModal`, `TradeEntryModal`: 보정·실제 확인·매매는 별도 금융 계약과 확정 절차를 갖는다.

## 화면 계약

하나의 자산 상세 모달에 아래 순서로 배치한다. 편집 가능한 사용자는 추가 ‘편집’ 모달 없이 입력할 수 있다. 공유/읽기 전용 사용자는 허용된 정보만 일반 텍스트로 읽는다.

| 영역 | 내용과 조작 |
| --- | --- |
| 헤더 | 종목명·티커·닫기. 평가 요약/자동 시세와 기준일은 읽기 정보로 구분 |
| 종목 공통 정보 | 표시명·태그, 기존 수정 가능한 통화/유형·수동 가격/기준일, 일반 메모·비공개 보유 메모. 모든 계좌의 해당 종목에 적용됨을 짧게 표시 |
| 계좌별 보유 | 계좌 이름을 제목으로 시장형 수량/평균가, 평가형 매입/평가금액, 현금성 잔액과 해당 보유의 일반/비공개 메모를 직접 편집 |
| 추가 작업 | 다른 계좌에 보유 추가, 매매 기록, 증권사 확인, 삭제처럼 속성 편집과 다른 행동 |
| 하단 | 닫기와 대표 버튼 `저장`. 변경 없음/저장 중/저장 오류 상태를 구분 |

- 수량·평균가처럼 빈번한 값은 바로 보여준다. 긴 메모·드문 종목 설정은 같은 본문에서 펼칠 수 있으나 별도 모달로 보내지 않는다. 접어도 초안을 유지하고 오류가 있으면 해당 영역을 연다.
- 전체 계좌에서 진입하면 해당 종목의 계좌별 보유를 표시한다. 특정 계좌에서 진입하면 그 계좌 영역을 우선 펼치고 다른 계좌는 같은 본문에서 볼 수 있게 한다. 숨긴 계좌를 편집·삭제했다고 처리하지 않는다.
- 편집 가능한 속성은 현재 폼과 대조표로 전수 확인한다. 기존 티커 불변·유형별 검증은 유지하고 평가금액 같은 파생값을 임의 입력으로 바꾸지 않는다. 유형/통화 변경은 기존 보유에 미치는 영향을 검증한다. 기존에 지원하는 계좌 재지정도 별도 창으로 보내지 말고 해당 계좌 영역의 입력으로 제공하되 중복 보유 처리 계약을 먼저 확인한다.
- 자동 조회 시세와 수동 가격 입력을 명확히 구분한다. 아무것도 바꾸지 않은 시세를 저장 payload에 다시 넣어 수동 가격으로 만들지 않는다.
- 일반 메모와 비공개 보유 메모는 같은 문서/입력으로 합치지 않는다. 실제 공유 정책에 맞는 짧은 라벨로 구분하고 종목 공통 메모와 계좌별 메모의 우선순위도 유지한다.
- 기본 반응형은 640px 미만 전체 화면, 그 이상 최대 42rem 중앙 모달이다. 한 종목 편집을 위해 데스크톱 전체 화면이나 읽기 전용 detail drawer를 사용하지 않는다. 여러 계좌는 세로 섹션이며 표 편집은 기존 별도 기능으로 유지한다.

## 한 모달 안의 추가 작업

- 다른 계좌에 보유 추가는 계좌 선택과 유형별 입력을 같은 상세에 추가한다. 일반 저장에 함께 반영한다. 새 계좌 만들기는 자산의 기존 계좌 추가 경로를 사용하며 이 상세에 계좌 관리까지 넣지 않는다.
- 수량/평균가 등 절대값 수정은 일반 `저장`으로 처리한다. 이것만으로 매매를 추정하거나 증권사 확인 완료로 기록하지 않는다. ‘보유 수정’과 같은 값을 다시 입력하는 ‘잔고 맞추기’ 모달 왕복은 제거한다.
- 실제 증권사 확인은 같은 shell의 확인 영역에서 날짜·확인 항목·메모를 명시해 기록한다. 필요한 보정 미리보기/확정은 같은 shell 내부 단계로 재사용한다. 기존 금융 검증·중복 방지·확인 의미를 UI 통합을 이유로 생략하지 않는다.
- 매매 기록도 동일 shell에서 매매 입력→미리보기→확정으로 전환한다. 완료/취소 시 상세로 돌아온다. 매매를 일반 속성 저장에 섞지 않는다.
- 일반 편집 초안이 있을 때 매매/확인/삭제 같은 별도 쓰기로 넘어가면 같은 shell에서 저장 후 계속/변경 버리고 계속/취소를 선택하게 한다. 저장 실패 시 진행하지 않는다. 금융 단계 전환으로 초안을 조용히 버리거나 수정 전 잔고로 거래를 확정하지 않는다.
- 보유 삭제/종목 삭제는 대상과 영향이 명확한 별도 행동이다. 확인은 동일 shell 안에서 하고 기존 삭제 제약을 유지한다. 삭제를 단순 빈 입력이나 계좌 섹션 접기와 연결하지 않는다.
- 이 흐름에는 활성 dialog·포커스 트랩·배경 하나만 존재해야 한다. 미저장 확인도 추가 모달을 쌓지 않는다.

## 최소 저장 계약 — 구현 첫 단계에서 확정

자동 활동 기록의 최신 구조는 [#122](./activity-15-tags-and-references.md)의 본문·태그·보유 참조를 따른다. 활동 종류별 편집 제한은 유지하지 않으며 기록 수정/삭제와 실제 잔고 변경을 분리한다. 이 상세 저장의 원자성/재시도와 개인정보 경계는 그대로 필요하다.

사용자에게 한 번의 `저장`을 제공하므로 종목 공통 정보·변경한 계좌 보유·일반/비공개 메모·추가 보유는 성공 또는 실패가 한 단위여야 한다. 브라우저에서 기존 RPC를 연속 호출하고 일부만 저장된 채 전체 성공으로 표시하지 않는다.

1. 기존 RPC의 실제 SQL·권한·활동 기록·원자성·충돌 계약을 확인한다. 기존 저장 함수로 한 단위 처리가 가능하면 재사용하고, 부족하면 한 종목 상세를 저장하는 목적별 RPC 하나로 묶는다. 범용 command 엔진·새 테이블·전체 자산 덮어쓰기 API를 만들지 않는다.
2. 변경된 필드와 계좌만 명시해서 저장한다. 미조회/조회 실패한 메모는 빈 문자열로 취급해 지우지 않는다. 초안 초기값은 편집용 정본에서 가져오고 계산용 집계 객체로 종목/보유 ID나 평균가를 혼동하지 않는다.
3. 서버가 종목·계좌·보유의 동일 소유자와 실제 관계, 유형별 필드·수량/금액 정밀도·중복 보유를 검증한다. 저장 범위 중 하나가 실패하면 전체 롤백한다. 신규 보유 추가의 응답 유실 재시도로 중복 행/활동이 생기지 않게 한다. 기존 금액 충돌·비공개 메모 충돌 보호를 약화시키지 않는다.
4. 기존 금융/자동 기록을 재사용한다. 범용 ‘상세 저장’ 로그와 기존 로그를 중복 생성하지 않으며 비공개 메모를 공유 활동 payload에 노출하지 않는다.
5. 저장 성공 시 상세를 유지하고 반영된 값으로 dirty 상태를 갱신한다. 자산 목록·집계도 갱신한다. 저장 완료 후 조회 실패는 저장 실패와 구별하고 재조회만 수행한다. 늦은 조회 응답/가격 갱신/창 크기 변경이 편집 중 초안을 덮어쓰지 않는다.
6. RPC 명칭/입출력·오류/재시도·동시 수정 처리와 각 필드의 저장 경로를 이 티켓에 기록한 뒤 구현한다. 기존 API/MCP 쓰기와 교차 사용해도 같은 데이터/권한/금융 규칙을 따른다. UI 편의를 위한 저장 RPC를 자동으로 새 MCP 도구로 추가하지 않는다.

## 구현 범위와 순서

저장 계약·현재 필드 대조 → 종목 공통/계좌별 직접 편집과 원자 저장 → 메모/추가 보유 연결 → 금융 작업의 단일 shell 단계 → 회귀 검증 순서로 진행한다. 작은 수직 슬라이스별로 실제 저장/재조회를 검증한다.

EditorModals의 필요한 폼 본문과 금융 컴포넌트의 shell/내용 분리를 재사용하되 공통 폼 엔진을 만들지 않는다. 자산 목록에서 직접 여는 계좌/보유 추가와 표 편집 등 유효한 경로는 유지한다. 다른 소비자가 있는 기존 모달을 무조건 삭제하지 말고, 이 상세가 사용하는 교체 경로와 실제 미사용 코드만 정리한다.

#118/#119와 독립 작업이다. #113의 종목 상세→별도 편집 진입 요구는 이 티켓으로 대체한다. 모달 디자인 가이드의 ‘서로 다른 쓰기를 억지로 묶지 않는다’ 원칙은 금융 행동에 유지하며, 이번 일반 상세 편집은 구체적인 한 종목 저장 시나리오로 원자 계약을 정한다.

## 완료 기준

- [ ] 종목 상세에서 기존 편집 가능 속성을 바로 수정·저장하고 별도 속성 편집 모달로 이동하지 않는다. 실제 기존 필드와 대조한 표를 티켓에 남긴다.
- [ ] 종목 공통/계좌별 적용 범위와 일반/비공개 메모가 명확하다. 시장형·평가형·현금성·복수 계좌에서 읽기/입력이 정확하다.
- [ ] 여러 계좌값·태그·메모를 함께 수정해 저장 성공 후 웹/API에 동일 값이 보인다. 하나의 검증 오류·권한 실패·충돌이 전체 부분 저장을 남기지 않는다.
- [ ] 응답 유실 재시도·신규 보유 중복·미조회 메모·읽기 실패·저장 후 갱신 실패·늦은 응답을 검증한다. 변경 없는 저장은 시세/활동/잔고 확인을 새로 만들지 않는다.
- [ ] 매매/증권사 확인/삭제/추가 보유 모든 경로에서 활성 dialog가 하나다. 단계 취소와 뒤로가기·미저장 선택·저장 실패에서 초안과 화면 맥락을 보존한다.
- [ ] 공유 사용자는 편집할 수 없고 비공개 메모를 조회할 수 없다. 서버와 응답/활동에도 같은 경계가 적용된다.
- [ ] 닫으면 기존 계좌 선택·검색·스크롤·초점으로 돌아간다. 360/390/768/1024/1440px에서 긴 이름·메모·오류·다계좌·키보드·44px 조작·footer/하단 탭 겹침을 확인한다.
- [ ] 관련 DB/API·MCP 교차 회귀·사용자 흐름 E2E·빌드·인코딩/변경된 RPC 배포 검사를 수행한다. 실제 검증/실기기 미검증 범위·로컬/운영 적용을 구분해 기록한다.
- [ ] 화면 구조/모달 가이드/시작 문서·필요한 스키마 개요/API 가이드에 최종 계약을 반영한다.

현재는 검토와 티켓 작성만 완료했으며 제품 코드·DB·배포는 변경하지 않았다.
