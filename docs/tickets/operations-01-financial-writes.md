## 근거와 발생 조건
- `supabase/migrations/202609210010_trade_entry_foundation.sql:257`: app_log_completed_trade가 잔고 버전을 검사한 뒤 행 잠금을 획득한다. 서로 다른 preview와 요청 키를 가진 동시 확정이 같은 검사에 통과하면 나중 요청이 앞선 잔고 변경을 덮어쓸 위험이 있다. 정적 검토 결과이며 실제 두 세션 재현은 구현 첫 단계다.
- `src/features/assets/TradeEntryModal.jsx:22`: 저장과 onSaved 재조회를 한 try에 묶고 오류 시 preview를 지운다. 저장 성공 후 조회 실패/응답 유실 시 새 preview·새 요청 키로 중복 거래를 기록할 수 있다.
- tradeData.js와 integrityData.js의 취소·보정·확인도 호출마다 키를 생성한다.

## 최소 변경 범위
- 먼저 로컬 독립 DB 두 세션으로 경쟁 상황을 재현한다. 잔고 잠금 후 버전 검사 또는 조건부 UPDATE로 검사와 변경을 원자화한다.
- 매매/보정/취소의 잠금 순서, 신규 잔고 동시 생성도 점검한다. 적용 migration은 보존하고 새 migration을 추가한다.
- 동일 저장 시도의 preview와 idempotency key를 유지한다. 입력 변경 시에만 새 시도로 전환한다.
- 서버 성공, 결과 불명, 저장 후 화면 갱신 실패를 구분한다. 성공한 쓰기는 조회 재시도로 복구한다. 결과 불명은 동일 키 재시도부터 한다.
- 보정 미리보기 후 확인 범위 변경도 preview를 무효화하도록 점검한다.
- 필요한 작은 재시도 helper만 공유한다. 범용 CRUD/명령 엔진은 만들지 않는다.
