# [활동] 할 일과 기록의 상단 요약 구조와 요약 기반 유사도 검색

상태: 로컬 구현·자동 검증 완료 · 운영/실클라이언트 검증 대기 · 2026-10-01
GitHub: https://github.com/kimyongin/fin/issues/174

2026-10-01 후속: [#175 단일 벡터와 무료 티어](./search-06-single-vector-free-tier.md)의 로컬 구현·검증을 완료했다. 제목 100자·요약 300자 상한을 확정하고 청크 없이 상단 전체를 임베딩한다. 아래 500자/1,000자와 청크 관련 계약·검증은 #174 당시 이력이며 현재 상한과 색인 구조는 #175를 따른다. 읽기 상세의 문서 표현은 [UI #167 후속](./ui-35-list-reading-and-mobile-interaction.md)을 따른다.

할 일과 기록을 상단의 짧고 구조화된 정보와 하단의 상세 본문으로 나눈다. 에이전트 스킬의 이름·설명으로 대상을 먼저 식별하고 필요한 상세 내용을 나중에 읽는 구조를 차용한다. 벡터 임베딩은 상단 내용에만 적용한다. 사용자가 2026-09-30 “티켓 구현하자”로 구현을 요청했고, 남은 선택에 “본문도 필수로 구현”이라고 답했다.

## 구현 계약 확정

- 신규 제목·요약·본문 모두 필수. 제목 500자, 요약 1,000자, 본문 25,000자. 요약은 보통 2~4문장의 일반 텍스트이고 상세 본문은 Markdown이다. 새 결론/조건 필드를 추가하지 않는다. 할 일 본문은 기존 `trigger_text` 필드를 유지해 데이터 이관 없이 긴 본문을 지원한다.
- 의미 검색 allowlist는 제목·요약뿐이다. 태그·일정·참조는 기존 필터/표시 용도다. 기존 자료를 자동 요약하지 않고 제목만 의미 검색한다. 본문 키워드 검색은 유지하되 목록은 본문·일치 발췌를 표시하지 않는다.
- 새 웹·MCP는 strict 목적별 RPC로 저장한다. 구 RPC는 현재 설치된 클라이언트용 호환 경로로 유지하며 같은 도메인 쓰기와 영수증을 재사용한다. 배포 후 실제 구 클라이언트 사용 여부를 확인한 별도 종료 작업 없이 구 경로를 제거하지 않는다. 신규 본문/요약 null은 거절한다. 기존 기록의 관련 값만 수정할 때는 미변경 null을 보존한다. 할 일 전체 저장은 필수 세 필드를 모두 받는다.
- complete는 실제 `result_title`·`result_summary`·`result` 본문을 요구하고 한 트랜잭션으로 결과 기록과 상태를 저장한다. reopen/cancel에는 결과를 강제하지 않는다. 자동 금융/원칙/배분/메모 기록의 상단은 서버가 확인한 변경 사실에서 결정적으로 생성하며 과거 자료를 backfill하지 않는다.
- 목록은 제목 → 요약(최대 3줄, 상세에서 전체 읽기) → 기존 상태·일정·태그·조작으로 구성한다. 빈 요약이면 제목·메타데이터만 표시한다. 요약 편집과 완료 결과 작성은 단일 모달의 필드이며 중첩 편집 모달을 만들지 않는다.
- 배포 순서: 호환 DB·worker와 재색인 → 웹·HTTP/OAuth MCP → 스킬/플러그인. 이 구현 요청은 운영 배포/플러그인 업로드 요청과 구분한다.

아래 설계 검토안의 미정/구현 금지 표현은 작성 당시 기록이며 위 확정 계약으로 대체한다.

## 확정 요구와 제안의 구분

사용자 확정 요구는 할 일과 기록 양쪽의 상단 요약 구조, 하단 본문, 상단만 벡터 임베딩하는 검색 범위다. 화면의 목록에서도 상단 정보만 사용하며 그 구조에 맞게 디자인해 가독성을 높인다. 저장된 상단 내용을 그대로 한 덩어리로 출력하는 방식은 요구를 충족하지 않는다. 아래 필드 구성·글자 수·키워드 검색·기존 자료 전환 방법은 검토안이다. 이 티켓 작성으로 구현이나 운영 데이터 변경을 시작하지 않는다.

## 현재 구조와 바뀌는 의미

- 스킬 원본 [Portfolio SKILL.md](../../plugins/portfolio/skills/portfolio/SKILL.md)는 상단 `name`·`description`과 자세한 지침·참고 문서를 분리한다. 이 제품에는 대상을 찾기 위한 짧은 설명과 상세 읽기의 분리를 차용한다. 스킬 파일 전체 형식이나 YAML 편집 UI를 그대로 옮길 필요는 없다.
- 현재 기록은 `activity_events.title/body`, 할 일은 `portfolio_tasks.title/trigger_text`를 사용한다. [Pinecone 계약](../design/activity-search-pinecone.md)과 `20260927160000_activity_search_pinecone_context.sql`은 제목과 본문/설명 전체를 청크로 나누어 임베딩한다.
- 현행 계약은 본문 후반부의 조건·숫자까지 의미 검색하는 시나리오를 포함한다. 새 요구는 상단 설명을 통해 관련 대상을 찾는 방향으로 이 범위를 바꾼다. 본문에만 있는 정보의 의미 검색 누락은 새 범위의 한계이며 전체 본문 임베딩으로 조용히 보완하지 않는다.
- 제목·요약과 상세 본문을 같은 대상에서 저장한다. 새 지식 테이블·불변 이력·별도 요약 버전 테이블·범용 문서 엔진은 도입하지 않는 방향을 제안한다. 기존 권한·금융 원자성·멱등성·반복 일정·할 일 완료 의미는 유지한다.

## 제안하는 상단과 하단

| 영역 | 할 일 | 기록 |
| --- | --- | --- |
| 상단 제목 | 해야 할 작업의 이름 | 수행·관찰·판단을 식별하는 이름 |
| 상단 요약 | 목적, 적용 상황, 확인할 범위와 기대 결과를 짧게 설명 | 핵심 결과, 중요한 근거와 적용·재검토 조건을 짧게 설명 |
| 기존 메타 정보 | 상태·일정·반복·태그·관련 종목 | 날짜·출처·태그·관련 종목·연결된 할 일 |
| 하단 본문 | 자세한 실행 절차·기준·참고 자료 | 자세한 근거·수치·출처·한계·조사 과정 |

최소 필드로 `title`, 별도 `summary`, 상세 본문을 제안한다. 결론·조건·근거마다 고정 필드를 추가하기보다 짧은 요약 안에 필요한 내용을 적는다. 실제 반복 사용에서 독립 필드가 필요한 사례가 확인되면 그때 검토한다. 날짜·태그·관련 대상은 기존 필드를 재사용한다.

요약은 단순히 본문의 첫 몇 글자를 잘라 만든 미리보기가 아니다. 어떤 상황에서 이 항목을 찾아 읽어야 하는지 알 수 있어야 한다. 본문 첫 문단을 파싱해 요약으로 간주하거나 요약을 본문에도 중복 저장하지 않는 방향을 제안한다. 별도 필드여야 UI·MCP·색인에서 같은 범위를 명확히 사용할 수 있다.

읽기 상세는 제목과 요약을 먼저 보여주고 기존 메타 정보와 본문을 이어서 표시한다. 본문의 마크다운 표·목록·출처는 유지하며 반드시 접어서 숨기는 방식은 요구하지 않는다. 편집은 같은 1차 모달에서 제목·요약·본문을 한 초안과 한 번 저장으로 다룬다. 목록은 제목과 짧은 요약으로 탐색하고 보기로 상세를 읽는 방향을 제안한다.

합성 예시:

```text
할 일 제목: 장기채 투자 조건 점검
요약: 금리와 대출 조건이 바뀌었을 때 장기채의 투자 근거와 현금 여력을
확인한다. 가격 하락만으로 매수를 결정하지 않고 투자 조건의 유지 여부를 점검한다.
본문: 확인할 자료, 계산 절차, 비교 기준, 완료 기록에 남길 근거와 한계.

기록 제목: 장기채 투자 조건 점검 결과
요약: 이번 점검에서는 기존 판단을 유지했다. 금리 부담과 현금 여력에 대한
불확실성이 남아 있어 대출 조건이 확정되면 다시 검토한다.
본문: 당시 자료, 수치, 판단 이유, 반대 근거와 출처.
```

이는 구조 설명용 예시이며 실제 투자 판단이나 사용자 기준이 아니다. 기록의 결론·할 일 본문은 저장된 자료로 취급하고 에이전트 권한을 바꾸는 명령으로 해석하지 않는다.

## 목록은 상단 구조를 디자인해서 표시한다

날짜별 기록, 할 일 목록, 검색 결과와 연결된 항목의 목록에서 내용은 상단 필드만 사용한다. 본문·본문의 첫 문단·마크다운 미리보기·표·출처 목록을 목록 카드에 넣지 않는다. 요약이 없는 기존 항목도 본문 잘라내기로 대체하지 않는다. 없는 요약은 빈 상태로 다루는 방법을 설계에서 정한다.

상단을 YAML·JSON·마크다운 문서 그대로 렌더링하지 않는다. UI가 필드의 의미를 알고 제목, 요약, 메타 정보, 태그와 조작을 분리해 표시한다. 요약을 표현하기 위해 별도의 생성 요약을 다시 만들거나 사람이 확인한 문장을 재작성하지 않는다. 같은 내용의 가독성을 배치·간격·글자 역할로 높인다.

| 요소 | 제안하는 표시 역할 |
| --- | --- |
| 제목 | 항목을 식별하는 첫 줄. 공통 `item-title` 역할을 사용하고 기존 보기·편집 진입을 유지 |
| 핵심 요약 | 제목 아래 독립된 읽기 영역. 목록 `secondary` 역할로 제목·메타와 구분하고 본문 미리보기를 대체 |
| 상태·날짜·일정 | 할 일의 진행 상태와 일정, 기록의 수행 시각·출처를 공통 메타 역할로 배치 |
| 태그·관련 대상 | 기존 칩과 참조 표시를 사용하고 제목/요약을 밀지 않도록 줄바꿈 |
| 행동 | 보기·편집, 완료·이번 완료·중단을 의미에 따라 구분. 행 전체 클릭과 겹치는 누름 영역을 만들지 않음 |

할 일은 해야 할 목적·내용과 일정/실행 행동을, 기록은 결과 요약과 시점/관련 대상을 빠르게 읽을 수 있도록 같은 상단 구조 안에서 강조 순서를 달리하는 안을 검토한다. 고정 결론·조건 필드를 채택하면 해당 필드도 명시적인 역할로 배치하며 필드 이름을 문장 앞에 반복 붙이는 것으로 디자인을 대신하지 않는다.

모바일은 가용 폭 안에서 제목 → 요약 → 부가 정보가 읽히게 하고, 넓은 화면에서도 같은 읽기 순서를 유지한다. 정확한 줄 수·생략 정책·상태와 행동 위치는 모바일/PC 시안을 만든 뒤 확정한다. 긴 요약의 나머지는 상세에서 읽을 수 있어야 하고 중요한 부정·조건이 사라지는 생략은 별도로 검토한다. 글자를 줄여 밀어 넣거나 전역 overflow 숨김으로 넘침을 감추지 않는다.

본문 키워드 검색을 유지하는 경우에도 검색 결과 목록에는 상단 정보만 보여준다. 본문 단어 일치 여부를 짧은 메타 표시로 알리고 해당 근거는 상세에서 확인하는 안을 검토한다. 본문 일치 발췌를 목록에 넣는 현행 검색 표시와의 충돌은 #165에서 함께 해결한다.

## 상단만 사용하는 벡터 검색

1. 임베딩 입력의 제안 범위는 `제목 + 요약`이다. 기존 날짜·태그·상태·관련 종목은 표시와 필터로 사용하며 임베딩에 넣을지는 상단 필드 목록 확정 시 명시한다. 사용자에게 보이지 않는 별도 검색 요약은 만들지 않는다.
2. 상세 본문, 연결된 할 일/기록의 본문, 본문 출처·표·코드·금융 snapshot을 passage 입력에 섞지 않는다. 상단에 없는 내용을 임베딩 전 자동 추론·확장하지 않는다. 질의 임베딩은 기존 검색어를 사용한다.
3. 의미 검색 결과의 일치 발췌는 실제 사용한 상단 내용에서만 낸다. 본문을 근거로 높은 유사도가 나온 것처럼 표시하지 않는다. 원본 하나가 여러 청크에 맞아도 결과는 기존 원본 단위로 합친다.
4. 에이전트는 검색 결과의 제목·요약으로 관련 항목을 고른 뒤 목적별 상세 조회로 본문을 읽고 판단한다. 검색 점수·요약만으로 본문의 주장을 확정하거나 저장된 검토안을 채택된 원칙으로 간주하지 않는다. 검색/목록 응답의 본문 제공 범위도 이 흐름에 맞춰 검토한다.
5. 제목·요약 변경은 해당 원본의 벡터를 무효화하고 재색인한다. 본문만 바뀌면 상세 내용은 갱신하되 임베딩 입력·내용 해시가 같으면 재임베딩하지 않는 방향을 제안한다. 요약과 본문이 모순되지 않도록 작성·편집 책임을 함께 정한다.
6. 전체 본문용 구 벡터·구 발췌는 전환 후 의미 검색에서 사용하지 않는다. 대기 중인 구 작업과 늦게 도착한 worker 결과도 거절할 수 있도록 입력 범위 식별자·해시·커서 계약을 정한다. 기존 큐·벡터 저장소 안에서 해결하고 새 상태 테이블을 선행하지 않는다.
7. 요약 없는 기존 자료를 본문 임베딩으로 대체하지 않는다. 제목만 임베딩하거나 요약 준비 전 의미 검색에서 제외하는 대안 중 하나를 확정해야 한다. 불완전 색인 상태를 정상 완료로 표시하지 않는다.

본문의 정확한 문구·숫자를 찾는 키워드 검색은 전체 본문을 유지하는 안을 제안한다. 사용자가 제한한 것은 벡터 유사도 검색이므로 키워드 범위까지 제한됐다고 해석하지 않는다. 다만 이 선택은 아직 확정하지 않았다. 혼합 결과에서 상단 의미 일치와 본문 단어 일치를 구분한다. 목록은 상단만 표시하고 본문 일치 근거는 상세에서 제공하는 안을 검토한다.

## 요약 작성과 기존 기록 전환

- 신규 작성: 사용자와 에이전트가 저장 전에 상단 요약과 본문을 함께 확인한다. 에이전트 스킬의 기록 초안과 MCP 필드도 같은 구조를 사용한다. 요약은 원문에 없는 주장·적용 조건을 만들지 않는다.
- 자동 기록: 기존 금융/원칙/배분 저장에서 생성하는 기록에는 그 트랜잭션의 확인된 사실로 짧은 요약을 만드는 방법을 정한다. 요약 보완을 위해 성공한 금융 변경을 반복하거나 별도 수동 기록을 추가하지 않는다.
- 기존 기록·할 일: 본문·태그·연결·시각·소유권을 보존한다. 제목이 모호하거나 본문이 길면 단순 잘라내기를 완성된 요약으로 취급하지 않는다. AI 일괄 요약을 승인된 데이터 쓰기로 간주하지 않으며, 초안 검토·저장 범위·비용을 따로 정한다.
- 기존 할 일 `trigger_text`와 상세 본문의 관계, 필드 이름/길이와 구 HTTP·OAuth 클라이언트의 생략 처리도 확정해야 한다. 일반 메모·활동을 범용 payload 모델로 합치지 않고 목적별 저장 계약을 확장한다.

## 입력 파라미터와 필수 속성 검증

2026-09-30 재검토에서 작성 지침·입력 스키마·서버 검증을 함께 다루도록 보완했다. 스킬 안내만으로 필수 속성의 완성을 보장하지 않는다. 상단 속성은 별도 파라미터로 받고 서버가 같은 규칙으로 검증하는 것을 구현 범위에 포함한다. 아래 필수성 표는 설계 권장안이며 길이·구 클라이언트 전환과 함께 확정한다.

현재 `portfolio-tools.ts` 기준 `record_manual_activity`는 `title/body`와 날짜·시간대·태그·참조를 따로 받는다. `save_general_task`는 `title/trigger_text`와 일정·반복·태그·대상을 따로 받는다. `transition_general_task`의 완료 결과는 `result` 문자열이며, `update_activity.patch`에는 제목·본문·날짜·참조가 있다. 이 네 경로에 새 `summary`는 아직 없다. 현재 스키마의 required에 있는 nullable 필드는 키가 필요하다는 뜻이며, 실제 값이 반드시 채워져야 한다는 뜻과 구분한다.

| 속성 | 제안하는 책임과 검증 |
| --- | --- |
| 제목 `title` | 신규 할 일·기록 필수. 공백만 있는 문자열과 길이 초과를 거절 |
| 요약 `summary` | 신규 할 일·기록 필수 권장. 별도 문자열로 입력하고 공백·누락·길이 초과를 검증. 본문에서 자동 추출하거나 제목을 그대로 복사해 누락을 숨기지 않음 |
| 상세 본문 | 별도 입력으로 저장. 짧은 기록에도 의미 없는 문단을 요구할지는 검토하되, 상세 절차·근거가 필요한 자료는 스킬의 작성 검토에서 보완. 최종 필수성·할 일 필드 이름과 길이는 확정 필요 |
| 태그 | 선택 배열. 기존 소유자 태그 ID만 허용하며 수정 시 생략은 유지, 빈 배열은 해제 |
| 관련 종목·할 일 | 선택. 없는 연결을 검수 통과용으로 만들지 않음. 티커 형식과 연결 대상 소유권·접근 권한은 서버 검증 |
| 날짜·일정·반복 | 도메인별 기본값과 조건부 필수 규칙. 날짜 미정 할 일 허용, 반복 방식에 필요한 요일·시각·시간대의 조합을 검증 |
| 출처·완료 상태·소유자 | 신뢰할 수 있는 인증·기존 완료 명령·서버 규칙에서 결정. 사용자나 에이전트가 상단을 채우려고 실행 사실이나 작성 주체를 임의 지정하지 않음 |

요청 형태는 목적별 도구의 기존 파라미터에 `summary` 등을 명시적으로 추가한다. 임의의 `header` JSON 또는 본문 앞 YAML에서 속성을 추출하는 범용 입력은 만들지 않는 안을 권장한다. UI는 같은 필드를 각 입력란과 디자인 요소에 연결한다.

수정 요청은 최종 저장 상태를 검증한다. 지원되는 부분 수정에서 생략한 필드는 유지하고, 필수 요약의 명시적인 null/빈값 해제는 거절하는 안을 권장한다. 기존 요약 없는 자료의 단순 태그 편집까지 막을지 등 이관 중 예외를 따로 확정한다. 새 클라이언트가 필수값을 보내지 않은 경우와 구 자료/구 클라이언트의 호환 처리를 섞지 않는다.

검증은 세 곳에서 책임을 나눈다. 웹 폼은 누락을 즉시 표시하고, MCP inputSchema는 타입·필수 키·길이·형식을 도구 사용 전에 설명하며, 목적별 서버 저장은 이를 다시 검증해 HTTP/MCP 우회를 막는다. 검증 실패 시 해당 필드와 수정할 이유를 반환하고 원본·태그·완료 상태를 부분 저장하지 않는다. 같은 도메인의 검증 규칙을 공유하되 모든 변경을 처리하는 범용 검수 엔진은 만들지 않는다.

형식 검증으로 요약의 정확성까지 보장할 수는 없다. 제목 반복, 본문의 중요한 부정·조건 누락, AI 검토안을 사용자 결정으로 바꾸는 표현, 본문에 없는 사실은 스킬의 저장 전 내용 검토와 품질 평가로 다룬다. 저장마다 별도 LLM 검수 호출·점수 테이블·승인 상태를 추가하지 않는 안을 권장한다.

## Portfolio 스킬과 모든 기록 생성 경로의 동시 전환

실제 스킬 수정은 구현 단계의 필수 작업이다. 서버가 지원하기 전에 현재 설치 스킬에 새 파라미터 사용을 지시하지 않는다. 수정 대상은 저장소의 `plugins/portfolio/skills/portfolio` 원본이며 설치 캐시를 직접 고치지 않는다.

| 대상 | 필요한 변경 |
| --- | --- |
| `SKILL.md` | 기록 초안을 제목·요약·본문으로 제안하도록 연결하고, 구체적인 작성·검수 규칙은 활동 참고 문서로 안내 |
| `references/activities.md` | 공통 작성 규칙, 필수/선택/서버 생성값 구분, 저장 전 검토, 누락 오류 수정과 재조회 검증의 정본 |
| `references/knowledge-review.md` | 이론·뉴스·결정의 요약에 주제·핵심 결론·주요 조건을 담고 상세 근거는 본문에 보존. 검색 요약으로 후보를 고른 뒤 실제 본문을 읽기 |
| `references/cycle-review.md` 및 활동을 만드는 다른 참고 문서 | 해당 분야의 필요한 평가 요지·미확인 조건을 요약에 반영하고 공통 작성 규칙을 참조. 같은 규칙을 각 문서에 전문 복제하지 않음 |
| MCP schema·description·handler | 신규/수정/완료 결과의 제목·요약·본문 필드와 서버 검증을 일치시키고, nullable·생략·기본값·오류 설명을 제공 |
| 자동 금융·원칙·배분 기록 | 같은 저장 계약을 만족하는 제목·요약을 확인된 사실로 서버에서 생성. 사람이 필수 요약을 직접 입력해야만 금융 저장이 가능하도록 일괄 변경하지 않음 |

특히 `transition_general_task`를 빠뜨리지 않는다. 완료 기록의 요약은 실제 수행 결과를 받아야 하며 원래 할 일의 목적 요약을 그대로 복사해 완료 결과로 쓰지 않는다. 완료와 결과 기록을 한 트랜잭션으로 저장하고 필요한 결과가 누락되면 둘 다 저장하지 않는다. reopen/cancel에 수행 결과 필드를 강제하지 않는다. 결과 구조와 필수성은 완료 동작별로 확정한다.

저장 전 스킬 검토 순서는 다음을 제안한다.

1. 현재 schema와 실제 조회값에 따라 제목·요약·본문을 구성하고 필요한 태그/참조를 확인한다. 선택값이 없으면 빈 배열·null·생략의 계약을 지키며 내용을 꾸며 채우지 않는다.
2. 할 일 요약에 목적·대상·기대 결과가, 기록 요약에 핵심 결과·중요한 한계가 드러나는지 확인한다. 모든 기록에 무관한 재검토 조건이나 수치를 의무적으로 만들지 않는다.
3. 요약과 본문의 사실·부정·조건·판단 주체가 일치하는지 확인한다. 본문 수정으로 요약이 부정확해졌다면 같은 저장에서 요약을 보완한다. 스타일만 바뀐 본문에 요약 재작성을 강제하지 않는다.
4. 사용자의 저장 요청 또는 보여준 초안 동의 범위 안에서 한 번 저장한다. 구조화 도입이 매번 추가 승인 단계를 만드는 이유는 아니다. 검수 과정에서 새로운 결정이 필요할 때만 질문한다.
5. 저장 성공 후 상세를 재조회해 제목·요약·본문·선택한 태그/참조를 확인한다. 요약 때문에 성공한 완료·금융 변경을 반복 실행하지 않는다. 저장 성공과 색인 대기/실패를 구분한다.

신규 작성뿐 아니라 기존 기록 정정, 할 일 수정, 완료 기록, 자동 기록, 조회 응답과 에이전트 재조회까지 전환표로 추적한다. 호환 서버/DB → 소비 UI·MCP → 스킬/플러그인 공개의 배포 순서와 구 클라이언트 종료 조건을 정하고 각 단계의 실제 지원 상태를 확인한다.

## 스킬에 넣을 제목과 요약 작성 지침 초안

제목·요약은 사람이 목록에서 내용을 고르고 에이전트가 관련 자료를 검색하는 공통 설명이다. 상단만 임베딩하므로 나중에 찾을 핵심 주제·대상·중요 조건을 상단에 표현해야 한다. 아래 규칙은 구현 시 `references/activities.md`에 반영할 작성 지침 초안이다. 실제 검색 품질 개선은 평가로 확인하며 문체만으로 보장하지 않는다.

### 제목 작성

- 핵심 대상과 다루는 문제·행동·결과가 드러나는 구체적인 제목을 쓴다. 할 일은 `대상 + 할 작업`, 기록은 `대상/주제 + 확인한 결과나 판단`을 기본으로 하되 어색한 고정 문법을 강제하지 않는다.
- `오늘 조사`, `점검 완료`, `중요한 내용`, `결과 정리`처럼 다른 항목과 구별되지 않는 제목을 피한다. 무엇을 조사·점검했고 어떤 결과인지 드러낸다.
- 본문과 사용자의 표현에 근거한 이름을 쓴다. 필요한 경우 자산명과 티커, 전문용어와 익숙한 표현을 함께 쓰되 실제 동의 관계가 확인된 표현만 사용한다. 무관한 키워드·동의어 목록·태그 나열을 제목에 붙이지 않는다.
- 날짜·회차는 구분에 필요할 때만 포함하고 제목을 날짜로 대신하지 않는다. 같은 반복 작업도 완료 기록에서는 실제 결과 차이가 드러나게 작성한다. 새로운 사실이 없으면 변화 없음과 확인 범위를 정직하게 표현한다.

### 요약 작성

- 제목을 그대로 반복하지 않고 그 항목을 읽어야 하는 이유를 설명한다. 초기 작성 기준은 자연스러운 2~4문장으로 제안하며 단순한 기록은 한 문장으로 충분할 수 있다. 최종 글자 수 제한은 모델 입력 예산·모바일 가독성과 함께 확정한다. 형식을 채우기 위해 문장을 늘리지 않는다.
- 할 일은 무엇을 어떤 상황에서 확인/수행하고 어떤 결과를 남겨야 하는지 설명한다. 아직 수행하지 않은 작업을 완료한 것처럼 쓰지 않는다.
- 기록은 무엇을 확인했는지, 어떤 결과/판단이 나왔는지, 그 이유와 중요한 제한이 무엇인지 담는다. 이론은 적용 상황·주장·한계, 뉴스는 사건·대상·중요성, 결정은 선택·이유·재검토 조건 중 실제 자료에 있는 내용을 우선한다. 별도 분류 필드를 의무화하는 규칙은 아니다.
- 대화 없이 요약만 읽어도 이해되게 쓴다. `그것`, `위 내용`, `지난번과 같다`를 단독 설명으로 쓰지 않고 필요한 대상·주제·비교 기준을 명시한다.
- 검색할 만한 핵심 개념을 자연스러운 문장에 포함한다. 예를 들어 대출 만기와 현금 확보가 핵심이면 그 내용을 명시한다. 모든 가능한 질문을 끌어오거나 검색 노출을 위해 본문에 없는 연관 주제를 추가하지 않는다.
- 결론을 바꿀 수 있는 부정·조건·불확실성·판단 주체를 보존한다. `매수를 검토했으나 보류`를 `매수 결정`으로 줄이거나 AI 제안을 사용자 채택으로 바꾸지 않는다. 핵심 숫자·기준 시점은 항목을 구별하거나 판단을 이해하는 데 필요한 경우에만 넣는다.
- 자세한 절차·수치 표·출처 URL·긴 인용은 본문에 둔다. 요약에서는 근거의 요지만 표현한다. 본문에만 있는 세부 내용은 의미 검색으로 회수되지 않을 수 있으므로, 반드시 다시 찾을 핵심 조건이 빠졌는지 검토한다.

### 저장 전 검토와 품질 평가

스킬은 저장 전 제목·요약만 읽고 대상·주제·목적 또는 결과를 식별할 수 있는지, 본문에 비춰 중요한 부정·조건·미확인 범위가 빠지지 않았는지 확인한다. 그 다음 사용자가 나중에 할 법한 자연스러운 질문 1~2개를 떠올려 요약에 해당 의미가 실제로 담겼는지 검토한다. 이 질문을 별도 저장 필드로 만들거나 모든 저장마다 추가 임베딩 호출을 수행하지 않는다.

검증 집합에는 단순한 키워드 반복 질문뿐 아니라 자연어 바꿔 말하기, 같은 대상의 다른 주제, 같은 주제의 반대 결론, 계획과 완료 결과, 조건부 판단, 미확인 자료와 무관 질문을 포함한다. 작성 예시에서 그대로 복사한 질문만으로 성능을 판정하지 않는다. 검색 누락이 요약의 정보 누락인지 임베딩/순위 문제인지 구별해 기록한다. 검색을 위해 중요한 조건을 제거하거나 무관한 키워드를 늘리는 수정은 허용하지 않는다.

## 설계에서 확정할 항목

- 상단 필드의 최종 목록과 임베딩 allowlist. 최소안은 제목·요약이며 새 독립 결론/조건 필드의 필요성은 미확정이다.
- 요약의 형식·권장 길이·최대 길이와 신규 필수 권장안의 확정. 본문 필수성, 할 일의 긴 본문 지원과 기존 `trigger_text` 호환 방식, 완료 결과 파라미터의 구조.
- 요약 없는 자료의 검색 동작, 기존 자료 요약을 작성·검토·저장할 주체와 전환 순서.
- 본문 키워드 검색 유지 여부와 혼합 결과의 표시·발췌·순위 계약.
- 본문 수정 시 요약 확인 흐름과 자동 기록의 요약 생성 규칙. 별도 요약 이력/자동 생성 상태를 추가하기 전에 실제 소비 시나리오를 확인한다.
- 할 일·날짜별 기록·검색 결과의 모바일/PC 목록 시안, 필드별 표시 역할, 요약 없는 상태와 긴 요약 생략 정책. 검색 근거도 목록의 상단 전용 표시 계약을 따른다.
