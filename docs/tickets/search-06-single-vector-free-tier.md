## 목적과 범위

**목적은 무료 티어 안에서 할 일·기록 검색의 구현과 운영을 단순하게 만드는 것이다.** 짧은 제목·요약을 통째로 임베딩하고 항목 하나에 현재 벡터 하나만 관리한다. 모델 교체나 토큰 비용 감소 자체를 성과로 삼지 않고, 청크 때문에 생긴 저장·작업·검색 분기를 실제로 없애는 것을 핵심 성과로 삼는다.

#174는 입력을 제목·요약으로 바꿨지만 기존 900-byte 청크와 청크별 큐·벡터·집계를 유지했다. 사용자는 구현 단순화를 우선하고 무료 티어를 사용하며, 기존 제목 500자·요약 1,000자는 너무 길다고 밝혔다. 이번 티켓은 이를 반영한 후속 작업이며 사용자의 명시적 요청으로 구현에 진입했다.

첫 사용자 시나리오 S1: 할 일/기록의 제목·요약 저장 → 비동기 임베딩 하나 → 웹/OAuth 검색 → 상세 본문 읽기. 공통 기반은 이 시나리오의 저장·색인·검색에 필요한 만큼만 변경한다. 본문 키워드 검색, 목록 상단 전용 표시, 레거시 제목만 임베딩, 소유자/공유 권한은 #174 계약을 따른다.

## 구현 목표

2026-10-01 구현 계약: 사용자의 구현 요청과 공급자 실측을 반영하여 `llama-text-embed-v2`, dense 1,024차원, 제목 100/요약 300 Unicode 코드 포인트를 채택한다. UTF-8 저장/전송과 문자 수는 구별하며 DB `char_length`, 웹 `Array.from`, MCP JSON Schema 길이 기준을 맞춘다. 본문 필수·25,000자 계약은 유지한다. 새 작성·변경한 상단 필드에 새 상한을 적용하고, 기존 초과 필드가 그대로인 편집은 허용한다. 기존 원본/요약을 자동 절단하거나 재요약하지 않는다. 신규 자동 기록의 생성 요약만 300자로 제한한다.

임베딩 입력은 제목 + 줄바꿈 + 요약 전체이며 분할/절단하지 않는다. 새 입력은 최대 1,601 UTF-8 bytes다. 긴 기존 상단은 전체 입력이 1,800 bytes 이하이면 그대로 색인하고, 넘으면 키워드 검색과 원문 읽기를 유지하면서 `excluded_count`로 표시한다. 공개 byte-level tokenizer 근거와 실제 2,048토큰 한도에 여유를 두는 입력 예산이며 토큰 계수기/분할기를 추가하지 않는다. 빈 입력은 제외한다. 기존 필드를 고쳐 한도 안으로 만들면 다시 색인한다.

합성 calibration/evaluation으로 정한 초기 cosine 임계값은 `0.212384`다. E5의 0.8059를 재사용하지 않는다. pipeline `pinecone-llama-summary-v3`는 모델 변경 시 구 벡터·작업·검색 커서를 무효화한다. 파생 큐/벡터만 재생성하고 원본은 보존한다. 큐는 항목별 최신 작업 하나로 합치고, 기존 120초 visibility/최대 5회 재시도는 유지한다. 삭제 시 대기 작업도 제거하며 늦은 결과는 원본 잠금·소유자·현재 hash·작업 일치 검사로 거부한다. 월간 할당 초과/속도 제한은 무한 재시도하지 않으며 공급자 오류 시 검색은 기존 키워드 폴백을 유지한다.

- 입력은 제목과 요약을 정해진 순서/구분자로 결합한 원문이다. 본문·태그·연결 원문·자동 재요약을 넣지 않는다.
- 항목당 현재 벡터는 최대 하나, 최신 입력을 처리할 논리적 대기 작업도 하나다. 최신 변경은 기존 작업에 반영하고 변경 횟수만큼 큐를 누적하지 않는다.
- 청크 분할·겹침·문맥 복제·`chunk_no`·청크별 식별자/완료 수·최고 청크 점수 선택·청크 검색 결과 병합을 제거한다. `chunk_no=0`을 강제한 채 기존 구조를 영구 유지하는 것은 완료가 아니다.
- 큐와 worker는 기존 구조를 축소하여 재사용한다. 새 범용 작업 엔진, 모델 라우터, 이중 벡터 저장소, 이력/상태 테이블을 도입하지 않는다. 벡터 저장 위치를 공급자 쪽으로 옮기는 작업도 범위 밖이다.
- DB 검색, Edge index/search, 웹 HTTP·OAuth MCP가 같은 단일 벡터를 소비한다. 재색인 완료율은 대상 항목 중 현재 입력·모델에 맞는 벡터가 있는 항목 수로 계산한다.

## 무료 티어와 모델 선정 검토 이력

사용자 추가 의견: 기존 제목 500자·요약 1,000자는 너무 길게 느껴진다. **제안은 제목 최대 100자, 요약 최대 300자**이며 보통 제목 20~50자, 요약 1~3문장으로 작성한다. 상세 근거·절차·표·출처는 본문에 둔다. 당시에는 미확정 제안이었으며 현재는 위 구현 계약으로 확정했다. 문장 수는 작성 지침이며 서버의 의무 문장 수 규칙으로 만들지 않는다.

짧아진 입력을 기준으로 현재 E5를 먼저 측정했다. 아래 2026-10-01 실측에서 정규화 확장으로 한도를 넘는 합법 문자열이 발견돼, 단순한 문자 상한만으로 수용하기에는 Llama 계열이 더 유리한 후보가 됐다. 실제 공급자 확인과 품질 검증 전 모델을 확정하지 않는다. 입력 제한 확정 시 웹·MCP·서버·스킬을 함께 맞추고 기존 긴 상단 자료를 자동 절단하지 않는다. 기존 초과 자료의 편집/재색인 처리 계약도 모델 선정 전에 확정한다.

무료 할당은 공개 정책이며 실제 계정의 플랜·남은 할당량을 확인한 결과가 아니다. 한시적 유료 플랜 체험 크레딧을 무료 티어로 간주하지 않는다. 구현 시 정책과 계정별 모델 접근·월간 할당·요청률을 다시 확인한다. 새 유료 공급자나 플랜 업그레이드를 전제하지 않는다.

모델 확정 전에 다음 근거를 이 티켓에 남긴다.

1. 실제 inference API의 모델명·입력 한도·차원 옵션·무료 사용 가능 여부를 확인한다. 현재 저장 차원과 호환되는 출력을 우선 검증하되 차원이 같아도 다른 모델의 벡터를 섞지 않는다.
2. 글자 수와 토큰 수를 동일하게 취급하지 않는다. 확정할 새 상한(제안 100자+300자)의 한국어·영문·혼합·이모지·연속 기호·URL 경계 입력을 tokenizer와 실제 `truncate=NONE` 호출로 확인한다. 기존 상한으로 저장된 긴 자료의 처리도 별도로 확인한다. 샘플 통과만으로 모든 합법 입력의 수용을 보장했다고 주장하지 않는다.

### 중요한 한계와 설계 권고

1. E5는 일반 한국어 예시에서 여유가 있지만 **100자+300자만 제한해서 모든 입력을 보장할 수 없다**. U+FDFA 정규화 확장이 반례다. E5를 유지하려면 정확한 모델 토큰 수 검증/초과 정책을 추가해야 하므로 구현 복잡도와 비교한다.
2. 정규화로 입력을 확장하지 않는 byte-level tokenizer라면 Unicode 코드 포인트 하나는 UTF-8 최대 4바이트다. 100+300개와 구분자 LF는 최대 1,601바이트이며 byte 합치기는 토큰 수를 늘리지 않는다. 따라서 공급자의 정확한 토크나이저와 접두/특수 토큰 예산을 확인하면, 2,048 한도 안에서 별도 거대 토크나이저를 앱에 넣지 않고 상한을 보장할 가능성이 있다. **이것은 바이트=토큰이라는 뜻이 아니라 보수적인 최대치 논증이다.** 실제 공급자 설정 확인 전 보장으로 채택하지 않는다.
3. 글자 수 기준은 단순성과 DB 일치를 위해 Unicode 코드 포인트를 제안한다. 브라우저 `.length`/`maxlength`의 UTF-16 단위와 서버/MCP 검증을 맞춰야 한다. 일반 완성형 한글은 한 글자=한 코드 포인트이나 조합 이모지는 여러 개다. 사용자에게 보이는 grapheme 수를 채택하면 위 4바이트 상한이 성립하지 않으므로 별도 크기 제한이 필요하다. 이 선택은 위 구현 계약에서 코드 포인트로 확정했다.
4. NVIDIA의 과거 공개 모델 주소가 현재 `llama-nemotron-embed-1b-v2`로 리다이렉트되고 최신 모델 카드는 8,192토큰을 설명한다. Pinecone 과거 공식 소개는 2,048이다. 따라서 위 NVIDIA 수치를 Pinecone `llama-text-embed-v2`의 실제 측정값으로 표시하거나 Pinecone 한도가 8,192로 늘었다고 추정하지 않는다. API model metadata와 합성 입력 실제 응답으로 동일성을 확인해야 한다.
5. 무료 Starter의 공개 포함량은 두 후보 모두 월 5M 토큰이다. 측정한 일반 상한 입력과 질의에 임의의 월간 가정(문서 신규/수정 1,000건, 질의 3,000회, 최초 재색인 200건)을 적용하면 E5 약 312,000, NVIDIA 공개 tokenizer 약 367,200토큰이다. 재시도·다른 앱 사용·공급자 토큰 집계 차이는 제외한 예시이며 계정 잔여량 또는 서비스 성공 보장이 아니다.

이 초기 조사 당시에는 실행 프로세스에 키가 없어 공급자 평가는 미실행이었다. 이후 기존 CLI 로그인으로 키를 발급하고 실제 무료 계정/모델/길이/품질 검증을 완료했다(상단 실행 기록). 검토 결과는 **단일 벡터 구조와 짧은 상단을 유지하고, 앱에 추가 토큰 검증 복잡도를 최소화할 수 있는 Llama 후보를 다음 실제 공급자 검증 대상으로 우선 검토**하는 것이다. 길이/품질/무료 티어 게이트를 통과하기 전 모델 교체와 100/300 제한을 구현하지 않는다.

### 남은 적용 경계

로컬 구현·자동 검증은 완료했으며 일반 로컬 functions serve는 `.env.search`를 읽어 실행 중이다. 실제 Pinecone를 사용한 S1과 archive 후 재개 smoke도 통과했다. 운영 적용은 dispatcher 중지/구 worker 배제 → 백업/전진 DB migration → 새 index/search/MCP Edge → 웹/제품 플러그인 → 재색인 coverage 순서다. 전환 중 의미 검색을 비활성화하고 키워드 검색을 사용한다. 모델 벡터를 섞어 롤백하지 않는다. 실제 ChatGPT 연결과 모바일 확인은 별도 배포 후 검증이다.

공급자 할당량/요청률 복구 후에는 운영자가 같은 private `activity_search_queue_text` helper로 현재 입력이 eligible이고 현재 hash/model 벡터가 없는 항목만 재큐잉한다. 정상 벡터는 다시 요청하지 않으며 새로운 원본·요약을 만들지 않는다. 로컬 합성 smoke는 pending 작업 archive → coverage missing=1 → 원본 상단 그대로 재큐잉 → 실제 worker 저장/검색으로 이 재개를 확인했다. 이는 무료 월 할당량 자체를 실제로 소진한 검사가 아니다.
