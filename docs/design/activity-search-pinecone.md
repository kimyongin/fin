# 활동 검색 임베딩의 Pinecone 전환

2026-09-27 Astra 방식 선정·설계 완료 · 2026-09-28 Sol 로컬 구현/실모델 검증 · 운영 적용 전.
소유 티켓: [#161](../tickets/search-01-korean-hybrid.md). 상위 계약은 [활동 검색](./activity-context-search.md), 응답·표시는 [#165](../tickets/search-05-search-evidence.md)를 따른다.

## 결정과 범위

사용자는 Supabase 내장 모델로 처리하던 임베딩을 Pinecone으로 바꾸도록 요청했다. `multilingual-e5-large`를 이번 구현 모델로 정하고, 한국어 실제 품질 통과를 운영 활성화 조건으로 둔다. 다른 모델로 자동 전환하거나 품질 미달을 숨기지 않는다. Sol이 아래 기준으로 평가·구현하고 결과를 #161에 기록한다. 수치 측정과 확정된 절차에 따른 임계값 산출은 구현 검증이며 추가 모델 전환을 요구하지 않는다.

Pinecone Inference에서 벡터를 생성하고 기존 Supabase Postgres/pgvector에서 저장·권한 검증·필터·검색·페이지 처리를 수행한다. 사용자 원본은 기존 `activity_events`와 `portfolio_tasks`다. Pinecone 벡터 DB 인덱스, 두 번째 검색 저장소, 공급자 선택 UI, 범용 임베딩 프레임워크는 만들지 않는다. CLI의 `Default` 프로젝트 관리 키로 합성 입력의 모델 호출을 확인했다. 앱 서버용 API 키 설정과 실제 요금제/잔여량은 아직 확인하지 않았다.

## 검토에서 확인한 문제

| --- | --- |

| 구 큐 메시지·진행 중 worker가 모델을 식별하지 않음 | 메시지·완료 쓰기·검색 입력에서 모델을 확인하고 구 결과 저장을 거절 |

현재 기준은 티커 필터를 쓰는 `app_search_activities_ranked_ticker`다. 과거 `instrument_id` 전용 검색을 최신 원본으로 덮어쓰지 않는다. #162 연결 확장과 #163 종목 자동완성은 이번 교체에 포함하지 않는다.

## 공급자·키·외부 전송

- 모델은 `multilingual-e5-large`, 출력은 1024차원 dense vector, 거리는 cosine이다. 차원 자르기·0 채우기·구 벡터 변환을 하지 않고 원문에서 다시 생성한다.
- Edge에서 `POST https://api.pinecone.io/embed`를 호출한다. 공식 `2025-10` API 계약을 고정하고 `Api-Key`와 버전 헤더를 사용한다. 현재 내장 `fetch`로 충분하며 CLI를 서버에서 실행하지 않는다.
- 문서 청크는 `input_type=passage`, 질문은 `input_type=query`다. API가 접두 처리를 맡으므로 텍스트에 `query:`/`passage:`를 중복 추가하지 않는다. `truncate=NONE`으로 내용의 조용한 유실을 막는다.
- 모델 응답의 이름·dense 유형·입력 대비 결과 수·1024개 유한 숫자·0이 아닌 벡터를 검증한다. 잘못된 응답은 저장하거나 정상 검색으로 표시하지 않는다.
- `PINECONE_API_KEY`는 서버 비밀이다. 로컬 Git 제외 환경 파일과 승인된 배포 대상의 Edge secret에서만 사용한다. CLI 사용자 로그인 토큰을 앱 인증에 재사용하지 않는다. 구현 시 연결된 프로젝트의 사용 가능한 최소 권한 API 키를 준비하며 값은 채팅·로그·티켓·브라우저 번들에 출력하지 않는다.
- 외부 전송 대상은 검색어, 기록 제목/본문, 할 일 제목/설명의 색인 청크다. 사용자 ID·이메일·태그·관계 ID·계좌/보유 테이블·금융 snapshot·인증정보·내부 실행 JSON을 추가하지 않는다. 본문에 사용자가 쓴 개인/금융 내용이 있으면 그 내용도 전송되므로 이를 '개인정보 전송 없음'으로 설명하지 않는다. 공급자의 보관 정책까지 Supabase 내부 처리와 같다고 가정하지 않는다.
- 공식 요금표는 Starter의 이 모델에 월 500만 토큰을 제시한다. 문서 재색인과 질문이 모두 사용량에 포함되고 Supabase 함수/DB 비용은 별도다. 구현 시작 시 실제 플랜과 모델 접근을 확인한다. 이번 요청은 유료 업그레이드·최소 결제·추가 크레딧 구매 승인이 아니다. Starter를 사용할 수 없으면 활성화 전 비용 조건을 사용자에게 설명한다.
- 요청마다 Pinecone `usage.total_tokens`와 상태/지연을 내용 없는 집계로 확인할 수 있게 한다. 기존 함수 로그·공급자 대시보드로 충분하며 사용량 전용 DB 테이블은 추가하지 않는다. 백필 전 합성 샘플 토큰 수와 대상 청크 수로 예상 사용량을 기록하고 잔여량이 확인되지 않으면 무제한이라고 추정하지 않는다.

## 원문·청크·색인 계약

### 최종 결정: 문맥을 보존한 원문 분할

이번 구현은 **B: 제목·소제목 문맥을 포함하는 문단/문장 단위 원문 임베딩**으로 확정한다. 짧은 글은 하나로, 긴 글은 의미가 이어지는 범위로 묶는다. 요약 생성·요약 저장·요약 벡터·검색 결과 재정렬 모델은 이번 구현에 넣지 않는다. 이는 아래 사용 시나리오와 운영 비용을 비교한 설계 결정이며 실측 품질 우위를 주장하는 결정이 아니다. Sol은 네 후보를 모두 구현하는 대신 이 확정안을 구현·검증한다.

검색 시나리오는 (1) 투자 심리에 관한 글처럼 주제를 찾기, (2) 매도 조건·반례·숫자처럼 세부 근거를 찾기, (3) 찾아낸 기록을 실제 원문과 함께 읽기다. 세 가지를 모두 제공해야 한다.

| 대안 | 판단 | 결정 근거 |
| --- | --- | --- |
| A 고정 400자 분할 | 미채택 | 숫자 위치만으로 문장이 끊기고 제목·소제목 맥락이 사라짐. 전체 길이 제한만 제거해서는 경계 문제를 해결하지 못함 |
| B 문맥을 보존한 원문 분할 | 채택 | 제목/소제목으로 주제를 보완하고 원문 조건·예외를 보존. 별도 생성 모델 없이 수정과 재색인을 한 흐름으로 관리 가능 |
| C 요약 하나를 통째로 임베딩 | 미채택 | 주제 탐색에는 유용할 수 있지만 요약에 빠진 세부 근거는 의미 검색으로 복구하기 어려움. 요약 생성·검증·재생성 비용도 발생 |
| D 요약+본문 | 이번에는 미채택 | 주제 탐색을 보완할 가능성이 있으나 두 종류의 파생 자료와 순위 결합·갱신 실패 처리가 필요. 현재 시나리오에서 그 추가 비용을 정당화할 근거가 없음 |
| LLM으로 청크별 문맥 생성 / 의미 유사도 기반 분할 | 이번에는 미채택 | 생성 또는 추가 임베딩 호출과 갱신 경로가 늘어남. 문서 구조를 이용하는 B를 검증한 뒤 구체적인 실패 사례가 있을 때 재설계 |

제목이 모호하거나 글 전체를 추론해야 알 수 있는 주제는 B의 한계로 기록한다. 구현 검증에서 주제 질문이 인수 기준을 못 넘으면 운영 활성화를 멈추고 요약 보강을 포함해 재설계한다. 실패할 가능성을 이유로 네 방식을 선행 구현하지 않는다. 검색 관련성이 높다는 것이 본문의 주장을 지지한다는 뜻은 아니며 반대 주장도 원문으로 읽어야 한다.

### 분할과 입력 구성

분할은 DB의 목적별 순수 함수 하나가 담당한다. enqueue·worker 원문 조회·coverage·품질 평가가 같은 결과를 소비하고 Edge에서 다시 다른 방식으로 나누지 않는다. 새 범용 분할 프레임워크나 청크 정본 테이블을 도입하지 않는다.

1. 원문은 현재 제목과 본문/설명을 줄바꿈으로 합치고 바깥 공백만 정리한다. 내부 줄바꿈·순서·숫자·부정 표현은 보존한다. 제목 500자·본문 25,000자 등 허용 입력 전체를 처리하고 12,000자/30개 청크 제한을 제거한다. 제목 자체도 원문 범위에 포함해 긴 제목의 뒤쪽이 누락되지 않게 한다.
2. 빈 줄을 문단 경계로 삼고 Markdown ATX 제목(`#`~`######` 다음 공백)을 절 경계로 삼는다. fenced code 안의 `#`는 제목으로 해석하지 않는다. 소제목이 바뀌면 묶기를 끝낸다. 같은 절의 짧은 문단/목록 행은 입력 예산 안에서 순서대로 묶는다.
3. 예산을 넘는 문단은 문장 끝(`.`, `?`, `!`, `。`, `？`, `！` 뒤 공백/줄끝)을 우선해 나눈다. 소수점이나 URL 내부 마침표에서는 나누지 않는다. 그래도 긴 문장/표 행/코드는 공백, 마지막으로 Unicode 문자 경계 순서로 나눈다. 완전한 한국어 문장 분석기를 도입하는 계약은 아니며 구두점 없는 긴 글도 손실 없이 처리한다.
4. 임베딩 입력은 `제목: {제목 문맥}\n소제목: {현재 소제목 문맥}\n{원문 발췌}`다. 없는 문맥 줄은 생략한다. 반복 문맥은 각각 UTF-8 120바이트 이내의 원문 앞부분으로 한정하고 문자 중간을 자르지 않는다. 생략된 제목/소제목의 나머지는 원문 발췌 쪽에 그대로 포함된다. 생성한 해석이나 요약은 붙이지 않는다.
5. 최종 입력 전체(라벨·문맥·중복 문장 포함)의 초기 최대 크기는 **UTF-8 900바이트**다. 문자 수를 토큰 수로 환산하지 않고 SQL에서 동일하게 계산 가능한 보수적인 예산을 사용한다. 이는 900토큰 또는 품질 최적값이라는 주장이 아니다. Pinecone의 호스팅 한도 및 실제 한국어/영문/이모지/URL 입력으로 `truncate=NONE` 호출이 통과하는지 구현 게이트에서 확인한다. 거절되는 합법 입력이 있으면 조용히 잘라 저장하지 않고 실패로 남기며 크기 계약을 재검토한다.
6. 같은 절에서 이어지는 청크에는 직전 청크의 마지막 완결 문장 하나를 **120바이트 이하일 때만** 겹친다. 긴 문장을 중간에서 잘라 겹치거나 다른 절/코드/표로 넘겨 붙이지 않는다. 겹친 문장 때문에 새 본문이 한 글자도 들어가지 못하면 겹침을 생략한다. 각 청크는 반드시 새 원문 범위를 포함하고 번호는 0부터 연속한다.
7. 전체가 예산에 들어오는 짧은 글은 원문 전체 한 건만 임베딩한다. 제목이 이미 발췌 안에 있으면 같은 제목을 앞에 중복하지 않는다. 빈 원문은 청크 0개다.

900/120바이트는 이 설계에서 선택한 초기 처리 규칙이다. 이는 한국어 수백 자 수준의 내용을 묶으면서 반복 문맥과 입력 한도를 함께 관리하기 위한 보수적 절충이다. 품질 미달 시 보고할 항목이며 구현자가 네 후보 탐색이나 임의 크기 변경으로 설계를 대신하지 않는다. 변경이 필요하면 근거와 새 처리 식별자를 설계에 기록한다.

분할 결과는 `chunk_no, excerpt, embedding_input`을 반환한다. `excerpt`는 원문에서 연속된 구간이고 겹침이 있다면 바로 앞 문장까지 포함한다. 공급자에게는 `embedding_input`만 보내고 화면에는 `excerpt`를 사용한다. 내부 표/코드 형식을 미화하거나 소제목을 만들어내지 않는다. 이 함수의 호출 결과를 이어서 대조해 중복을 제외한 원문 전체가 보존됨을 검증한다.

### 저장·갱신·완료 판정

기존 원본 테이블과 `activity_search_vectors`를 유지한다. 원본별/청크별 PK, `excerpt`, 전체 원문 해시, 모델, 벡터, 처리 시각이면 충분하다. 문맥이 붙은 입력은 원문과 순수 분할 함수로 재구성하고 별도로 저장하지 않는다. 새 요약 컬럼·청크 테이블·상태 테이블·공개 API는 만들지 않는다. 1024차원 컬럼·모델 제약과 관련 함수는 새 migration에서 변경한다.

저장/수정 트랜잭션은 기존 벡터를 무효화하고 새 전체 해시·모델의 실제 분할 결과만 기존 큐에 넣는다. 제목·소제목만 바뀌어도 반복 문맥이 달라지므로 해당 원본 전체를 재색인한다. 후반부만 수정한 경우도 전체 해시가 바뀐다. 부분 재색인 최적화는 추가하지 않는다.

coverage는 순수 분할 함수가 내놓은 모든 청크 번호에 현재 모델·전체 해시의 유효 벡터가 존재하는지 확인한다. 길이/400이나 단순 벡터 개수만으로 완료를 추정하지 않는다. 실패 보관·마지막 청크 누락·일부 성공은 pending으로 남고 현재의 준비된 청크만 검색에 사용한다. 빈 원문은 필요한 청크가 없으므로 완료다. 삭제 시 벡터를 제거하고 남은 큐 메시지는 원본 없음으로 폐기한다. 권한은 매번 원본에서 확인한다.

해시는 `pinecone-e5-context-v1` 처리 규칙 식별자와 전체 원문으로 계산한다. 이 식별자는 이번 모델·문서 입력 목적·분할 규칙에 대응하는 코드 상수이며 사용자별 설정/버전 저장소가 아니다. 이후 처리 규칙 변경은 새 식별자와 재색인을 요구한다. 모델 이름은 기존 `model` 필드에 보관한다.

문자 수는 토큰 상한을 보장하지 않는다. 비교 검증에서 Pinecone 모델 메타데이터의 실제 입력 한도와 한국어·영문·이모지·긴 URL 입력을 확인한다. 길이 거절은 성공으로 ack하지 않는다. 자동 잘림으로 통과시키지 않고 입력 구성 계약을 보완한다. 질의는 기존 최대 500자를 보존하고, 모델 한도를 넘으면 키워드 fallback을 반환한다.

기존 원본별 벡터 PK와 재시도 큐를 유지한다. 메시지에는 모델을 포함하며, worker는 모델·현재 원문 해시·청크·소유자를 확인한 뒤 임베딩한다. 완료 RPC는 실제 모델 인자를 필수로 받아 다시 확인하고 원본 수정과 직렬화한 후 벡터 저장/ack를 원자적으로 처리한다. 동일 작업의 재전달은 같은 현재 청크를 덮어쓰는 것으로 끝난다. 다른 모델·삭제된 원본·구 해시 작업은 벡터를 쓰지 않고 폐기한다. 오래된 함수 호출이 새 모델 이름을 임의로 붙여 저장할 수 없도록 구 완료 RPC 서명은 퇴역한다.

## 검색·실패·페이지 계약

- 검색 요청은 전체 질문을 한 번 임베딩하고 현재 모델/해시의 본문 벡터를 비교한다. 같은 원본은 최고 코사인 청크 하나로 대표하며 동점은 작은 청크 번호를 선택한다. 제목/단어 일치가 기존 순서대로 우선하고 새 RRF·요약 경로·reranker를 추가하지 않는다. 점수는 관련성 신호이며 정답/찬성 확률이 아니다.
- 결과에는 원본 ID·제목·날짜와 대표 청크의 원문 발췌를 반환한다. 추가한 제목/소제목 라벨을 원문 인용처럼 섞지 않는다. 상세 보기와 MCP의 기존 원본 조회로 본문 전체를 읽을 수 있고 에이전트는 조건·예외를 판단하기 전에 원문을 확인한다. 별도 이웃 청크 조회 API를 만들지 않는다.
- 기존 검색어 없는 탐색, 제목 정확/접두/부분 일치 우선순위, 티커/태그/기간/상태 필터, 원본별 최고 청크 점수와 중복 제거를 유지한다. 권한 확인과 필터는 순위·페이지 제한보다 먼저 적용한다.
- 새 ranked RPC는 질의 벡터와 모델 식별을 함께 검증한다. 모델·차원이 다른 벡터를 비교하지 않는다. 키워드 호출은 벡터/모델 없이 허용한다. 함수 인자의 `vector(384)`/`vector(1024)` 표기만으로 서로 다른 함수 서명이나 런타임 검증이 보장된다고 가정하지 말고 명시적으로 검사한다.
- 같은 `activity_search_vectors`를 읽는 구 비티커 ranked RPC도 함께 점검한다. 구 모델 벡터를 받으면 새 검색을 요구하는 오류로 거절하고 벡터 없는 기존 호출은 유지한다. 최신 웹/OAuth가 그 구 함수로 되돌아가지 않도록 검증한다. 별도 legacy `activity_embeddings` 테이블의 정리는 이번 모델 전환 범위에 넣지 않는다.
- DB의 채택 기준과 `matched_by`, `semantic_threshold`는 같은 보정값을 사용한다. 순수 의미 결과의 기존 점수순 rank 계산과 단어 우선순위는 유지한다. 모델·분할 식별자·임계값을 커서 fingerprint에 포함하여 구 페이지를 명확히 거절한다.
- Pinecone 호출은 8초, 기존 검색 worker 왕복은 10초 이내로 제한한다. 질의 요청 안에서 공급자 재시도나 밀린 문서 색인을 실행하지 않는다. 초기 호출의 timeout/401/403/429/5xx/잘못된 응답은 기존 `embedding_timeout` 또는 `embedding_unavailable` 키워드 fallback으로 처리한다. hybrid 후속 페이지 실패는 재시도/새 검색 오류이며 키워드 페이지를 이어 붙이지 않는다.
- 색인 실패는 기존 120초 visibility/최대 5회 전달/실패 보관 정책을 사용한다. 공급자 오류 본문에는 입력이 포함될 수 있으므로 HTTP 상태·제한된 오류 분류만 로그에 남긴다. 장기 한도·키 오류 후에는 운영자가 원인을 해결하고 현재 원문/모델의 미색인 청크만 다시 큐에 넣는다. 새 무한 재시도 시스템을 만들지 않는다.
- coverage는 현재 모델·처리 해시·분할 결과의 실제 누락을 센다. 큐가 비었어도 실패 보관/미색인 원본이 있으면 complete가 아니다. 파생 벡터·큐에 authenticated 직접 읽기/쓰기 권한을 열지 않는다. 기존 공유 권한을 유지하고 권한 없는 원본·개수·발췌는 반환하지 않는다.
- 배포·복구용 `ACTIVITY_SEARCH_SEMANTIC_ENABLED`는 질의 임베딩 활성화만 제어한다. 명시적으로 true일 때만 켜고 false/미설정이면 외부 질의 호출 없이 기존 ranked 키워드 경로로 간다. 이 경우 `embedding_unavailable`, `index_status=not_checked`를 사용하고 CPU/한도/색인 대기라고 추측하지 않는다. 기존 hybrid 커서는 이 상태에서도 새 검색을 요구하며 키워드로 이어 붙이지 않는다. 색인 worker 실행은 기존 cron의 pause/resume으로 제어한다.
- #165의 화면은 서버 모델명을 사용하고 `gte-small` 기본값과 영어 전용 모델에 근거한 고정 한국어 경고를 제거한다. 검색 누락 가능성·점수 비확률성·부분 색인/오류 설명은 유지한다. MCP 설명/가이드도 같은 의미로 갱신한다. 기존 secondary/meta 스타일과 상세 복귀·필터 범위를 유지한다.

## 품질·검증 게이트

구현할 대상은 확정안 B 하나다. 네 방식의 비교 실험이나 요약 모델 확보를 구현 선행 작업으로 요구하지 않는다. 주제 질문·세부 사실/조건·부정/예외·여러 주제가 섞인 문서·대명사/문장 경계·후반부 근거를 각각 최소 4개씩, 총 24개 이상의 검증 질문으로 고정하고 별도 무관 질문 6개를 둔다. 보정 집합과 검증 집합은 분리한다. 제목이 모호한 글, 짧은 글, 비슷한 주장의 방해 문서를 포함한다.

원본 단위 Hit@5(기대 원본이 하나 이상 채택된 질문 비율)·Recall@5(질문별 관련 원본 회수율)·nDCG@5와 유형별 적중, 무관 결과 수, 원문 근거 존재 여부, 벡터 수·색인/수정 토큰·처리 시간·실패 경로를 기록한다. 인수 기준은 Hit@5 전체 80% 이상(24개면 최소 20개), 유형별 4개 중 최소 3개, 지정 후반부/조건·예외/경계 사례 전부 통과, 무관 질문 6개 의미 결과 0건이다. 작은 합성 집합의 통과를 모든 실제 질문에 대한 보장으로 설명하지 않는다.

색인 비용은 실제 청크 입력 토큰 합계와 재색인 빈도로 계산한다. 제목/소제목 반복과 제한된 겹침도 비용에 포함한다. 별도 요약 생성 비용은 없다. 기존 방식보다 청크 수가 줄어든다고 단정하지 않으며 전체 원문 확장으로 늘어날 수 있음을 기록한다.

임계값 숫자는 실측 없이 정하지 않는다. 아래 산출 규칙을 확정해 Sol이 구현 검증에서 재현 가능한 숫자를 기록하도록 한다. 사용자 원문을 fixture나 평가 출력에 복제하지 않는다.

1. 기존 12개 질문/문서를 보정 집합으로 유지하고 금융 주제의 유사하지만 정답이 아닌 방해 문서·무관 질문을 추가한다. 별도로 위 24개 이상의 검증 질문과 6개 무관 질문을 모델 결과를 보기 전에 고정한다. 검증 corpus는 최소 30개 원본이고 한국어 바꿔 말하기, 영문/티커 혼합, 짧은 질문, 청크 경계, 12,000자 뒤 및 허용 본문 끝부분의 유일한 근거를 포함한다.
2. 실제 문서와 질의의 입력 목적을 분리하고 DB와 같은 코사인·원본별 최고 청크 점수로 평가한다. 보정 집합의 무관 질문 최고 점수보다 높은 후보 중 기대 자료의 top-5 적중과 채택을 가장 많이 유지하는 임계값을 선택한다. 선택값·보정 집합을 고정한 뒤 검증 집합을 한 번 평가한다. 검증 문항에 맞춰 반복 조정하지 않는다.
3. 검증의 기대 자료가 임계값 이상이면서 상위 5개에 드는 비율은 80% 이상(24개면 최소 20개), 무관 질문 6개는 의미 결과 0건이어야 한다. 후반부/청크 경계 근거의 지정 사례와 제목 정확 검색·명시적 티커 필터는 전부 통과해야 한다. 임계값 전 top-5만 좋거나 keyword가 맞힌 것을 의미 검색 성공으로 세지 않는다.
4. 정상·실패·재시도·구 작업 경쟁·모델/차원 오류·구 커서·수정/삭제·본인/친구/타인 권한·미색인 coverage를 DB와 실제 Edge HTTP/OAuth에서 검증한다. `npm test`, `npm run check:edge`, `npm run check:workflow-guides`, `npm run check:encoding`, build 및 해당 DB/E2E 게이트를 적용한다. 일반 로컬 DB를 초기화하지 않고 격리 E2E만 그 실행기가 reset한다.
   - 정리된 제목+본문의 길이 0/399/400/401/11,999/12,000/12,001자와 제목 500자·본문 25,000자의 허용 최대 입력에서 선택한 방식의 예상 항목 수와 후반부 처리 여부를 확인한다. 본문 청크 방식은 한국어·이모지에서 문자 경계와 원문 범위의 빠짐없음도 확인한다.
   - 마지막 청크가 실패/누락되면 색인 완료로 표시하지 않는다. 12,000자 이후만 수정해도 해시가 바뀌고 구 작업 결과가 거절되어야 한다. 후반부만 근거인 검색은 원본 한 건으로 반환하고 기존 긴 기록도 재색인 후 같은 조건을 통과해야 한다.
5. 실제 공급자 사용량과 최초 호출 지연을 별도로 기록하고 반복 검색 최소 30회의 p50/p95·오류/fallback 횟수를 기록한다. 수치로 관측한 범위만 주장한다. 360/390/768/1024/1440px와 200% 확대에서 긴 모델명·부분 색인·fallback·빈 결과·상세 복귀를 확인하고 미검증 화면은 공개한다.

모델 접근 실패나 품질 미달이면 키워드 검색을 유지하고 운영 의미 검색을 켜지 않는다. 그 결과를 가지고 모델/분할/채택 방식의 변경을 Astra에서 검토한다. 낮은 점수를 이유로 0.96을 임의의 다른 상수로 치환하거나 무관 결과를 허용해 게이트를 통과시키지 않는다.

2026-09-28 사용자 예외: 품질 미달과 기본 OFF 상태를 설명받은 뒤 사용자가 의미 검색 활성화와 운영 배포를 직접 요청했다. 이 배포는 품질 통과로 표시하지 않으며 합성 검증의 후반부 누락 1건과 무관 결과 1건을 #161에 유지한다. 이후 검색 기준 변경은 Astra 설계 검토를 따른다.

## 전환과 복구

구/신 모델 이중 저장 없이 검색 파생 자료를 한 번 재생성한다. 짧은 키워드 전용 구간을 허용하고 원본/권한/금융 데이터는 보존한다. 새 `vector(1024)` 컬럼과 HNSW 인덱스를 만들 수 있지만 최종 구조에는 현재 단일 벡터 컬럼/색인만 남긴다. 기존 migration을 수정하지 않는다.

1. Sol이 로컬 구현과 품질 게이트를 끝내고 정확한 commit·대상·키 설정·예상 사용량·원본 수/청크 수·복구 명령을 배포 기록에 준비한다. 운영 적용은 기존 별도 배포 승인 범위를 따른다.
2. 승인된 대상에서 `activity-search-index` cron만 멈추고 전송 중 worker를 확인한다. 새 HTTP/OAuth 검색 코드를 질의 의미 검색 OFF 상태로 먼저 적용하여 벡터 없는 ranked 호출과 키워드 커서가 구 DB에서도 정상임을 확인한다. 이 호환성은 로컬에서 먼저 검증한다.
3. 새 migration 하나의 트랜잭션에서 검색 원본 쓰기와 충돌을 제어하여 구 큐/벡터를 정리하고 1024차원·모델 제약·문맥 분할/해시·완료 RPC·검색/coverage를 전환한 뒤 현재 원본을 재큐잉한다. 원본을 지우지 않는다. 구 완료 서명과 입력 모델 없는 의미 호출이 새 벡터를 오염시키지 못하게 한다. 트랜잭션 중/직후 원본 수정도 빠짐없이 새 큐를 만든다.
4. 새 worker와 서버 비밀을 확인하고 cron을 재개한다. 재색인 완료는 큐/실패 보관 수와 현재 원본 coverage를 함께 확인한다. 운영 검증은 승인된 테스트 계정의 합성 자료로 수행하고 사용자 본문을 로그에 남기지 않는다.
5. 실제 HTTP/OAuth 결과·원본 수 보존·공유 격리·coverage를 확인한 뒤 의미 검색 ON 및 웹 표시를 공개한다. 이후 수정/삭제/재검색도 확인하고 운영 배포와 실제 ChatGPT 검증을 각각 기록한다.

실패 시 우선 질의 의미 검색을 OFF로 돌려 키워드 검색을 제공하고 문제 worker의 cron을 멈춘다. 원본은 계속 저장할 수 있고 큐가 새 작업을 보관한다. 원인을 해결한 뒤 현재 해시의 누락만 재큐잉한다. 새 DB 위에 구 384차원 worker만 되돌리는 복구는 금지한다. gte-small 복귀가 필요하면 별도 역방향 파생 색인 migration과 재생성이 필요하므로 즉시 복구 경로는 키워드 전용이다.

## Sol 구현 인계

방식 선정과 저장·갱신·검색·완료 판정 설계는 완료했다. 다음 단계는 Sol 선택과 명시적 구현 요청 후 확정안 B를 구현하고 품질을 검증하는 것이다. 실측 임계값 보정은 구현 검증에 속하지만 색인 구조 선택을 대신하지 않는다. 후속 구현 파일은 `_shared/search-embedding.ts`, `activity-search-index`, `_shared/activity-search.ts`, 최신 티커 검색 RPC/coverage와 큐 관련 incremental migration, 품질 평가 스크립트, 검색 테스트, `ActionTimeline.jsx`의 설명 및 MCP 설명/가이드다. 실제 DDL이 바뀔 때 스키마 OVERVIEW를 갱신한다.

첫 작업은 API 키/Starter 접근 확인과 합성 입력으로 모델·차원·입력 목적·토큰 사용량을 확인하는 것이다. 위 품질 산출 절차까지 완료한 후 확정된 임계값을 DB에 반영한다. API 키 부재와 품질 미측정은 구현 단계의 검증 작업이며 지금 실서비스 성공으로 표시하지 않는다. 설계 변경 없이 해결할 수 있는 함수 이름·테스트 배치·오류 래핑은 Sol이 결정한다.

설계 당시에는 코드·DB·키·Pinecone 리소스를 변경하거나 모델을 실행하지 않았다. 2026-09-28 Sol 로컬 구현에서는 확정안의 DB/Edge/UI/MCP 계약을 연결했고 실제 Pinecone 합성 평가에서 24문항 중 23문항과 무관 질문 6문항 중 5문항만 통과했다. 후반부 지정 사례도 1건 실패했다. 자세한 검증/미검증 기록은 #161을 따른다. 품질 기준이 충족되지 않았으므로 운영 의미 검색은 활성화하지 않는다.
