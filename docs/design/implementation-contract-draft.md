## 2. 현행 조사에서 확인한 제약

- `usePortfolioDerivedData.js`: 시장 시세가 없으면 평균가를 평가에 사용한다. `portfolioMath.js`: 환율이 없으면 환산 0을 반환한다. 새 계약에서는 실제 0과 품질 상태를 분리해야 한다.
- `202607190014_strategy_modes_and_principles.sql`: `app_save_strategy`는 버킷을 삭제·재생성한다. 변경 전후 버킷 DB ID를 영구적인 판단 참조로 사용할 수 없다.
- 같은 마이그레이션의 공유 전략 읽기는 `to_jsonb(strategy)`를 반환한다. 개인 기준을 기존 JSON에 단순 추가하면 공유 노출될 수 있다.
- `202607190008_news_facts_and_annotations.sql`: 뉴스는 기존 공유 읽기 대상이며 사실 삭제 시 의견이 cascade 삭제되는 구조다. 과거 판단 근거는 원본 ID만 참조해서는 안 된다.
- `202607190012_limit_news_fact_to_one_annotation.sql`: 사실별 의견 하나를 수정하는 모델이다. 신규 사용자 판단의 다중 이력 저장소로 재사용하지 않는다.
- `holdingActions.js`: 시장형·평가형·현금성 저장 RPC가 분리돼 있다. 공통 쓰기 규칙은 기존 개별·일괄·MCP 경로 모두에 적용해야 한다.
- `schema/OVERVIEW.md`에 거래 재계산과 과거 리포트가 기재돼 있지만 검색한 로컬 migration에는 해당 정확한 DDL이 없다. legacy migration은 placeholder다. 이 문서가 기존 거래 트리거·리포트 스키마를 검증했다는 뜻은 아니다.

## 3. 잔고와 매매 계약 권장안 (#32/#37/#38)

### 범위와 원본

- 스트림 단위는 소유자 + 계좌 + 종목이다. 통화/유형은 해당 시점의 종목 속성을 보존한다. 거래가 있는 종목의 통화·유형 변경은 단순 메타데이터 수정으로 처리하지 않는다.
- 기존 보유값을 초기 기준점으로 보존하고 그 이후의 거래로 현재값을 계산한다. 불완전 과거 거래로 초기 보유값을 덮어쓰지 않는다.
- 계산의 서버 원본은 기준점 + 유효한 체결/정정 이벤트다. `holdings`는 기존 조회를 위한 현재 투영값으로 동기화한다. 실제 테이블 재사용/확장은 기존 트리거 조사 후 결정한다.
- 시장형만 buy/sell 기록을 지원한다. 평가형/현금성은 기존 금액 등록·보정으로 관리한다. 자동 현금 차감·환전·분할·배당·계좌이체는 첫 버전 범위 밖이다.

### 숫자

- API의 금액·수량은 decimal 문자열로 주고받고 서버 PostgreSQL numeric로 계산한다. UI에서 Number로 산출한 결과를 저장 원본으로 삼지 않는다.
- 권장 입력 한계: 수량·단가 소수점 8자리, 정수부 최대 20자리. 초과 입력은 묵시 반올림하지 않고 오류/수정 안내한다. 기존 데이터가 이 한계를 넘으면 이관을 중단하고 범위를 조정한다.
- 원가 풀은 소수점 16자리, 양수 반올림은 half-up. 매도 원가는 원가 풀을 수량 비율로 배분하며 중간 UI 평균가로 다시 계산하지 않는다. 거래 1건당 정밀도 경계와 반복 거래 오차를 테스트한다.
- 평균가는 원가 풀/수량이다. UI 표시 반올림과 저장 정밀도를 분리한다. 수량 0이면 원가 0, 평균가는 미정(null)으로 반환하고 기존 0 표시와의 호환을 제공한다.
- 공매도/음수 수량·가격은 거부한다. 실제 buy/sell 수량·단가는 양수. 초기/보정의 평균가 0은 별도 무상취득 등 사유로 허용하되 missing과 구별한다.

### 계산 예시 (P1 제외안 전제)

| 사건 | 수량 | 잔여 원가 | 평균가 |
| --- | --- | --- | --- |
| 초기 20주, 평균 65,000원 | 20 | 1,300,000 | 65,000 |
| 10주를 71,000원에 매수 | 30 | 2,010,000 | 67,000 |
| 12주를 80,000원에 매도 | 18 | 1,206,000 | 67,000 |
| 남은 18주 전량 매도 | 0 | 0 | 없음 |
| 5주를 60,000원에 재매수 | 5 | 300,000 | 60,000 |

소수 예시: 0.5주×100 + 0.25주×120 → 0.75주, 원가80, 평균106.666… . 화면 반올림 평균을 다시 저장해 원가를 잃지 않는다.

### 시간·보정·정정 (P2 기준점 유지안 전제)

- 거래일은 사용자 시간대의 날짜, 실제 시각은 선택 입력이다. 기록 시각은 서버 UTC로 별도 저장한다. 날짜만 주어진 거래에 실제 시각을 꾸며 넣지 않는다.
- 날짜와 명시적 스트림 순번으로 재생한다. 같은 날 매수/매도 순서가 결과를 바꾸거나 보정 당일 포함 여부가 불명확하면 어느 쪽인지 묻는다.
- 새 보정은 절대 수량/평균가 또는 금액을 선언하는 기준점이다. 최신 기준점 이후의 과거일 거래는 뒤의 거래를 재생하며, 중간 초과 매도가 생기면 원자적으로 거부한다.
- 기준점 이전 거래 추가/취소는 과거 이력만 정정하고 이후 기준점이 선언한 현재값을 바꾸지 않는다. 미리보기에 이 영향을 명시한다. 초기 등록 이전의 불완전 이력은 수익률 계산 대상으로 승격하지 않는다.
- 취소는 원거래를 참조하는 무효화 이벤트다. 매수를 취소하려고 매도를 생성하지 않는다. 같은 취소 재시도는 같은 결과이며 기록은 삭제하지 않는다.
- 매매와 보정의 미리보기는 owner/input hash/stream version/expiry에 결합한다. 확정은 같은 계산과 락/CAS를 사용한다. stale 상태는 재계산하며 몰래 새 값으로 확정하지 않는다.
- 표 저장은 변경된 잔고 필드만 기준점을 만들고 메타데이터/변경 없는 행은 제외한다. 모든 변경 행과 감사는 한 트랜잭션으로 처리한다. 필터 밖 행을 지우지 않는다.

## 4. 평가·비중 계약 권장안 (#32/#34/#43)

- 실제 값 0, 가격 미확인, 오래된 가격, 평균가 대체, 환산 불가를 별도 품질 상태로 반환한다. 가격일·환율일·보유 변경 버전을 함께 제공한다.
- 시장형은 최신 저장 시세를 사용하고 없으면 기존 평균가 대체를 ‘원가기준 추정’으로 명시한다. 환율이 없으면 원화값은 null이며 0이 아니다. 수량 0은 가격이 없어도 평가 0이다.
- 평가형·현금성은 사용자 입력 금액을 쓰고 별도 실제 확인일을 보여준다. 저장일을 증권사 확인일로 해석하지 않는다.
- 하나라도 원화 평가 불가인 잔고가 있으면 전체 평가액/전체 비중은 산정 불가다. 대신 ‘평가 가능한 부분 합계’와 누락 건수를 표시한다. 계산 가능한 자산만으로 전체 비중처럼 재정규화하지 않는다.
- 전부 평가 가능하되 대체 가격/오래된 시세가 있으면 비중은 추정으로 표시한다. 배분 후보 금액은 완전한 가격/환율 입력을 확보하기 전 제공하지 않는다.
- 권장 freshness: 시장 시세/환율이 사용자 기준일에서 7일을 초과하면 오래됨. 7일 이내도 실시간을 의미하지 않으며 실제 날짜를 항상 표시한다. 시장별 거래일 캘린더 도입은 후속이다.
- 전체 분모는 모든 계좌의 시장형/평가형/현금성 원화 평가 합계다. 목록 필터로 바꾸지 않는다. 버킷에 연결되지 않은 태그는 ‘목표 미연결’ 값으로 드러낸다.
- 목표 합계는 decimal 기준 100%. 목표 미연결 자산이 있으면 원인과 현재 비중은 보여주되 적립금/리밸런싱 후보 산출을 보류해 잘못된 배분을 막는다.
- 유효한 경우 부족액 D=max(총액×목표비중−현재액,0), 적립금 C를 D/ΣD로 배분한다. 전체 C를 사용하며 적립 후 재최적화 알고리즘으로 바꾸지 않는다. 원 단위 잔액은 소수부 큰 순, 동률은 안정 ID순 배분해 합계 C를 맞춘다.
- 한도 null은 미설정, 0은 거래 허용액 0. 기존 코드의 0→Infinity 처리를 그대로 계승하지 않는다. 기존 저장 0의 의미는 이관 시 확인하며 임의 재해석하지 않는다.
- 월간 잔여 한도는 원장 완전성 확보 이후 계산한다. 초기 원장에 없는 이달 거래가 있을 수 있으면 ‘월간 한도 준수 미확인’을 표시한다. 계산 후보를 한도 검증을 마친 주문처럼 설명하지 않는다.

## 5. 원칙과 공유의 버전 경계 권장안 (#43)

- 기존 전략은 현재값을 유지하되 저장마다 immutable strategy revision을 기록한다. revision은 버킷 이름·태그 연결·모드별 목표·적립금·한도·상세 원칙을 함께 보존한다.
- 버킷에 안정적인 논리 ID를 도입하고 삭제는 retired 처리한다. 새 revision 참조에는 revision 내 버킷 키를 사용해 기존 재생성 ID 변화와 분리한다.
- 개인 투자 기준은 별도 소유자 전용 profile revision으로 관리한다. 기존 `strategies.principles`에 새 비공개 성향/자금 필요 정보를 섞지 않는다.
- 분석이 사용한 policy reference는 strategy_revision_id + profile_revision_id(nullable)다. 선택적 보유 이유 revision도 별도 참조한다. 둘을 한 번에 수정하면 원자적으로 저장한다.
- 현재값 수정은 expected_revision으로 충돌을 검사한다. 과거 revision은 덮어쓰지 않는다. 변경 없는 저장은 새 revision을 만들지 않는다.
- 기존 값은 migrated provenance로 보존한다. 기존 기본값이 실제 사용자 선택이었다고 소급 인증하지 않는다.

| 데이터 | 소유자/OAuth 본인 | 기존 친구·뷰어 (기본 상태, 새 정보는 명시적 허용 필요) |
| --- | --- | --- |
| 기존 자산·현재 전략·기존 상세 원칙 | 읽기/허용 수정 | 기존 허용 범위 읽기 유지 |
| 기존 뉴스·의견 | 읽기/허용 수정 | 기존 공유 유지 |
| 새 개인 기준·보유 이유 | 읽기/의도에 따른 수정 | 기본 금지. 허용한 공개 범위만 읽기 |
| 새 브리핑·판단·할 일 | 읽기/허용 변경 | 기본 금지. 허용한 공개 범위만 읽기 |
| 비공개 revision·근거 snapshot | 읽기 | 금지 |
| 기존 활동·CSV | 기존 동작 유지 | 기존 허용 범위만 유지 |
| 새 민감 데이터 변경 감사 | 소유자 | payload·존재·건수 누출 금지 |

기존 공유 RPC는 필드 allowlist로 바꾸고 private 테이블은 별도 RLS를 적용한다. 개인 분석에서 수집한 새 근거도 기본 private 저장으로 두며 기존 공유 뉴스 테이블에 자동 삽입하지 않는다. 사용자가 공유 뉴스로 옮기는 기능은 별도 명시적 동작이며 첫 버전에서 필수는 아니다.

### 선택적 공유 상세안 (ADR-0003 반영, UI 세부는 검토 중)

- [ADR-0003](../adr/0003-extensible-feature-sharing.md): 내부는 owner/audience/feature/action 단위, 첫 화면은 권한 묶음으로 단순화한다. 첫 버전 audience는 기존 친구/뷰어 공유 대상 집합이며 친구별 override는 구현하지 않는다.
- 브리핑/판단/할 일은 각각 독립 read 권한이다. ‘투자 점검 기록도 공유’ 묶음은 세 권한만 일괄 설정하는 UI 제안이다. 개인 기준/보유 이유/근거 자료는 별도 키·기본 off이며 영구 공유 금지가 아니다.
- 영역 허용은 해당 영역의 현재 및 향후 기록을 포함한다고 저장 전에 명시한다. 실제 공유 대상과 본문을 미리 보여준다. 기존 공유 관계가 있다는 이유만으로 신규 권한을 자동 부여하지 않는다. 새로운 기능 키도 기본 deny다.
- 연결 대상은 각각 권한을 검사한다. 판단 공유가 개인 기준·보유 이유·다른 할 일 공유를 자동 허용하지 않는다. 허용하지 않은 참조는 ID/제목/요약을 내보내지 않고 일반적인 ‘비공개 근거’ 표시만 제공한다.
- 공유되는 본문 자체에 사적인 이유가 적혀 있을 수 있다. 자동 필드 숨김이 본문 내용까지 익명화한다고 주장하지 않는다. 공개 미리보기에서 본문을 포함한 실제 공개 내용을 보여준다.
- 과거 policy/evidence snapshot은 공유 전용 응답의 allowlist로만 제공한다. 원본 private snapshot 테이블 접근은 허용하지 않는다. 공개한 의견의 근거가 숨겨질 수 있음을 설명한다.
- 철회/친구 삭제는 다음 요청부터 거부하고 공유 캐시를 무효화한다. 이미 상대가 열람·복사한 내용까지 회수할 수 있다고 약속하지 않는다.
- 친구 권한은 OAuth MCP의 자기 포트폴리오 읽기 범위를 자동 확장하지 않는다. 첫 버전 친구 열람은 앱의 별도 공유 문맥에서 수행한다.
- 신규 감사 payload/CSV, 검색, 건수, 페이지네이션, 공유 링크 직접 요청까지 같은 권한을 적용한다. shared 화면에 비공개 존재 여부가 새지 않아야 한다.

## 6. 점검·판단·질문의 관계 계약 권장안 (#44)

### 논리 레코드 (실제 테이블명은 관련 DDL 검증 후 매핑)

| 레코드 | 필수 관계/필드 |
| --- | --- |
| review_run | owner, 요청/기준시각, timezone, immutable context snapshot, 상태, idempotency |
| review_scope | run, 대상 종류/ID, 조사 from/to, 충분/일부/미확인, 사유, 근거 참조 |
| evidence_revision | owner, URL/제목/발행일(nullable)/확인일, 사실 요약, 원문 또는 보관 요약, 출처·정정 관계 |
| event | owner, 대상 종목, 발생/발표일(nullable), evidence revision 연결. 같은 URL과 같은 사건은 별개 |
| briefing_revision | run, headline/status, 변화/불확실성, evidence/decision/task 참조 |
| decision_revision | 제안/채택/대체 상태, 선택지·이유·작성 주체, policy/thesis/evidence revision, 이전 결정 |
| task + task_history | 조사/실행, 대상, 질문/계획, 조건/기한, 상태, 연결 판단/근거, expected_version |
| task_fill_link | task, 실제 trade ID; 거래당 실행 task 최대 하나 |

모든 참조에서 owner를 검증한다. UUID를 안다는 이유로 타 사용자 레코드를 연결할 수 없다. 소유권 있는 복합 FK/서버 검사와 RLS를 함께 적용한다.
기존 daily_reports/rebalance_suggestions의 재사용 여부는 정확한 DDL 확인 후 결정하며 중복 저장 원본을 만들지 않는다. 기존 뉴스는 revision snapshot의 원본으로 참조 가능하지만 원본 편집/삭제로 과거 근거를 삭제하지 않는다.

### 상태와 변경 권한

- run: draft → complete / partial / failed. 저장된 scope와 근거가 있어야 확정. partial은 실행 단위 최종 결과이고 다음 실행에서 실패 범위를 이어간다. 저장 재시도와 새 조사는 구분한다.
- decision: proposed → adopted는 사용자 채택 의도가 있어야 한다. adopted → superseded는 후속 채택 결정으로 원자 연결한다. 모델은 새 제안을 추가할 수 있지만 채택된 결정을 덮어쓰지 않는다. 제안 거절은 dismissed로 이력 보존한다.
- 조사 task: open ↔ waiting; 답+근거가 있으면 resolved. 저장 요청 범위에서 모델이 해결을 기록할 수 있으나 작성 주체를 명시한다. 새 정정 근거로 resolved → open을 기록할 수 있다. paused/closed는 사용자만 해제한다.
- 실행 task: planned/partial/completed는 유효 체결 합계로 계산한다. paused/cancelled는 사용자 의도. 취소 후에도 체결은 보존한다. 체결 취소로 completed가 partial로 돌아갈 수 있다.
- 실행 계획은 계좌·종목·매수/매도 방향·수량 단위가 맞는 체결만 연결한다. 금액/조건부 할 일은 별도 완료 정책이 없으면 수량 자동 완료를 적용하지 않는다. 과다 체결은 100%로 숨기지 않고 초과 수량을 표시한다.

### 확정·동시성·재시도

- context 조회는 쓰기를 하지 않는다. 저장 요청 때 run을 만들고 독립 immutable snapshot과 결과를 저장한다.
- 배치 확정은 briefing, scope, 근거 참조와 유효한 변경을 한 트랜잭션으로 기록한다. 요청 키+입력 해시가 같으면 동일 ID/응답, 다르면 idempotency_conflict.
- 모든 mutable 대상에 expected_version. 충돌은 결과를 덮어쓰지 않고 재조회·재검토한다. 이미 저장된 immutable 초안/근거는 남겨 재사용할 수 있다.
- 오래된 context로 분석한 결과는 그 당시 분석으로 보존하되 stale_context 표시를 한다. 최신 포트폴리오에 대한 의견처럼 승격하거나 질문 상태를 무조건 적용하지 않는다.
- 대상별 조사 완료 구간을 보관한다. latest 날짜의 max 하나로 실패 구간을 덮지 않는다. 다음 요청은 이전 미확인 구간 + 완료 구간 말단 3일 겹침(초기 권장) + 열린 질문을 반환한다. 장기 기간은 페이지/구간으로 나누고 실패 구간을 유지한다.
- 사용자 열람은 실제 앱/사용자 명시 동작으로만 기록하고 ChatGPT 응답 생성으로 추정하지 않는다.

### 최소 계약 예시 (가칭)

```json
{
  "operation": "finalize_review",
  "idempotency_key": "client-generated-uuid",
  "run_id": "run-uuid",
  "expected_run_version": 1,
  "context_id": "immutable-context-uuid",
  "scopes": [{"subject_id": "instrument-id", "status": "partial", "reason": "최신 공시 확인 실패", "evidence_revision_ids": []}],
  "briefing": {"status": "insufficient_data", "headline": "A기업 최신 발표는 아직 미확인", "decision_ids": [], "task_ids": []},
  "task_changes": []
}
```

응답은 run/briefing ID, persisted 상태, 범위별 저장 결과, stale_context 및 실제 적용한 버전을 반환한다. user_id는 입력값을 신뢰하지 않고 인증에서 도출한다.

## 7. 저장 의도 권장안 (#32/#33)

- ‘점검해줘’는 읽기/분석이며 저장하지 않는다. ‘점검하고 저장해줘’는 근거·브리핑과 해당 조사 질문 갱신을 허용하지만 투자 원칙 변경·제안 채택·매매 생성은 허용하지 않는다.
- ‘몇 주 샀어/팔았어’는 완료 매매 입력 흐름이다. 계좌/종목/날짜/가격이 명확하면 서버 미리보기 후 불필요한 재질문 없이 기록하고 변화와 성공 여부를 알려준다. 날짜 생략은 사용자 시간대 오늘로 적용했다고 명시한다.
- 계좌/종목 모호함, 같은 날 순서 불명, 보정/취소의 후속 영향, 대량 보정은 변경 전후를 확인받는다. preview ID가 인간 확인의 증거는 아니다.
- ‘유지하고 다음 실적 때 다시 보자. 기록해줘’는 사용자 유지 결정 + 조사 task를 기록할 수 있지만 매매는 만들지 않는다.
- 클라이언트 자체 도구 승인은 별개이며 우회하지 않는다. 뉴스 본문은 데이터이지 도구 지침이 아니다.

## 8. 화면 연결 권장안 (#36)

- today는 별도 라우트. 기존 overview는 자산으로 유지한다. 신규 기본 진입을 today로 하되 명시적 기존 hash는 보존한다.
- 자산의 태그/계좌/종목/표 편집 컴포넌트는 유지한다. ‘목표와 비교’는 allocation 하위 화면. 현재 보기를 보존하고 뒤로 돌아온다.
- 기존 strategy 링크는 원칙의 운용 계획으로 연결하고 배분 점검 진입을 표시한다. 기존 news/activity는 자료 보관함/활동 내역으로 매핑한다.
- 원칙은 개인 기준 / 상세 원칙 / 운용 계획 섹션. 기존 목표·적립금·한도 편집을 재사용한다. 프로필을 기존 공유 상세 원칙과 다른 공개 범위로 표시한다.
- 판단 목록에서 proposed/adopted/superseded를 구분한다. 관련 task와 근거는 상세에서 연결하고 분석 본문을 자산 카드마다 반복하지 않는다.
- 친구 보기에서는 기존 공유 데이터와 추가 허용된 영역만 표시한다. 비공개 today/decision/task로 진입하면 소유자 정보나 건수를 보여주지 않고 접근 불가/공유 자산으로 안내한다. 공유할 일은 읽기만 가능하고 채택·완료·수정 버튼을 제공하지 않는다.
- 모바일 하단 5개/PC 좌측 탐색을 기본으로 검증한다. 공유 보기에는 허용 메뉴만 표시한다. 메뉴 숨김과 별개로 서버가 권한을 검증한다.
- 모바일은 관련 대상 상세를 전체 높이로, PC는 충분한 폭에서 우측 패널로 연다. 필터/스크롤/키보드 포커스를 복구한다. 표 미저장 상태 이동은 유지/버리기/머무르기를 제공한다.

## 9. 다음 단계와 완료 게이트

1. P1~P3은 ADR-0002, 기능별 권한 구조와 단순 UI 분리는 ADR-0003에 확정했다. 정밀도·상태 전이·공개 필드와 UI 세부는 후속 검토한다.
2. 거래/리포트의 기존 정확한 DDL·트리거·RLS를 대상 한정 조회한다. 아직 조회하지 않았으므로 #32/#44는 완료 처리하지 않는다.
3. 계산 예제와 정책을 자동 fixture로 만들고 테이블 대응/입출력/오류 코드 및 이관 검증을 구체화한다.
4. #36 실제 React 기반 연결 시안과 #43 기존 노출 문제를 검증한다. 이번 문서는 동작하는 시안이나 보안 검증 완료가 아니다.
5. 사용자 결정이 반영되면 PRD/ADR/관련 티켓을 동기화하고 구현 인수 경계를 고정한다. 현 단계에서는 GitHub 티켓을 닫지 않는다.
