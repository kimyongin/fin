# 구현 전 계약 설계

2026-09-21 · 상태: 1차 설계안 작성 / 계약 검증 전. 기능 구현 완료가 아니다.

PRD/ADR는 제품 정책, 이 디렉터리는 데이터·호출 계약, 티켓은 작업 범위와 인수 조건을 담당한다. 티켓에 DDL/API 전체를 복제하지 않고 해당 계약을 연결한다.

에이전트 전달 명세: [공통 규칙·도구 설명·작업 가이드 관리](./agent/README.md). 지금은 문서 초안이며 실제 MCP 등록/배포와 구별한다. 기능 변경 시 관련 시나리오/설명/스키마/테스트를 함께 갱신한다.

단계 1~3을 먼저 통과하면 첫 수직 기능을 구현한다. 전체 제품의 모든 SQL/화면 설계를 끝낼 때까지 기다리지는 않는다. 거래 등 미확정 계약을 임의 구현해서도 안 된다.

## 코드 작성 전 통과 조건

- 정상/실패 JSON이 동일한 스키마로 검사되며 unknown 필드, 타인 ID, 누락 근거 등 반례가 명시돼 있다.
- 기존 테이블 재사용/신규/보존과 이관 영향이 구별돼 있다.
- 인증·직접 DB 접근·동시 수정·재시도·오래된 문맥 처리에 모순이 없다.
- 모델에서 API를, API에서 앱 화면과 다음 점검을 복원할 수 있다. 모델 추론 없이 ID/버전/관계로 이어진다.
- 검증 결과를 예상과 실제로 구분한다. fixture 검증이 RLS/트랜잭션/운영 검증을 대신하지 않는다.

## 다음 세션 시작점

`daily-review-api.md`의 문맥 증명 방식부터 작은 기술 검증을 한다. 순수 조회에서 저장한 적 없는 context_id를 요구하던 초안의 모순을 먼저 없앤다. 이어 JSON Schema와 계약 fixture를 만들고 성공·반례를 자동 검사한다. 운영 DB나 OAuth 실험 파일은 이 단계에서 변경하지 않는다.
