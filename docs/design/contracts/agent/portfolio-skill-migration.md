# Portfolio 작업 가이드의 플러그인 스킬 전환

2026-09-29 · Astra 설계 · 사용자 승인 방향: `get_workflow_guide` 전체 제거 및 스킬 전환. 아래 구성과 인수 조건은 구현 인계안이며 아직 적용·배포하지 않았다.

구현 티켓: [agent-01](../../../tickets/agent-01-workflow-guide-to-skill.md). 기존 개인용 [플러그인 배포 절차](../../../engineering/chatgpt-plugin-deployment.md)와 [지식 활용 검증 기록](./portfolio-knowledge-skill-plan.md)을 이어간다.

## 목표와 확인한 현재 상태

사용자가 태그·검색 순서·가이드 이름을 말하지 않아도 필요한 자료를 읽고 작업을 수행한다. 재사용할 결론은 에이전트가 정리해 기록을 제안하고 사용자 동의 후 저장한다. 안내를 받기 위한 별도 MCP 호출과 같은 지침의 중복 관리를 없앤다.

기준 커밋은 `b3b54f5`다. 현재 OAuth 서버는 11개 topic의 정적 `workflow-guides.ts`를 도구로 반환한다. 사용자별 데이터를 읽거나 절차를 실행하는 기능은 없다. 같은 일일 검토 지침을 `daily_portfolio_review` prompt와 `portfolio://guide/daily-review` resource로도 제공한다. 서버 instructions와 설치된 스킬은 가이드 조회를 권한다. 별도 source digest, 검토 manifest, 검사 스크립트와 CI gate가 이 전달 방식을 관리한다.

현재 통합 플러그인에는 `portfolio-knowledge-review` 스킬 하나가 있으며 투자 지식 검토에 범위가 한정돼 있다. 일반 웹 대화 두 건의 앱 호출은 확인했으나 스킬 자동 선택의 독립 증거, 자발적 기록 제안·동의 후 저장, 실제 모바일 사용은 미검증이다. 전환 설계로 이 미검증 사항을 통과 처리하지 않는다.

## 책임과 지원 범위

| 위치 | 책임 |
| --- | --- |
| 플러그인 스킬 | 사용자 의도 해석, 필요한 자료 선택, 질문·초안·동의·호출 순서, 기록 제안, 작업별 결과 해석 |
| 각 MCP 도구의 schema/description/응답 | 실제 입력·출력, 쓰기 범위와 부수 효과, 해당 도구의 재시도·충돌 처리, 미지원 동작 |
| 짧은 MCP server instructions | 실제 도구 결과로 현재값 확인, 조회와 쓰기 동의 구분, 성공 결과에 따른 저장 보고 등 공통 핵심 경계 |
| 서버·DB | 인증·소유권·공유 권한, 입력 검증, 필요한 버전 검사·중복 방지·원자성·금융 계산 |

스킬에 도구 스키마 전문이나 서버 정책을 복제하지 않는다. 반대로 가이드에만 있던 도구별 필수 사용 조건은 해당 description에 넣는다. 문장의 자연어 동의 여부는 에이전트 행동 검증 대상이다. 서버가 사용자의 대화상 동의를 직접 검증한다고 주장하지 않는다.

개인용 Portfolio 플러그인의 ChatGPT 웹·모바일을 작업 안내의 기준 경로로 삼는다. MCP 앱만 연결한 클라이언트도 목적별 도구와 서버 보호를 사용하지만 스킬 기반의 자발적 검색·기록 제안까지 제공된다고 보장하지 않는다. 앱만 쓰는 경로를 위해 가이드 도구·별도 지침 서버·대체 가이드 도구를 남기지 않는다. 스킬 미선택은 검증할 제품 실패이며 사용자에게 매번 스킬 이름을 말하도록 하는 것으로 해결 처리하지 않는다.

## 스킬 구성

`plugins/portfolio/skills/portfolio/SKILL.md` 하나를 진입점으로 사용한다. 기존 `portfolio-knowledge-review`의 행동을 이 스킬에 합치고 현재 패키지에서는 구 진입점을 제거한다. 플러그인 항목·앱 연결은 현재의 한 항목 구성을 유지한다. 다음은 구현할 파일 구성이다.

| 파일 | 읽는 상황 |
| --- | --- |
| `SKILL.md` | 연결된 Portfolio의 조회·관리·검토 요청. 실제 조회, 현재 도구 확인, 쓰기 동의, 자동 기록 중복 방지와 아래 지침 선택을 짧게 안내 |
| `references/knowledge-review.md` | 배분·전략·보유 이유의 판단, 과거 결정 재검토, 뉴스·이론 활용과 기록 초안 제안 |
| `references/assets.md` | 계좌·종목·보유·배분 수정, 종목 메모, 이미 체결된 거래 기록과 잔고 보정 |
| `references/principles.md` | 현재 투자 원칙의 정리·수정과 과거 저장본 정정·삭제 |
| `references/activities.md` | 할 일·반복·활동 CRUD, 기간 회고와 전체 페이지 조회 |
| `references/product-feedback.md` | 앱 문제·개선 요청의 제안·등록·수정과 권한 있는 관리자 처리 |
| `references/sharing.md` | 전체 포트폴리오 공유, 친구 연결·해제와 공유 자료 조회 |

한 요청에 필요한 파일만 읽고 일반 잔고 조회는 실제 조회 도구로 바로 처리한다. 스킬 description은 Portfolio 사용 요청에서 발견되도록 하며 앱 소스코드 개발이나 무관한 일반 투자 질문까지 무조건 적용하지 않는다. 사용 중 구체적인 앱 문제의 피드백 제안은 지원한다. 자동 선택을 비활성화하지 않는다.

지침은 한국어로 쓰고 실제 도구 식별자만 코드 표기로 사용한다. 도구마다 고정 호출을 강제하지 말고 사용자 목적에 필요한 조건과 순서를 담는다. 계좌·수량·공유 대상이 불명확한 쓰기는 필요한 질문을 한다. 사용자가 이미 명확히 승인한 작업을 반복 확인하지 않는다.

지원 파일 읽기는 실제 ChatGPT 웹·모바일에서 검증해야 한다. 읽을 수 없는 클라이언트에서 해당 참조를 읽었다고 가정하지 않는다. 지원 파일 전달이 실패하면 서버 제거 전에 패키지 구성을 다시 검토한다. 이 문서는 모바일의 파일 읽기 지원을 확인한 증거가 아니다.

## 기존 11개 topic의 이관 기준

| 기존 topic | 목적지 | 반드시 보존할 판단·절차 |
| --- | --- | --- |
| assets | assets | 미보유 종목과 수량 0 보유 구분, 배분 제외 자산의 총자산 포함, 시세 갱신 경로, 승인한 변경만 저장 |
| holding_thesis | knowledge-review / assets | 이유 검토와 종목 공통 메모 저장 구분. 현재 메모 확인, 자동 생성 활동을 수동 중복하지 않음 |
| trade_entry | assets | 미래 의향과 체결된 거래 구분, 계좌·수량·가격·날짜 확인, 실제 사용 가능한 미리보기·저장 도구, 금융 재시도 |
| reconciliation | assets | 증권사 현재 절대값으로 보정, 변화 없으면 쓰기 생략, 과거 거래 재생·실제 주문 취소로 오해하지 않음 |
| policy | principles | 이미 알려진 답 재사용, 빠진 선호만 질문, 전체 현재 문서 보존, 실제 변경과 과거 행 정정 구분 |
| daily_review | knowledge-review | 현재 원칙·보유·배분과 저장 자료 조회, 필요한 외부 조사, 조사 부족 표시, 승인 후 활동 저장 |
| decision_followup | knowledge-review / activities | AI 제안·사용자 채택·실행 구분, 당시 판단 근거 보존, 기록과 후속 할 일의 독립 동의·부분 성공 |
| todo | activities | 예정과 수행 구분, 반복 회차·전체 중단, 요청한 대상 변경, 금융 작업 성공 후 기록 보완을 위해 금융 쓰기를 반복하지 않음 |
| activity_report | activities | 정확한 기간·시간대, 전체 원본 페이지, 요약을 사건으로 중복 계산하지 않음, 현재 할 일을 과거 말일 상태로 오해하지 않음 |
| product_feedback | product-feedback | 투자 기록과 앱 피드백 구분, 자발적 제안 후 동의, 불필요한 개인정보 배제, 외부 GitHub 변경과 별개 |
| sharing | sharing | 전체 읽기 공유 범위, 대상과 영향 확인, 연결·해제·초기화 동의, 비밀번호 비공개·읽기 권한 |

매핑은 topic 문장 전체의 복사 지시가 아니다. 구현 시 현재 tools/list 정의·handler와 대조해 폐기된 지침을 버린다. 예를 들어 기준 가이드의 policy에는 MCP에서 공유 변경을 못 한다는 과거 문장이 남아 있지만 현재 sharing 도구는 존재한다. 실제 기능과 충돌하는 문장은 이관하지 않는다. 스키마가 보장하는 필드 검사나 모든 도구 이름 목록을 스킬에 다시 만들지 않는다.

이론·뉴스·결정의 검색 기준, 실제 앱 조회, 태그 지시 없는 검색, 원문 확인, 검색 실패 보완, 기록 초안·동의 후 저장은 기존 지식 활용 스킬에서 보존한다. 세 분류는 내용 해석 기준이며 새 DB 종류·예약 태그·이론 개수 제한을 만들지 않는다.

## 기존 portfolio-knowledge-review의 통합 검토

사용자는 기존 스킬까지 함께 검토해 정리하도록 명시했다. 이 스킬의 핵심인 자발적 조회·기록 제안을 새 일반 관리 안내에 묻히게 하지 않는다. 구 스킬과 11개 가이드를 이어 붙이지 않고 아래 기준으로 한 번씩 배치한다.

| 기존 문단·규칙 | 통합 판단과 위치 |
| --- | --- |
| name/description의 투자 검토 한정 | `portfolio`의 제품 사용 범위로 넓힌다. 단순 잔고도 스킬 범위에 포함하되 지식 검토 분기로 보내지 않는다. 소스코드 개발 제외와 제품 피드백 요청을 구분한다. |
| 활동을 다음 판단의 근거로 사용·사용자에게 검색법을 반복 설명시키지 않음 | 진입점의 핵심 목적과 검토 분기 선택 기준으로 보존한다. 상세 방법은 knowledge-review에 한 번만 둔다. |
| 이번 대화에서 실제 현재값 조회·메모리로 대체 금지 | 진입점의 공통 원칙으로 올린다. 같은 대화에서 읽은 관련 값은 변경·시간 경과를 판단해 재사용한다. 모든 응답마다 무조건 재조회하는 규칙으로 강화하지 않는다. |
| 현재 도구 확인·get_workflow_guide 조회 | 실제 제공 도구/schema 확인은 유지하고 가이드 조회 문장은 삭제한다. 필요한 첨부 지침을 읽는 방식으로 대체한다. |
| 현재 원칙·자산·목표·할 일 조회 | knowledge-review에 유지하되 요청과 관련된 정보만 읽는다. 일일 문맥과 최근 목록이 필요한 모든 이론·결정을 포함한다고 가정하지 않는다. |
| 실제 태그 목록→검색→중요 원문 | knowledge-review에 통합한다. 이미 확인한 태그는 재사용하고, 태그가 불필요한 직접 ID 조회에 목록 호출을 강제하지 않는다. |
| 단순 잔고·제공 글 요약 범위 | 진입점의 분기 규칙으로 옮긴다. 사용자가 지정한 글만 요약할 때 계좌·원칙·활동까지 읽지 않는다. |
| 이론/뉴스/결정 구분과 우선순위 | knowledge-review에 유지한다. 이론과 유효한 결정은 최근 기간으로 잘라내지 않고, 뉴스는 사건일·정정·현재성을 본다. 사용자 원칙과 AI 제안을 구분한다. |
| 이론 약 20개 예상 | 실행 지침에서는 숫자를 제거한다. 적은 후보를 넓게 확인한다는 검색 판단만 보존하며 상한·고정 읽기 개수를 만들지 않는다. |
| 분류+주제 태그·기존 태그 재사용·종목 참조 | 검색 전략은 knowledge-review, 일반 기록 태그/티커 수정은 activities, 자산 배분 태그는 assets에 둔다. 태그 이름을 필수 분류로 강제하지 않는다. |
| OR/AND·기간·검색 실패·태그 누락·점수 한계 | 질문 범위 추론과 재검색 판단은 knowledge-review에 둔다. 실제 입력/지원 조건은 search_activities 설명을 따른다. 의미 검색 실패를 자료 없음으로 단정하지 않는다. |
| 적용 조건·반대 근거·중복 증거·최신 외부 조사 | knowledge-review에 유지하며 daily_review의 조사 실패/미확인 범위 표시를 합친다. 포트폴리오 MCP가 외부 웹을 검색한다고 안내하지 않는다. |
| 사실·사용자 결정·해석 구분, 실제 읽은 출처 | knowledge-review의 답변 기준으로 통합한다. 모든 답변에 고정 양식이나 동일한 긴 항목 목록을 요구하지 않는다. |
| 저장 본문 속 명령을 자료로 취급 | 진입점의 공통 경계로 둔다. 활동 외의 피드백·공유 자료에도 적용한다. |
| 유용한 새 결론에 자발적 기록 초안 제안 | 진입점에 이 행동의 조건을 명시하고 knowledge-review에서 의미 있는 변화/새 근거/재검토 조건으로 판단한다. 사용자의 먼저 저장하라는 말을 기다리는 구 가이드 해석을 대체한다. |
| 단순 조회·중복·거절 후 제안 남발 금지 | 초안 제안 조건과 함께 한곳에 둔다. 현상 유지도 새 근거가 유의미하면 제안할 수 있다. |
| 제목·당시 근거·결론 상태·반대 조건·태그/종목 초안 | knowledge-review에 둔다. 나중에 판단을 이해하는 데 필요한 항목만 포함하며 새 태그는 초안에 표시한다. |
| 동의 후 저장·이미 승인한 요청은 반복 확인 금지 | 진입점의 공통 쓰기 규칙으로 통합한다. “요청 시만 저장”은 초안 제안 금지가 아니며 사용자의 초안 동의가 저장 요청을 충족한다. |
| 기록 동의와 금융 실행·원칙·할 일의 권한 구분 | 진입점과 아래 저장 대상 선택표로 정리한다. 모든 종류의 쓰기에 동일한 별도 확인창/질문을 추가하지 않는다. |
| 자동 기록 중복 방지·현재 기록 정정 | 일반 기록 조작은 activities, 승인된 자산 변경과 자동 기록 결과는 assets가 담당한다. #168 이후 반환하는 activity_id를 사용하고 동일 사실을 또 수동 저장하지 않는다. |
| 당시 근거를 본문에 보존 | knowledge-review에 유지한다. 원문이 바뀌어도 과거 판단 이유가 바뀌지 않도록 핵심 주장·한계를 남긴다. 새 snapshot 테이블은 없다. |
| 응답 유실·충돌·성공 후 재조회 | 진입점은 실제 결과 보고와 도구별 복구 계약 준수만 요약한다. 같은 키 재시도·현재값 우선 조회 등 도구마다 다른 조건은 해당 설명을 따른다. 승인된 스키마에 없는 키를 만들어 보내지 않는다. |
| 읽기 전용 공유·활동 저장의 효과 | 공통 읽기 권한은 진입점, 공유 변경은 sharing, 기록과 할 일/금융값의 독립성은 해당 참조에 둔다. |

### 같은 대화에서 저장 대상을 고르는 기준

| 사용자의 요청 | 대상과 경계 |
| --- | --- |
| “이번 검토의 이유를 기록해” | 일반 활동. 당시 근거와 결론 상태를 남기며 원칙·목표·보유값은 변경하지 않는다. |
| “이 내용을 종목 메모로 바꿔줘” | 현재 종목 공통 메모를 읽고 승인된 내용으로 수정. 자동 활동이 만들어지면 중복 수동 기록을 만들지 않는다. |
| “이 기준을 앞으로 내 원칙에 반영해” | 현재 원칙에 대한 승인된 변경. 기존 문맥을 보존하고 원칙 저장 계약을 사용한다. |
| “다음 달에 다시 검토할 할 일을 만들어” | 기존 할 일 중복 확인 후 일반 할 일. 판단 기록과 할 일이 모두 요청되면 각각의 결과를 보고한다. |
| “목표를 40%로 바꿔” | 실제 목표 배분 변경. 검토/기록 동의를 이 요청의 승인으로 대신하지 않는다. |
| “앱이 이렇게 동작했으면 좋겠어” | 제품 피드백 후보. 등록 의도가 명확하지 않으면 요약을 보여주고 저장 여부를 묻는다. |

이 표를 일반 활동으로 모든 결과를 보내는 규칙으로 쓰지 않는다. 이미 의도와 대상이 명확하면 바로 해당 절차를 따르고 모호한 쓰기 대상만 확인한다. “기록해”가 앞서 제시한 하나의 초안을 가리키면 다시 기록 종류를 묻지 않는다.

### 통합 후 핵심 검토 흐름

1. 사용자의 질문에서 필요한 현재 상태와 관련 지식을 판단한다. 실제 앱에서 확인한 자료를 사용하고 필요한 이론·뉴스·결정만 찾아 원문을 읽는다.
2. 현재 원칙과 사실, 과거 가정, 반대 근거를 비교해 답한다. 기존 기록을 찾는 비용을 사용자에게 태그 지정 요청으로 넘기지 않는다.
3. 다시 쓸 가치가 있는 새 결론이면 간결한 초안과 근거·상태·재검토 조건을 보여주고 저장 여부를 묻는다. 저장 금지 요청과 거절을 지킨다.
4. 동의한 대상에 한 번 저장하고 실제 결과를 확인한다. 자동 생성 기록이 같은 사실을 담으면 추가 저장하지 않는다. 기록 저장과 실제 자산 변경을 구분한다.

이 네 단계는 투자 검토의 핵심이며 모든 Portfolio 요청의 강제 절차가 아니다. 계좌 조회, 공유 설정, 피드백 등록까지 매번 이론 검색·판단 기록 제안으로 연결하지 않는다.

## 제거 범위와 호환 계약

- OAuth `get_workflow_guide` definition, 출력 schema, topic enum, handler, 도구 그룹, 시작 시 가이드 검사 및 호출 권고를 제거한다. `workflow-guides.ts`와 가이드 전용 렌더링·revision 계산을 제거한다.
- 동일 지침의 MCP prompt `daily_portfolio_review`, resource `portfolio://guide/daily-review`, 목록/읽기 처리기를 제거한다. 현재 OAuth endpoint의 유일한 prompt/resource임을 재확인하고 해당 capability 광고를 제거한다. 같은 내용을 다른 서버 문서 도구로 옮기지 않는다.
- 제거 후 오래된 `tools/call` 요청은 기존 unknown-tool JSON-RPC 오류 `-32602`를 반환하며 저장 부수 효과가 없다. 제거한 prompt/resource 메서드는 기존 미지원 메서드 경로 `-32601`로 처리한다. 별도 호환 handler·퇴역 topic 저장소는 두지 않는다. 새 대화/메타데이터 갱신을 안내하고 무한 재호출하지 않는다.
- `check-workflow-guides.mjs`, `workflow-guide-review.json`, 관련 npm 명령·CI 단계·seed 호출과 가이드 존재/단계 수 검사를 제거·교체한다. 도구 registry/schema/handler, 권한·재시도·금융 계약 테스트는 유지한다. 같은 source digest 체계를 스킬용으로 다시 만들지 않는다.
- 현재 PRD, 개발/배포 규칙, 계약 색인과 현재 티켓의 필수 게이트를 새 책임에 맞춘다. 과거 배포·검증 기록과 이전 ZIP은 이력으로 보존하고 실행 경로에 넣지 않는다. `plugins/portfolio-knowledge`는 과거 시험본이며 다음 배포 원본은 `plugins/portfolio` 하나다.
- DB schema·기존 기록·OAuth 앱 ID·보유 계산·공유 범위 변경은 없다. legacy agent-token endpoint의 종료는 별도 작업이며 이번 변경은 OAuth 가이드 제공 경로를 대상으로 한다.

## 구현·배포 순서

1. **S1 새 스킬로 투자 검토와 기록까지:** 하나의 스킬과 필요한 참조를 작성하고 가이드 호출 의존을 없앤다. 대표 검토 요청에서 실제 앱 조회→근거 답변→자발적 초안→동의 후 단일 저장·재조회까지 합성 데이터로 연결한다. 명시 선택 시험과 자동 선택 시험은 따로 기록한다. 구 서버에 가이드가 있어도 새 스킬 흐름은 이를 소비하지 않는다.
2. **S2 관리 작업 이관과 서버 정리:** 나머지 topic의 필요한 행동을 참조에 정리하고 아래 표의 시나리오로 확인한다. 가이드 전용 도구·prompt/resource·검사 체계를 로컬에서 완전히 제거한다. 각 도구가 가이드 없이 자기 계약을 설명하는지 확인한다. 새 범용 dispatcher나 서버 대화 엔진은 만들지 않는다.
3. **S3 배포와 실클라이언트 확인:** 현재 설치된 버전보다 높은 새 ZIP을 준비한다. 같은 내부 플러그인 이름과 앱 ID로 기존 Portfolio 항목을 갱신한다. 웹·모바일에서 스킬 본문/필요 참조 전달과 대표 작업을 먼저 확인한 뒤, 명시적으로 승인된 범위에서 OAuth Edge의 제거 버전을 배포한다. 서버 메타데이터 갱신 후 최종 도구 부재와 목적별 작업 성공을 재확인한다. 플러그인 업로드와 Edge 배포는 서로 다른 배포다.

전환 중 새 스킬과 구 서버의 일시 공존은 배포 순서를 위한 것이며 완료 상태가 아니다. 파일 전달·자동 선택이 실패하면 실패 내용을 기록해 스킬을 보완하고 서버 제거 배포를 보류한다. 영구 fallback 가이드 보존으로 범위를 바꾸지 않는다. 실제 모바일 확인이 불가능하면 로컬 구현 완료와 배포 준비까지만 보고한다.

서버 제거 전 실패는 기존 서버를 유지한 채 패키지를 고친다. 제거 후 회귀라면 먼저 동작하던 서버 커밋을 재배포해 구 패키지 복구에 필요한 가이드를 되살릴 수 있게 한 뒤, 필요한 경우 이전 정상 패키지 내용을 더 높은 버전으로 재업로드한다. ZIP의 낮은 버전 재설치 가능성을 가정하지 않는다. 복구 대상 서버 커밋·ZIP 해시·앱 ID를 배포 시 기록한다.

형식 검사는 스킬 frontmatter·참조 파일/링크·패키지 포함·현재 도구 이름과 앱 ID를 확인한다. 문구/문단 수만 맞추는 테스트로 의미 검증을 대신하지 않는다. 관련 unit·Edge type·인증된 MCP initialize/tools/list/call 회귀와 인코딩/빌드 검사를 수행한다. 실제 쓰기·응답 유실·충돌·권한 테스트는 격리 데이터로 수행하고 운영에 임의 시험 금융값을 저장하지 않는다.

웹과 실제 모바일에서 각각 새 대화의 자동 선택, 참조 전달, 실제 앱 호출, 저장 제안·동의 후 결과를 기록한다. 핵심 투자 검토는 클라이언트별 두 독립 대화에서 재현한다. 답변의 “읽었다” 문구만으로 스킬 선택·자료 조회를 증명하지 않는다. 클라이언트가 선택 근거를 제공하지 않으면 그 항목은 미확인으로 쓰고 행동 결과와 구별한다. 실패를 발견하면 질문·패키지/서버 버전·누락 단계·수정 후 재시험을 기록한다.

## 병행 개발과 인계

이 설계는 `codex/portfolio-skill-migration` worktree에서 작성했다. 다른 세션의 #168 구현은 기준 커밋에 없다. 그 작업이 커밋된 후 이 브랜치에 반영하고 도구의 새 `activity_id`, 메모 저장·자동 기록 의미를 다시 대조한다. 공유 작업 폴더의 미커밋 파일을 복사하거나 그쪽 파일을 수정하지 않는다. #168의 가이드 변경은 필요한 행동만 새 스킬/도구 설명에 옮기고 제거한 체계를 복원하지 않는다.

폴더 분리는 실행 환경까지 격리하지 않는다. 두 worktree에서 같은 Supabase project ID·포트·`.e2e` Docker 자원을 동시에 reset/사용하지 않는다. 구현 전 사용 중인 테스트 환경을 확인하고 순차 실행하거나 독립 인스턴스를 구성한다.

이번 산출물은 설계 문서와 로컬 구현 티켓이다. 실제 스킬·코드·설정·운영 데이터는 변경하지 않았다. Sol의 명시적 구현 요청 후 S1부터 시작한다. 새 배포 승인과 실제 모바일 검증은 구현 완료 보고와 구분한다.
