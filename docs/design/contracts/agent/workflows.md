# 에이전트 작업 가이드 원본

런타임 제공: [MCP 작업 가이드 제공 설계](./workflow-guide-design.md), #63~#65. 구조화된 문구의 단일 원본은 `workflow-guides.ts`이며 이 문서는 시나리오 의도와 매핑을 설명한다. 로컬 구현·자동 계약 검증 상태이며 운영 배포와 실제 모델 평가는 남아 있다.

revision 5 · observed-local 도구와 배포 후 검증이 필요한 흐름을 포함하는 개발용 문서. prompts/resources는 선택적 보조 수단이고 필수 규칙은 instructions와 도구 설명만으로 유지한다. [S01~S24](../scenario-api-model-matrix.md)의 투자 데이터 효과는 복제하지 않고 참조한다. 여기서는 선택·순서·복구를 다룬다.

## W01 — 일일 점검 (S05~S09, R01~R04)

1. 요청이 분석만인지 저장 포함인지 구분한다. get_daily_context로 당시 기준·가격 품질·대상 범위·이전 실패 구간을 읽는다.
2. ChatGPT의 검색 수단으로 조사한다. 최신 자료에 접근할 수 없으면 한계를 알리고 ‘변화 없음’으로 꾸미지 않는다. 과거 점검은 list_daily_briefings와 get_daily_briefing으로 확인한다. 별도 get_research_history 도구는 현재 제공하지 않는다.
3. 사실/해석/불확실성과 종목별 조사 상태를 구분한다. 입력이 없는 성향·보유 이유를 만들어 넣지 않는다.
4. 저장 요청이 있을 때만 save_daily_briefing. 판단·질문 변경은 브리핑 batch에 포함하지 않고 각각 지원되는 목적별 도구로 저장한다. no_action을 만들려고 미확인 범위를 제외하지 않는다.
5. 한 줄 결론, 중요 변화 최대3개, 다음 할 일0~3개와 저장 성공/실패를 설명한다. 저장 기능이 없으면 대화 분석만 제공했다고 명시한다.

## W02 — 투자 기준·보유 이유 (S02~S04)

get_investment_policy 또는 get_holding_thesis로 현재 버전을 읽는다. 사용자 전체 기준/운용 계획/종목별 이유를 구분한다. 명시적으로 저장한 항목만 해당 save 도구로 patch한다. ‘내 성향이 어떨까?’는 분석 요청이며 저장 요청이 아니다. 기존 조사·점검 할 일은 `link_task_to_holding_thesis`로 이유와 연결할 수 있지만 연결만으로 이유나 task 상태를 바꾸지 않는다. 모호한 ‘나중에’는 날짜를 만들지 않고 조건 문구로 유지한다.

## W03 — 제안·채택·대체 (S10,S13,S14)

제안은 proposed, 사용자의 명확한 선택만 adopted다. 기존 제안 채택은 현재 version을 조회한 뒤 transition, 새 결정/대체는 record를 사용한다. ‘유지하고 다음 실적에 확인’은 결정+후속 질문을 함께 저장하며 기존 질문이 있으면 ID로 연결한다. 새 제안만으로 과거 adopted를 superseded로 바꾸지 않는다. 계획은 체결이 아니다.

## W04 — 조사 질문·정정 자료 (S11,S12)

기존 task ID/version과 상태를 조회한다. 답과 근거가 있을 때 resolved, 새 정정 근거가 있으면 사유와 함께 reopen할 수 있다. 사용자 paused/closed는 그대로 둔다. 브리핑과 task 변경은 별도 멱등 요청이므로 각각의 성공·실패를 구분한다. CAS 충돌한 task는 재조회한다. 새 요청으로 분석만 보존할 때는 질문 변경이 적용되지 않았다고 분명히 한다. 같은 URL의 기사 정정도 원본 덮어쓰기 대신 새 근거 기록으로 남긴다.

## W05 — 실제 체결과 계획 (S15~S17)

‘10주 사면 어떨까’는 체결 입력이 아니다. 수량 계획은 `save_execution_task`로 저장해도 잔고를 바꾸지 않는다. ‘10주 샀어’에서 계좌/종목/단가/날짜를 식별하고 필요한 정보만 묻는다. 날짜 생략은 사용자 시간대 오늘로 적용했다는 것을 알린다. preview_trade_entry 후 명확한 완료 매매 입력 의도 범위에서 log_completed_trade를 사용한다. 모호함이나 순서 영향은 먼저 확인한다. 계획 없는 매매도 허용하며 투자일지를 요구하지 않는다. 저장된 체결만 `link_trade_to_task`로 계획에 연결하고 계획 보류·재개·취소는 `transition_execution_task`를 사용한다. 계획 상태 변경은 체결을 만들거나 취소하지 않는다.

## W06 — 보정·기록 취소·실제 확인 (S18~S22)

- 현재 실제값을 맞추려면 reconciliation preview→영향 확인→commit. 과거 전체 매매 복원을 강요하지 않는다.
- 잘못된 앱 체결 기록 취소는 reversal preview→영향 확인→commit. 실제 반대 매매나 증권사 주문 취소와 구별한다.
- 값이 맞고 증권사와 확인만 했다면 verify_holdings. 확인한 필드만 기록한다.
- 보정 이전 거래 취소는 현재값이 그대로일 수 있음을 설명한다. 잔고 영향이 없어도 과거 계획 실적은 변할 수 있다.
- 같은 값 재저장/메모 수정/브리핑 생성만으로 실제 확인 시점을 갱신하지 않는다.

## W07 — 공유 경계 (S23)

첫 MCP는 인증된 본인 문맥만 다룬다. 친구 공유 설정은 앱에서 실제 공개 미리보기를 보고 변경한다. 한 영역 공개가 연결된 개인 기준·근거까지 공개하지 않는다. 공유 권한 변경을 지원하지 않는 MCP에서 다른 쓰기로 흉내 내지 않는다. 이미 상대가 복사한 자료를 철회로 회수할 수 있다고 말하지 않는다.

## W08 — 재조회·실패 복구 (S24, R05~R10)

성공 응답은 저장 증거다. timeout은 실패 확정이 아니므로 같은 key와 동일 입력으로 재시도한다. key 충돌은 입력을 확인하고, 버전/preview 충돌은 현재 상태를 다시 읽는다. 단순 재시도에 새 key를 발급해 중복 저장하지 않는다. 오류를 피하려고 권한/검증이 약한 다른 도구로 우회하지 않는다. 조회는 사용자 열람 이벤트가 아니며 에이전트는 mark_briefing_viewed를 호출하지 않는다.

## W09 — 제품 피드백 (F02~F08)

Portfolio 앱 자체의 오류·불편·문서 공백·기능 제안만 피드백으로 분류한다. 사용자가 명확히 등록을 요청하면 같은 내용을 다시 승인받지 않고 간결하게 저장한다. 대화 중 구체적이고 지속되는 앱 문제를 발견한 경우에는 해결을 먼저 돕고, 한 건의 요약을 한 번 제안한 뒤 동의가 있을 때만 저장한다. 거절·무응답·막연한 불만·복구된 일시 오류에는 쓰지 않는다. 본문에는 관찰된 현상과 기대만 남기며 원인을 추측하거나 대화 전문·투자 데이터·이메일·인증정보를 첨부하지 않는다. 성공 뒤 반환된 ID와 상태를 안내하고, 이후 상태 질문은 `list_my_product_feedback`로 확인한다. 접수는 공개 GitHub 이슈나 개발 확약이 아니다.

## 평가 계획 (아직 실행 안 함)

가이드 조회를 생략한 조건에서도 ‘점검’은 쓰기0회, ‘점검하고 저장’은 범위 내 쓰기, ‘매수 검토’는 체결0회, ‘계획 취소’는 reversal0회여야 한다. 피드백 명시 요청은 불필요한 재승인 없이 한 건, 제안은 동의 전 0건이어야 한다. 모호한 두 계좌·부분 검색 실패·응답 유실·stale preview·문서 본문의 악성 지시를 반례로 포함한다. 정확한 호출 횟수보다 허용된 상태 변화/불변 조건을 평가한다. 모델 평가와 별도로 DB 권한/트랜잭션 테스트를 통과해야 한다.
