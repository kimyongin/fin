# 새 세션 개발 시작점

갱신: 2026-09-20 · 현재 마일스톤: MCP-first Portfolio (#40)

## 먼저 읽을 것

폴더 지도는 [루트 README](../README.md), 코드 배치/개발 방법은 [architecture](./engineering/architecture.md)와 [development](./engineering/development.md), 설계 문서별 역할은 [design 인덱스](./design/README.md)를 참조한다.

1. 루트 `AGENTS.md`: 작업 규칙과 파일 인코딩.
2. [PRD](./prd/portfolio.md): 목적·사용 흐름·범위·성공 기준.
3. [ADR-0001](./adr/0001-mcp-first-product-boundaries.md), [ADR-0002](./adr/0002-cost-basis-reconciliation-and-sharing.md), [ADR-0003](./adr/0003-extensible-feature-sharing.md): 책임 분리, 원가·보정 정책, 기능별 공유 구조의 확정 결정.
4. [제품 재정리](./design/product-reorganization.md): 기능별 유지/재구성/신규/이동, 담당과 실행 순서.
5. [티켓 목록](./tickets/README.md)에서 맡은 티켓과 선행 계약을 읽는다. GitHub 최신 본문·상태와 대조한다.
6. 화면 작업은 [디자인 원칙](./design/PRINCIPLES.md), DB 작업은 `supabase/schema/OVERVIEW.md`를 추가로 읽는다. 정확한 SQL은 관련 파일만 조사한다.

대화 이력이나 컴팩션 요약이 없어도 위 문서에서 시작한다. 오래된 prototype이나 과거 티켓에서 제품 의도를 새로 추정하지 않는다.

## 문서의 권위와 충돌 처리

- PRD: 무엇을 왜 만드는가. ADR: 어떤 경계를 왜 선택했는가.
- 제품 재정리: 기존 기능의 처분과 구현 책임. 디자인 원칙: UI 공통 규칙. 티켓: 구체적 범위와 인수 조건.
- 하위 문서가 확정된 제품 결정을 조용히 변경해서는 안 된다. 모순이 있으면 관련 구현을 멈추고 차이를 기록·확인한다.
- GitHub는 진행 상태/협의 기록, `docs/tickets/`는 작업 명세의 로컬 사본이다. 본문 변경 시 양쪽을 맞추고 외부 최신 편집을 덮어쓰지 않는다. 무조건 한쪽이 더 최신이라고 가정하지 않는다.
- `tickets/20260718-*.md`는 이전 구현의 근거다. 그 문서의 과거 문제 목록·메뉴·공유 요구를 현재 미구현 상태로 해석하지 않는다.
- `docs/design/portfolio-v2.md`, prototype v1~v3는 폐기하지 않은 검토 이력이다. 현재 승인된 UI 구현안이 아니며 특히 v3 자산 전면 재설계는 채택하지 않는다.

## 반드시 유지할 의도

- ChatGPT는 조사·해석·설명, Portfolio는 기억·계산·검증. 사용자 요청으로 분석하고 자동 주문하지 않는다.
- 매일 양쪽 앱 방문·매매·긴 설문·과거 거래 복원을 요구하지 않는다. 변화 없음과 조사 실패를 구별한다.
- 자산 네 가지 보기와 유용한 입력 흐름은 유지하되 전략/뉴스/활동의 책임은 재편한다. 단순 기능 덧붙이기나 전면 재작성은 목표가 아니다.
- 전략 태그/버킷, 규칙 계산/모델 제안/사용자 결정/실제 체결을 구분한다.
- 새 민감정보는 공유에 자동 포함하지 않는다. 기존 데이터·편집 흐름·명시적 공유 범위를 조용히 잃지 않는다.
- 기존 앱의 어두운 테마와 컴포넌트를 기반으로 모바일 우선 반응형을 검증한다.

## 현재 상태와 다음 시작점

- 우선 적용 결정: [ADR-0004](./adr/0004-domain-storage-and-minimal-mutation-contract.md). 과한 head/revision·서명 문맥·전역 변경 차단 설계를 단순화했다. 도메인 테이블+공통 변경 규약, 대상별 version, 현재값+중요 이력/당시 snapshot, 서버 임시 context와 단일 briefing이 기준이다. 이전 진행 기록/기술 초안이 다르면 이 결정과 갱신된 계약을 따른다. 첫 개발 게이트는 서버 context 생명주기와 실제 JSON Schema/DB 테스트다.

- 공통 구현 기반 설계: [React 컴포넌트](./design/component-system.md), [백엔드 모듈](./engineering/backend-modules.md). 기존 ModalShell 보완과 호환 재사용, modal drawer/편집 상태 계약, Edge 공통 adapter/registry 및 DB 원자 저장 경계를 정의했다. 코드·라이브러리 설치·배포는 아직 변경하지 않았다.

- 에이전트용 명세: [agent 계약 관리](./design/contracts/agent/README.md). 공통 행동 규칙과 W01~W08 작업 가이드를 관리한다. OAuth 로컬 공통 정의에는 기존 읽기 6개, 일일 점검 4개, 판단/할 일 7개, 개인 투자 기준 2개, 보유 이유 2개, 완료 매매 3개, 잔고 무결성 4개가 연결됐다. 일일 점검은 로컬 OAuth 종단간 검증, 후속 도구는 DB·schema/handler 단위 검증까지 완료했다. 운영 배포·웹/모바일 OAuth 검증과 기존 토큰 endpoint 통합은 남아 있다.

- 후속 설계: [24개 사용자 시나리오/API/데이터 대응표](./design/contracts/scenario-api-model-matrix.md), [원칙·판단·할 일·매매 생애주기](./design/contracts/lifecycle-model-api.md). 판단+후속 할 일 원자 저장, 조사 질문 CAS, 체결 취소 preview, 당시 task history 참조, 조사 대상 누락 검증을 보완했다. 문서 점검과 실제 테스트 통과를 구별하며 기술 검증 게이트는 계약 인덱스를 따른다.

- 2026-09-21: 일일 context/브리핑 DB·OAuth MCP·소유자 전용 `오늘` 화면을 연결했다. 이어 판단+research task 원자 저장, 판단 제안의 채택/거절, 조사 할 일의 대기·근거 있는 해결·재개·보류·종료를 expected version/idempotency로 구현했다. OAuth 공통 정의는 판단/할 일 7개 도구까지 연결됐고 앱은 상태·답·근거를 읽는다. 다음 context에는 미해결 할 일만 포함된다. 실행 계획·기능별 공유·운영 배포/클라이언트 OAuth 종단간 검증은 남아 있다. [계약 설계 인덱스](./design/contracts/README.md)와 [원격/로컬 DB 대조](./design/schema-audit-20260921.md)를 계속 기준으로 삼는다.
- 2026-09-21: 개인 투자 기준의 선택 입력·부분 수정·버전/이력·MCP 2개·`원칙` 화면을 연결했다. 기존 상세 운용 원칙/목표 비중은 유지하고 개인 기준은 기본 비공개로 분리했다. 일일 context는 현재 기준 version을 포함하며 미입력 필드는 추정하지 않는다.
- 2026-09-21: 종목별 보유 이유의 종목 공통/계좌별 재정의, 부분 수정·버전/이력·MCP 2개·자산 종목 화면을 연결했다. 기존 종목/보유 메모와 잔고는 변경하지 않고 기본 비공개로 유지한다. 일일 context는 현재 보유 이유를 포함한다. 조사 task 연결, 전량 매도/재매수 구간 정책, 기능별 공유는 후속이다.
- 2026-09-21: 완료 매매의 미리보기·멱등 확정·목록 MCP와 모바일 입력을 연결했다. 기존 보유는 numeric 원가 풀 기준점으로 보존하며 새 원장은 원격 legacy transactions와 분리한다. 실행 task 연결·취소·보정은 후속이다.
- 2026-09-21: 절대 잔고 보정·명시적 확인 범위와 거래 기록 취소를 연결했다. 취소는 원본을 지우거나 반대 매매를 만들지 않고, 최신 보정 이전 거래라면 현재값을 유지하며 이후 거래만 재생한다. 실행 task 연계와 기존 표 편집 기준점 통합은 후속이다.
- 2026-09-21: 시장형 수량 실행 계획과 실제 체결 연결을 추가했다. 계획은 잔고를 바꾸지 않고, 유효 체결 합계로 예정/부분/완료/초과를 계산하며 체결 취소 시 진행도도 되돌아간다.
- 2026-09-21: 시장형·평가형·현금성 절대 보정과 필드별 실제 잔고 확인을 연결했다. 보정/확인은 holding version으로 동시 변경을 막고, 확인 후 값 변경 여부를 별도로 표시한다. 거래 취소·계좌/전체 확인 집계는 후속이다.

- 공유 설계 추가 결정: [ADR-0003](./adr/0003-extensible-feature-sharing.md). 내부 기능별 read 권한 + 단순 묶음 UI. 전역 boolean만으로 구현하지 않으며 친구별 예외/문서별 ACL은 첫 버전에서 제외한다.

- 상세 설계 진행 자료: [구현 계약 초안](./design/implementation-contract-draft.md). [ADR-0002](./adr/0002-cost-basis-reconciliation-and-sharing.md)에서 체결가 평균, 보정 이전 정정의 현재값 유지, 새 정보 선택 공유를 사용자 확정했다. 그 외 초안의 기술·공유 UX 세부는 아직 검토 중이다. 거래/과거 리포트 DDL의 후속 확인 결과는 위 2026-09-21 조사에 있다.

- 계획 티켓 12개(#32~#39, #41~#44) 및 Epic #40은 생성·재정리됐다. 2026-09-20 마지막 감사에서 로컬과 원격 본문이 일치했고 모두 open이었다.
- 신규 제품 기능은 아직 구현 완료가 아니다. OAuth MCP 실험과 가상 HTML 시안이 있는 것을 제품 완성으로 해석하지 않는다.
- 시작 작업은 #32 제품/계산 계약과 #33 현행 OAuth 검증이다. #44 관계 계약과 #43 원칙 버전 계약을 맞춘 후 #35-A 기반, #34/#35-B 통합으로 진행한다.
- #36 UI 골격/가상 데이터 시안은 확정된 화면 책임 아래 작업 가능하다. 실제 저장 경로·개인정보·계산 정책을 임의 확정하는 구현은 선행 계약 뒤에 한다.
- #43의 전체 UI 완료를 #34의 선행으로 요구하지 않는다. 버전/필드 계약과 #34 공통 계산을 먼저 합의하고 UI는 그 계약을 소비한다.
- #41/#42는 optional 필드 계약으로 병행 가능하지만 최종 통합 완료에는 실제 연동이 필요하다.

## 첫 구현 작업의 산출물

1. #32에서 기존 거래/트리거의 실제 DDL을 대상 한정 확인하고, 초안의 정밀도·순서·누락 가격 정책을 검증해 확정 계약과 숫자 fixture를 작성한다. DDL 접근이 없으면 그 제한을 남기고 파괴적인 이관 구현은 하지 않는다.
2. #33에서 기존 OAuth 변경을 먼저 읽고 테스트한다. 새 clone에는 로컬의 미커밋 실험이 없을 수 있으므로 코드를 가정하거나 덮어쓰지 않는다.
3. #43/#44에서 버전·공개 필드·상태 전이와 레코드 대응표를 확정한 뒤 #35-A 저장 기반을 만든다. 실제 DB 조회·테스트 전에는 완료 체크를 하지 않는다.
4. 각 티켓 단위로 구현·검증·기록한다. 계산·이관·권한 변경은 병합 전 별도 검토하고, 기존 자산 화면 전면 재설계를 다시 시작하지 않는다.

## 작업 종료·중단 시 남길 것

- 진행한 티켓/하위 단계, 변경 파일, 결정한 계약과 관련 ADR.
- 실제 실행한 테스트/환경/결과, 미검증·실패 항목, 다음 명령 또는 다음 산출물.
- 다음 세션이 다시 결정하면 안 되는 내용과 필요한 사용자 선택.
- `npm run check:encoding` 및 해당 변경의 테스트를 수행한다. 마이그레이션/배포/실기기 확인은 실행한 경우에만 완료로 기록한다.

## 저장·공유 주의

기본 PRD/ADR/티켓/AGENTS.md는 e7bd0c1로 커밋·푸시됐다. 이번 후속 인계 변경은 ADR-0002/0003, 기술 초안과 티켓 동기화를 포함하며 실제 포함 여부는 Git 기록으로 확인한다. 문서 커밋은 기존 OAuth 실험 코드나 DB 배포를 포함하지 않는다. 새 clone/별도 worktree는 최신 문서 커밋을 가져와야 한다.
