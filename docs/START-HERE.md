## 최신 인계: 운영 안정성 개선 티켓

다음 개발은 [운영 안정성 개선 티켓 목록](./tickets/README.md#운영-안정성-개선--다음-개발-시작점)의 **#49부터 시작한다.** #49~#53은 정적 코드 리뷰에 근거한 명세만 작성했으며 아직 구현하지 않았다. 모델/세션을 바꾼 뒤 각 티켓의 코드 근거와 재현·인수 조건을 읽고 최소 수정 → 검증 → 수직 슬라이스별 커밋 순서로 진행한다.

- #49 매매 동시 처리·재시도 → #50 사용자별 비동기 상태 격리 → #51 배포 게이트 → #52 대상별 조회·공유 필드 → #53 모달·MCP 오류 진단.
- 위험 시나리오는 아직 재현 검증 전이다. 이전 기능 테스트 성공을 동시 실행·응답 유실·사용자 전환 경합 검증으로 간주하지 않는다.
- 범용 데이터/명령 프레임워크를 만들지 않는다. 기존 도메인 모델을 유지하면서 필요한 공통 처리만 작게 추출한다.
- RPC 누락 대응으로 운영 migration 020~023 적용 및 로컬/원격 목록 일치를 확인했다. 인증 사용자 성공 검증, 프런트/Edge 배포, 실사용 파일럿은 별도 증거가 필요하다. 운영 배포는 자동으로 진행하지 않는다.

- 운영은 `1a13ae4`까지 migration 001~019/OAuth MCP/Pages 배포 및 CI E2E 성공을 확인했다. 아래 배포 전 설명은 과거 감사 기준이다. 배포 성공과 실기기·지인 OAuth·전후 정량 대조·5일 파일럿 완료를 혼동하지 않는다.

## 먼저 읽을 것

폴더 지도는 [루트 README](../README.md), 코드 배치/개발 방법은 [architecture](./engineering/architecture.md)와 [development](./engineering/development.md), 설계 문서별 역할은 [design 인덱스](./design/README.md)를 참조한다.

1. 루트 `AGENTS.md`: 작업 규칙과 파일 인코딩.
2. [PRD](./prd/portfolio.md): 목적·사용 흐름·범위·성공 기준.
3. [ADR-0001](./adr/0001-mcp-first-product-boundaries.md), [ADR-0002](./adr/0002-cost-basis-reconciliation-and-sharing.md), [ADR-0003](./adr/0003-extensible-feature-sharing.md): 책임 분리, 원가·보정 정책, 기능별 공유 구조의 확정 결정.
4. [제품 재정리](./design/product-reorganization.md): 기능별 유지/재구성/신규/이동, 담당과 실행 순서.
5. [티켓 목록](./tickets/README.md)에서 맡은 티켓과 선행 계약을 읽는다. GitHub 최신 본문·상태와 대조한다.
6. 화면 작업은 [디자인 원칙](./design/PRINCIPLES.md), DB 작업은 `supabase/schema/OVERVIEW.md`를 추가로 읽는다. 정확한 SQL은 관련 파일만 조사한다.

대화 이력이나 컴팩션 요약이 없어도 위 문서에서 시작한다. 오래된 prototype이나 과거 티켓에서 제품 의도를 새로 추정하지 않는다.

## 문서의 권위와 충돌 처리

- PRD: 무엇을 왜 만드는가. ADR: 어떤 경계를 왜 선택했는가.
- 제품 재정리: 기존 기능의 처분과 구현 책임. 디자인 원칙: UI 공통 규칙. 티켓: 구체적 범위와 인수 조건.
- 하위 문서가 확정된 제품 결정을 조용히 변경해서는 안 된다. 모순이 있으면 관련 구현을 멈추고 차이를 기록·확인한다.
- GitHub는 진행 상태/협의 기록, `docs/tickets/`는 작업 명세의 로컬 사본이다. 본문 변경 시 양쪽을 맞추고 외부 최신 편집을 덮어쓰지 않는다. 무조건 한쪽이 더 최신이라고 가정하지 않는다.
- `tickets/20260718-*.md`는 이전 구현의 근거다. 그 문서의 과거 문제 목록·메뉴·공유 요구를 현재 미구현 상태로 해석하지 않는다.
- `docs/design/portfolio-v2.md`, prototype v1~v3는 폐기하지 않은 검토 이력이다. 현재 승인된 UI 구현안이 아니며 특히 v3 자산 전면 재설계는 채택하지 않는다.

## 반드시 유지할 의도

- ChatGPT는 조사·해석·설명, Portfolio는 기억·계산·검증. 사용자 요청으로 분석하고 자동 주문하지 않는다.
- 매일 양쪽 앱 방문·매매·긴 설문·과거 거래 복원을 요구하지 않는다. 변화 없음과 조사 실패를 구별한다.
- 자산 네 가지 보기와 유용한 입력 흐름은 유지하되 전략/뉴스/활동의 책임은 재편한다. 단순 기능 덧붙이기나 전면 재작성은 목표가 아니다.
- 전략 태그/버킷, 규칙 계산/모델 제안/사용자 결정/실제 체결을 구분한다.
- 새 민감정보는 공유에 자동 포함하지 않는다. 기존 데이터·편집 흐름·명시적 공유 범위를 조용히 잃지 않는다.
- 기존 앱의 어두운 테마와 컴포넌트를 기반으로 모바일 우선 반응형을 검증한다.

## 현재 상태와 다음 시작점

- 우선 적용 결정은 [ADR-0004](./adr/0004-domain-storage-and-minimal-mutation-contract.md)다. 도메인 테이블+공통 변경 규약, 필요한 대상별 version, 현재값+중요 이력/당시 snapshot을 사용한다. 범용 type+payload 저장소나 모든 객체 revision 엔진을 새로 만들지 않는다.
- [구현 현황 감사](./tickets/implementation-audit-20260921.md)가 로컬 완료·부분 완료·외부 대기 판정의 기준이다. #32/#37/#38/#41/#42/#44는 로컬 범위 완료, #33~#36/#43은 핵심 구현 후 운영/사용성 검증 대기, #39는 미완료다.
- migration 001~019에 일일 context/브리핑, 판단·조사 task, 개인 기준, 보유 이유, 완료 매매, 보정/확인/취소, 실행 계획, 기능별 공유와 공개 DTO가 있다. DB 작업은 항상 `supabase/schema/OVERVIEW.md`부터 읽는다.
- OAuth MCP는 공통 정의의 35개 도구와 self-contained instructions를 사용한다. 로컬 Edge에서 인증된 initialize/tools/list/오류 계약을 확인했다. prompt/resource는 선택적이며 제품의 전제가 아니다.
- 기존 agent-token `portfolio-mcp`는 legacy `mcp_*` RPC를 쓰는 호환 endpoint다. OAuth 도구와 의미가 달라 같은 배열로 합치지 않으며 신규 기능은 OAuth endpoint에만 추가한다.
- React 앱은 기존 자산 4가지 보기와 표 편집을 유지하면서 오늘/판단/할 일/원칙, 매매 기록·취소, 잔고 보정·확인, 공유 읽기를 연결했다. Google 로그인 시작 경로를 포함한 전체 Chromium E2E 22개가 통과했다.
- 자동 검증 기준점은 DB 223 assertions, Vitest 53 tests, Playwright 22 tests, production build, encoding check다. 숫자가 바뀌면 실제 최신 실행 결과를 기록한다.

## 저장·공유 주의

`git log`와 `git status --short`로 실제 상태를 다시 확인한다. `.claude/settings.local.json`과 `.e2e/supabase/.temp/cli-latest`는 사용자/로컬 런타임 파일이므로 기능 커밋에 섞거나 되돌리지 않는다. 비밀값을 문서에 복사하지 않는다.

새 세션 시작 요청 예시:

> AGENTS.md와 docs/START-HERE.md, docs/tickets/implementation-audit-20260921.md를 읽고 현재 Git 상태를 확인해줘. 운영 배포는 하지 말고 #39의 배포 전 점검부터 진행해줘.
