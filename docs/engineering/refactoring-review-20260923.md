# 구조 리팩토링 추가 검토

2026-09-23 · 정적 검토 · 구현 승인/완료를 뜻하지 않는다.

## 버그와 분리

입력 유실·취소·숨겨진 필드 검증·원칙 조회 경합은 #104~#106에서 관리한다. 아래는 외부 동작/저장 계약을 유지하면서 변경 비용을 줄이는 후보다. 이번에는 제품 코드, DB, 배포 설정을 변경하지 않았다. DB/RLS 전수 감사나 런타임 성능 측정 결과가 아니다.

## 우선순위와 범위

### 1. 전략 계산을 React 표현에서 분리 — 우선 권장

근거: src/features/strategy/StrategyPage.jsx의 StrategyDashboard는 목표/현재 비중, 부족액, 이탈 기준, 매매 한도, 적립금 계산과 JSX를 함께 담당한다. 동일 파일에 draft 변환, BucketEditor, StrategyEditor, ModeModal, PrinciplesModal과 조회/저장 조립도 있다.

- 첫 소비자: 기존 전략 대시보드 하나. 여러 소비자가 없어도 계산 자체를 독립 검증할 목적이 명확하다.
- 최소 변경: 전략 폴더 안에 순수 계산 함수와 단위 테스트를 둔다. 편집 컴포넌트는 실제 변경 책임에 맞춰 분리하되 범용 폼 엔진은 만들지 않는다.
- 효과: 한도/비중 계산 변경을 브라우저 없이 검증하고 UI 수정이 계산 코드를 건드리지 않게 한다.
- 완료 기준: 현재 계산값의 특성화 테스트(0원 자산, 미확인 평가액, 모드별 목표, 한도/적립금 경계)를 먼저 작성하고 추출 전후 결과 일치를 확인한다. 계산 의미 변경은 별도 버그/제품 결정으로 분리한다. 서버 금융 확정 계산을 프런트로 옮기지 않는다.

### 2. 공유·게스트 접근 책임을 자산 액션 묶음에서 분리 — 다음 권장

근거: src/features/portfolio/actions.js의 createPortfolioActions는 자산 CRUD 액션 조립 외에 signOut, handleGuestUnlock, handleSaveViewerProfile, 시세 동기화를 함께 담는다. src/App.jsx는 이 팩토리에 자산 편집 상태와 인증/공유 상태 setter를 함께 전달한다. 계좌/보유/종목/태그 액션 파일은 이미 분리되어 있으므로 다시 전면 분해하지 않는다.

- 최소 변경: 기존 공유/인증 기능 위치에 게스트 unlock·공유 프로필 작업의 전용 hook/모듈을 두고 해당 상태와 의존성만 소유하게 한다. App은 세션과 소유자 전환 조립을 유지한다.
- 효과: 공유 동작을 수정·테스트할 때 무관한 보유/태그 편집 의존성을 준비할 필요가 줄어든다.
- 완료 기준: 자산 액션 입력에서 공유 관련 setter/초안 의존성이 제거되고 기존 자산 액션 테스트와 게스트/친구/소유자 전환 회귀가 유지된다. 권한 판단은 서버에 남긴다. 전역 Context/상태관리 라이브러리 도입은 범위 밖이다.

### 3. E2E를 사용자 흐름별로 분리 — 운영 편의 개선

근거: e2e/app.spec.js에 배포 계약·피드백·점검·원칙·활동·자산·공유·반응형 검증이 함께 있다. e2e/helpers.js는 이미 있으므로 보조 프레임워크가 아니라 파일 책임을 정리하면 된다.

- 최소 변경: 활동, 원칙, 자산, 접근/공유, 앱 탐색 등 실제 시나리오 기준으로 나누고 재사용하는 메뉴 탐색만 기존 helpers에 옮긴다.
- 효과: 기능별 테스트 실행·실패 탐색·새 회귀 테스트 추가가 쉬워진다. 분리 자체가 실행 속도를 보장하지는 않는다.
- 주의: 동일 테스트 사용자를 공유하고 DB 쓰기가 있으므로 파일 분리로 worker 간 병렬 실행이 생기지 않게 기존 실행 순서/격리를 먼저 명시한다. 단순히 fullyParallel을 켜지 않는다.
- 완료 기준: 기존 테스트 목록/개수와 인수 조건을 보존하고 기능별 및 전체 실행을 모두 확인한다. 테스트 속도 최적화는 별도 측정 후 판단한다.

### 4. 활동 표현의 구 호환 코드는 릴리스 후 제한적으로 정리 — 낮은 우선순위

근거: src/features/activity/ActivityEventViewer.jsx에 폐기한 뉴스/번들/일시정지/실행계획 action label과 repairMojibake 등이 남아 있다. 이는 새 기능의 핵심 구조 문제는 아니며 일부는 운영의 과거 자동 기록 표시용일 수 있다.

- 먼저 실제 생성 경로와 #91 운영 전환 시 남길 데이터/표시 요구를 확인한다. 로컬 코드에서 오래된 이름이 보인다는 이유만으로 삭제하지 않는다.
- 없어질 생산자와 소비 데이터가 확인된 분기만 제거하고 알 수 없는 활동 fallback은 유지한다. 낮은 비용의 라벨 제거만으로 큰 효과가 있다고 주장하지 않는다.
