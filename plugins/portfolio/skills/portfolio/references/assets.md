# 자산·거래·잔고 관리

## 대상과 현재값

`get_portfolio_state`를 읽고 계좌/종목이 모호하면 `find_holdings`로 확인한다. 등록된 종목에 보유 행이 없는 것과 보유 행의 수량이 0인 것은 다르다. 여러 계좌가 있으면 금융 변경의 대상을 특정한다. 시장 종목의 활동 티커 참조는 특정 계좌의 금융 변경 대상이 아니다.

계좌는 `save_account`, 종목 등록은 `create_instrument`, 종목과 계좌별 보유 수정은 `save_asset_detail`을 사용한다. 현재값·버전과 승인한 수정 범위를 기준으로 필요한 필드를 보낸다. 현금·평가형 자산과 시장 종목의 입력 차이는 도구 schema를 따른다. 시세/환율은 직접 입력하지 않고 요청받은 가격 갱신에 `sync_prices`를 사용한다.

`get_strategy_state`로 현재 배분을 읽고 `save_allocation_targets`가 전체 목표 집합을 대체한다는 점을 고려한다. 일부 변경 시 나머지 목표를 보존한다. 목표 초기화와 전부 0% 설정을 혼동하지 않는다. `배분에 포함`에서 제외된 보유도 전체 자산·잔고에는 남는다. 자산 태그, 활동 태그, 목표 비중은 서로 다른 대상이며 목표 초기화가 태그 삭제는 아니다.

삭제는 도구 설명의 영향과 현재 대상을 확인한 승인 범위에서 수행한다. 계좌·종목은 수량이 0이어도 보유 행이 있으면 삭제할 수 없다. `delete_holding`은 현재 보유 행 삭제이며 증권사 매도를 실행하지 않는다.

## 종목·계좌 메모

이유를 검토하는 요청과 실제 메모 수정 요청을 구별한다. 승인한 메모 변경은 현재 내용을 읽고 `update_entity_note`의 해당 entity_type과 expected_note를 사용한다. 계좌 메모와 여러 계좌에서 공유하는 종목 공통 메모를 혼동하지 않는다. 종목 메모는 전체 포트폴리오 공유 범위에 속한다.

저장 후 현재 메모를 재조회한다. 반환된 `activity_id`가 있으면 `get_activity`로 자동 기록을 읽을 수 있다. 변화 없음이나 과거 재시도 응답에 ID가 없다고 실패로 단정하거나 수동 기록을 추가하지 않는다. 별도 재검토 할 일은 요청된 경우에만 만든다.

## 이미 체결된 거래

“사면 어떨까”는 판단/계획이며 체결 기록이 아니다. 사용자가 실제 체결을 기록해 달라고 했을 때 계좌·종목·매수/매도·수량·체결가·날짜를 확인한다. 날짜 생략 시 적용할 사용자 시간대 날짜를 밝힌다.

`preview_trade_entry`로 보유 수량·평균가 전후를 계산해 보여준다. 미리보기는 저장·예약되지 않는다. 명시적인 체결 기록 요청 범위 안에서 정확히 같은 입력과 반환된 보유 ID/버전, 안정적인 중복 방지 키로 `log_completed_trade`를 호출한다. 보유 버전이 바뀌면 새 미리보기와 변경 효과를 확인한다. 수수료·세금은 단순 체결가 평균원가 계산에 포함되지 않는다.

`list_transactions` 등으로 저장 결과를 확인한다. 이는 앱 기록이며 증권사 주문·송금·자동 현금 정산·증권사 잔고 인증이 아니다. 응답이 유실되면 동일 키·입력을 재사용하며 추가 기록을 만들지 않는다.

## 실제 잔고로 보정

파일을 해석할 때 관련 사용자 원칙이 있으면 `list_principles`로 읽는다. 원칙 없음과 조회 실패를 구분하고 자료에 없는 수량/원가를 추정하지 않는다. `find_holdings`와 사용자가 확인한 실제 증권사 현재값을 비교한다. 이미 맞으면 금융 쓰기나 별도 확인 상태 저장이 필요 없다.

다르면 `preview_holding_reconciliation`로 절대값 보정 효과를 보여준다. 사용자가 효과를 확인하면 같은 값·사유·날짜·현재 보유 버전·중복 방지 키로 `reconcile_holding`을 호출한다. 충돌이면 현재값을 다시 읽고 새 효과를 확인한다.

잘못된 과거 거래 기록을 반대 거래나 과거 재생으로 되돌리지 않는다. 기록 본문 편집/삭제는 현재 보유를 바꾸지 않는다. 보정은 자동 활동을 만들므로 같은 사실의 수동 기록·완료 할 일을 추가하지 않는다.
